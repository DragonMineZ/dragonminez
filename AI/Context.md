# DragonMineZ AI Context

This file captures project context that AI agents should read after `AI/Agents.md` and `AI/Memory.md`. Keep it factual and update it when the architecture, workflows, or important repo conventions change. Last full audit against the code: 2026-07-07 (v2.1.1).

## Project Snapshot

DragonMineZ is a Minecraft Forge mod for Minecraft `1.20.1`, Java 17, mod id `dragonminez`. The root project name is `DragonMineZ`; archives are named from `mod_id`.

This repo is data-heavy and player-customizable. Many systems load JSON from runtime folders in `config/dragonminez`, world save folders (`<world>/dragonminez/...`), datapacks, and external addon folders. Do not assume JSON is internal-only or safe to rewrite destructively.

Dependencies declared in `META-INF/mods.toml`: Forge, Minecraft, GeckoLib, TerraBlender, and **Curios** are all `mandatory=true`. Legendary Tooltips, Epic Fight, and Better Combat are declared `type="incompatible"`, and the `com.dragonminez.DragonMineZ` entry class additionally throws `IllegalStateException` at construction if any of them is loaded.

## Build And Run

Use the Gradle wrapper from repo root, usually PowerShell on Windows:

```powershell
.\gradlew.bat build
.\gradlew.bat runClient
.\gradlew.bat runServer
.\gradlew.bat runData
```

Important details:

- Java toolchain and compiler release are Java 17.
- `runClient` and `runServer` use `run/` as working directory; `runData` uses `run-data/` and writes to `src/generated/resources/`.
- `src/generated/resources/` is included as a main resource source set. `build` depends on reobfuscation tasks and re-runs `runData`.
- Gradle runs **offline** (`org.gradle.offline=true` in `gradle.properties`).
- The distributable jar is the no-classifier `jarJar` artifact (bundles `mariadb-java-client` and `HikariCP`); the plain `jar` task produces `-slim`. Never ship the slim jar.
- Client-only dev mods (JEI runtime, Oculus, Xenon, Free Cam, Huge Structure Blocks) are on the classpath only for `runClient` (`includeClientOnlyDevMods` in `build.gradle.kts`) because some mixin into vanilla codecs and would poison `runData` output.
- PackSquash optimizes bundled PNG/OGG/JSON before jar packaging; automatic on CI, off locally, forced with `-PoptimizeResources=true|false`. Options in `packsquash.toml`.
- There is no committed `src/test` suite. Validate with `build`, `runClient`, `runServer`, or targeted in-game scenarios.
- `scripts/check_lang.sh` validates language JSON with `jq`.

## Lifecycle

Primary boot path:

- `com.dragonminez.DragonMineZ` is the `@Mod` entry point. Its constructor first enforces the incompatibility list (legendarytooltips, epicfight, bettercombat), then calls `DMZCommon.init()`, then side-specific init through `DistExecutor` (`DMZClient.init()` on client, `DMZServer.init()` on dedicated server — the latter is log-only; commands register via event).
- Root-package helpers: `Reference` (MOD_ID), `Env`/`LogUtil` (logging).

`DMZCommon.init()` is the central registration and setup point, in order: `ConfigManager.initialize()`, `QuestRegistry.init()`, `WishManager.init()`, `NetworkHandler.register()`, `GeckoLib.initialize()`, then deferred registers on the mod bus — `MainAttributes`, `EntityAttributes`, `MainBlocks`, `MainBlockEntities`, `MainItems`, `MainFluids`, `MainSounds`, `MainTabs`, `MainEntities`, `MainVillagers`, `MainParticles`, `MainRecipes`, `MainMenus`, `MainEffects`, `MainEnchants`, `MainLootModifiers`, `MainStructurePlacements`, `MainStructureProcessors`, `MainStructureTypes`, `OverworldFeatures`, `SacredKaiFeatures` — plus `ModCommonEvents::commonSetup`, `MainGameRules.register()`, `MainDamageTypes.register()`. Note the structure/feature classes live under `server/world/...` but register from common init.

`ModCommonEvents` (mod bus) also registers entity attributes, adds player attributes (`STRENGTH`, etc.), registers `DragonBallSavedData` capability, adds a pack finder, and in `commonSetup` registers the TerraBlender `OverworldRegion` (weight 40, adds the rocky biome without replacing vanilla biomes) and `OverworldSurfaceRules`.

Server event flow (`common/events/ForgeCommonEvents`, forge bus):

- `onServerAboutToStart`: pre-loads Otherworld regions when `worldGen.otherworldActive`, and runs `VillagePoolInjector.injectAll`.
- `onServerStarting`: `StorageManager.init()`, `BetaWhitelist.reload()` (async), `WishManager.loadWishes(server)`, `DMZPermissions.init()`, `QuestRegistry.loadAll(server)`, `NpcAlignmentRules.load`, `NPCPlacementManager.load`, `WorldGuardCompat.init()`, then first dragonball scatter per ball set if `worldGen.generateDragonBalls`.
- `onServerStarted`: `StructureSpawnPlanner.precomputeAndWait`, Otherworld region load (double-check), `NPCPlacementManager.spawnForLoadedLevels`.
- `onLevelLoad`: `StructureSpawnPlanner.onLevelLoad`; re-runs Otherworld region loading when the Otherworld level loads.
- `onServerStopping`: `StorageManager.shutdown()`, `StructureSpawnPlanner.reset()`.
- `onAddReloadListeners`: `SpacePodDestinationRegistry`, `DragonDefinitionReloadListener`, `DragonWishRegistry`, and an inline listener calling `WeaponRegistry.loadAttributes`.
- `onRegisterCommands` → `DMZServer.registerCommands`.
- `ForgeCommonEvents` also hosts gameplay handlers: login/logout/death/respawn/dimension-change, melee/ranged crits, `LivingAttack`/`LivingDamage` mitigation hooks, equipment change, mob spawn finalize, villager trades.

Registration pattern:

- New content belongs in a `common/init/Main*` class registered from `DMZCommon.init()`.
- New packets must be registered in `NetworkHandler.register()`; see Networking below for ordering rules.
- New mixins require both a Java class and an entry in `dragonminez.mixins.json`.

## Player State

Player state is capability-based:

- Core classes: `common/stats/StatsCapability`, `StatsProvider`, `StatsData` (~1570 lines; state + most stat/form/combat math).
- `StatsCapability` registers the capability and attaches a `StatsProvider` to every `Player` in `AttachCapabilitiesEvent<Entity>`. `StatsProvider` implements `INBTSerializable` (`serializeNBT()→data.save()`, `deserializeNBT()→data.load()`), so vanilla `.dat` persistence is always active regardless of storage backend.
- `StatsData` owns exactly 12 sub-objects (ctor-constructed): `Stats`, `Status`, `Cooldowns`, `Character`, `Resources`, `Skills`, `Effects`, `SecondaryStatEffects`, `PlayerQuestData`, `BonusStats`, `Techniques`, `DynamicGrowthData`. (There is no `Training` object; training config lives in `config/dragonminez/training.json`.) Sub-objects live in `common/stats/character/`, `common/stats/skills/`, `common/stats/techniques/`, `common/stats/extras/` (DynamicGrowthData), and `common/quest/` (PlayerQuestData).
- NBT keys written by `save()`: `Stats`, `Status`, `Cooldowns`, `Character`, `Resources`, `Skills`, `Effects`, `SecondaryStatEffects`, `PlayerQuestData`, `BonusStats`, `Techniques`, `DynamicGrowth`, `HasInitializedHealth`. These are the save-format contract for all three storage backends — renaming any silently orphans existing NBT/JSON/DB data.
- `load()` is a per-key partial loader EXCEPT it hard-throws (`ClassNotFoundException`, wrapped in RuntimeException) when the `PlayerQuestData` key is absent. Treat `load()` as a full-document loader, not a safe partial merge.
- Clone (death/dimension): `onPlayerClone` revives caps, `newData.copyFrom(oldData)` (deep copies; PlayerQuestData round-trips through NBT), invalidates old caps. A client-side `static StatsData CLIENT_CACHE` preserves character-creation state across clone only.
- Login sync (`onPlayerLogin`): sends every config file except `general-user` via `SyncServerConfigS2C` (first packet `reset=true`), `SyncQuestRegistryS2C`, then per-player fixes (visited dimension, unlock `saiyan_saga`, form-selection defaults, clear stun/knockdown/strike-lock, skill-name repair, deactivate kisense) and a full `StatsSyncS2C`.
- Adding a state group requires updating ctor + `save()` + `load()` + `copyFrom()` together, and deciding which sync packet carries it.
- `Character#aura3D` (NBT `Aura3D`) is a purely cosmetic flag that does not belong to gameplay state: it mirrors the owning client's `general-user` `aura3DPersonal` option so that every OTHER client renders that player's aura in the style its owner picked. The client pushes it with `AuraModeC2S` when the option is toggled, and `AuraModeState.reconcileLocal` re-pushes it whenever a `StatsSyncS2C` for the local player disagrees — that self-heals the login race against the async storage load, plus respawns and dimension changes, without a dedicated handshake. The viewer's own `aura3DEntities` option governs NPC auras instead, since entities have no owner.

Sync packets (all decode into the same client-side `data.load(nbt)`):

- `StatsSyncS2C` = full `data.save()` (login, dimension change).
- `ProgressionSyncS2C` = `Stats` + `BonusStats` + `Skills` + `Techniques` + `PlayerQuestData` (after progression changes, `/dmzreload`).
- `ResourceSyncS2C` = `Resources` + `Status` only (respawn, resource changes). Because `load()` throws without `PlayerQuestData`, this packet relies on the client already having full data — be careful changing `load()` or packet contents.

Ticking is split across THREE PlayerTick handlers:

- `StatsCapability.onPlayerTick` (server, END phase) → `StatsData.tick()` which only ticks `Cooldowns`.
- `server/events/players/TickHandler` — the real gameplay loop: regen (every 20 ticks), sync (every 10), effects/secondary-stat-effects/techniques ticking, aura light, stun handling.
- `server/events/players/StatsEvents` — weights, food-regen queue, health. Also applies the max-health `AttributeModifier` (`DMZ_HEALTH_MODIFIER_UUID`); energy/stamina/poise are custom attributes from `MainAttributes` (`MAX_ENERGY`, `MAX_STAMINA`, `MAX_POISE`). `hasInitializedHealth` (persisted) gates the one-time full heal.

Race, class, form, stack-form, effect, mastery, TP, and stat calculations read `ConfigManager` live on every call — there is no memoization, so `/dmzreload` changes results immediately.

## Networking

`NetworkHandler` creates a Forge `SimpleChannel` named `dragonminez:network` (protocol "1.0", all versions accepted). ~54 C2S and ~25 S2C packet classes live in `common/network/C2S` and `common/network/S2C`.

- Packet ids come from a sequential `id()` counter, so **registration order defines the wire ids**. Append new packets; never reorder or insert mid-list, or client/server builds desync.
- Each registration is a `messageBuilder(...).decoder(...).encoder(...).consumerMainThread(handle).add()` triplet with explicit `NetworkDirection`.
- Helper send methods: `sendToServer`, `sendToPlayer`, `sendToAllPlayers`, `sendToTrackingEntityAndSelf`, `sendToTrackingEntity`.
- C2S categories: character creation/update, stat/skill changes, quests (accept/claim/unlock), wishes (`GrantWishC2S`), space pod travel, actions/forms/release limit, flight/dash/ki blasts, party, techniques, combat. S2C: stat/resource/progression sync, config sync, quest/wish registry sync, radar sync, animations, UI opens, party toasts, weapon registry sync, space pod destinations.
- Validate all C2S input server-side. Never trust the client for stats, unlocks, permissions, quests, wishes, or progression.

## Client HUD

Main HUD style is the client-only `style` string in `hud_layout.json` (`"default"`, `"minecraft"`, `"legacy 1"`, `"legacy 2"`; `client/gui/hud/HudStyle`). It replaced the old `alternativeHud` boolean, which is still read once for migration (`true` -> `"minecraft"`). Every other old HUD key (`xenoverseHudPosX/Y/Scale`, `healthBar/energyBar/staminaBarPosX/Y`) was removed from the UI and the code; the fields survive only as null, accessor-less ghosts in `GeneralUserConfig` so `JsonSchema` does not warn about unknown fields in existing files, and `getHudStyle()` nulls them so the next save drops them. All overlays are always registered (`ModClientEvents`); each one early-returns unless it is the current style, and every overlay skips itself while the HUD editor is open (`HudLayout.isPreview()`), because the editor draws the HUDs itself on top of its dim layer.

- Notifications (`client/gui/hud/NotificationHUD`, Extras element `notifications`, default top-right anchor 1/0, offset -6/6, scale 0.9): one stack for everything that used to be the tracked-quest panel, the quest notices, the tutorial hint and the tournament live notice. Entries are `Content(title yellow, subtitle light blue, description white, extra small grey bottom-right)` drawn in the `smooth` font on a `HudRender.panel` (semi-transparent fill + 1 px darker frame, no bars). Two kinds: `push(content, priority)` = transient, 5 s (`DURATION_MS`), at most 5 live, and `pin(key, Supplier<Content>, priority)` = persistent while the supplier returns non-null (`NotificationFeeds.registerDefaults()` pins `tracked_quest` = 1000, `tutorial_hint` = 950, `tournament` = 900 via `TournamentOverlay.notification()`). Order is priority desc, then newest first, so a new notice of the same priority pushes the older one down. Each entry owns two `HudSmoother`s: `appear` (fade + slide from the nearest screen edge, quadratic ease; the same path in reverse when it leaves) and `y` (slot glide when others push it). Stacking grows upward when the anchor is at the bottom. Feeders: `StoryNotificationManager` (quest started/failed/objective/complete), `ClientPacketHandler` (party invite, quest start failure), `VersionCheckerUtil` (update available). `SagaTitleCardHUD` and the vanilla titles of the world boss stay as they are.
- Layout (`client/gui/hud/layout/HudLayout`, `HudElement`): position, scale and visibility of every element (`main`, `minecraft_left/right`, `party`, `reserve`, `rage`, `skill_1..4`) live in `hud_layout.json` -> `layout.<style>.<element>` (`HudPlacement`: screen anchor 0/0.5/1 per axis + offset + scale + visible + hotbar). Missing entries fall back to `defaultPlacement`, so defaults can change without touching user files. Offsets and scale are stored in REFERENCE units: `HudLayout.unit` = GUI height / 360, so an element covers the same share of the screen at any window size or GUI scale (what the menus do with `ScaledScreen`). Exceptions that stay in raw GUI pixels because they hug the vanilla hotbar: the Minecraft-style side blocks and the three `legacy 2` elements (`legacy2_health`, `legacy2_ki` = ki bar + release/form icon, `legacy2_stamina`, each placed on its own; that style has no `main` element). `HudLayout.resolve` returns the box a HUD must draw into; HUDs never position themselves.
- Technique hotbar (`TechniqueHotbarHUD`): its four rows are layout elements `skill_1..skill_4` (every style; base 120x13 reference units, default staggered as a ladder, mirrorable; excluded from the meter collapse chain). Both technique bars (slots 1-4 / 5-8) share those rows. Display rules: holding a bar modifier shows that bar at full opacity; on release rows fade out fast (`FADE_SECONDS`), except a slot whose `TechniqueCooldown_<id>` is running, which settles at `COOLDOWN_ALPHA` for the whole cooldown, blinks when the synced cooldown reaches 0 and fades out `READY_LINGER_MS` later. If both bars have a lingering slot in the same row, the one closest to ready wins. One `HudSmoother` per slot, so closing the bar glides straight to the reduced opacity. In the editor a right-click on any row mirrors all four (positions reflected inside the group bounds), Shift+drag moves the group, resizing a row rescales the group around it, and Reset on a row resets the four. The old `techniqueHotbarRightSide` key is a null ghost field in `GeneralUserConfig` (same trick as the other removed HUD keys).
- HUD layout file: the active style and every placement live in their own client-only config, `config/dragonminez/hud_layout.json` (`HudLayoutConfig`: `configVersion`, `style`, `layout.<style|extras>.<element>`), so players can share a layout by sending that one file. It goes through the normal `loadAndValidate` path (versioned, value-preserving regeneration; user-only map keys survive, so a file with a missing/old version still keeps its placements). It is loaded only on `Dist.CLIENT`, is never synced (`ConfigManager.isClientOnlyConfig` covers it and `general-user`), and `HudEditorScreen` re-reads it from disk when it opens (`ConfigManager.reloadHudLayoutConfig`), so dropping a shared file in and opening the editor applies it without a restart. The old `general-user` keys `hudStyle`/`hudLayout` are null ghost fields; `GeneralUserConfig.migrateLegacyHud` moves them (and the older `alternativeHud`) into the new file once, right after load, then nulls every HUD ghost and both files are saved. That method replaced the ghost-nulling side effect that used to live in `getHudStyle()`.
- Editor history: snapshot-based undo/redo (`HudEditorScreen.Snapshot` = style + deep copy of the layout), capped at `HISTORY_LIMIT` = 5 steps each way. One step per gesture: a drag/resize is recorded on mouse release (only if something changed), instant actions (mirror, hide/show, reset, style change) go through `act(...)`, and arrow nudges on the same element within 800 ms merge into one step. Undo/Redo buttons show the available count and dim when empty; Ctrl+Z / Ctrl+Y / Ctrl+Shift+Z work too. Cancel restores the snapshot taken when the editor opened.
- Mirroring: `HudPlacement.mirrored` (right-click in the editor; only where `HudLayout.canMirror` allows it: `main` of `default`/`legacy 1`, `party`, and the technique rows). Nothing is drawn with a negative scale: `HudBar.setMirrored` flips the sprite UVs and anchors fill/chips/glint on the right, `HudRender.spritePart(..., flipX)` / a negative region width in `HudRender.blit` do the flipping, text is re-aligned instead of flipped, `HeadPortraitRenderer` negates its yaw, and `XenoverseHUD.part()` mirrors every blit around the element width except the baked `STM` label, which is drawn unflipped at the mirrored spot.
- Dynamic collapse: a side meter within `DOCK_DISTANCE` of a screen edge (or chained to one) slides out through that edge while it is empty/not applicable, and everything linked behind it (other elements within `LINK_DISTANCE` on its far side, overlapping on the other axis) shifts by the freed space. Links are geometric, never stored. A meter that is not docked stays visible even when empty. Meter visibility is fed by `HudSideMeters.update` -> `HudLayout.setMeterVisibility`.
- Minecraft style: a side block whose placement has `hotbar=true` ignores its box and keeps the hotbar-glued behaviour (slides with the offhand slot / attack indicator, shrinks on narrow screens); dragging it away in the editor clears the flag, snapping it back onto the hotbar side sets it again.
- Editor (`client/gui/config/HudEditorScreen`, opened from the config menu entry `config.hudEditor`): dims the screen, redraws the HUDs in preview mode (meters forced visible with a sample value, party shows sample members when empty), drag to move with 5 px soft-snaps (screen edges/margins, centre of each axis, other elements' edges with a gap, the hotbar for Minecraft blocks) drawn as guide lines, 8 handles for uniform resize, arrows to nudge, Show/Hide per element, Reset (selected or all), Cancel restores the whole layout and the style it opened with, Done/Esc saves `hud_layout.json`. The HUD style is chosen HERE (Style button cycles `HudStyle`; there is no separate style option in the config menu any more). Title and buttons sit at the top centre and use the DMZ widgets (`TexturedTextButton`, which now honours `AbstractWidget` alpha, `TextUtil` bordered text, the `smooth` font); the buttons fade out while an element is being moved/resized and back in afterwards, while the title (top) and the hint (bottom) always stay visible.
- `ModernHUD` (`default`), `MinecraftHUD` (`minecraft`), `PartyHUD` and `KiReserveHUD` draw from sprite sheets (`textures/gui/hud/hud_default.png`, `hud_minecraft.png`, `hud_party.png`, `hud_reserve.png`); the layout lives in `HudSprites`. Sheets are authored at 2 texels per GUI pixel and every on-screen size is derived from the sprite sizes (`BarSkin.width()/height()/border()`), while UVs are normalised against the LOGICAL sheet size passed to `HudRender.blit` - so a resource pack may ship any resolution (blockier or HD) as long as it keeps the layout and aspect ratio. Changing a sprite's size means updating its `HudSprites` entry. Bar layers: `frame` (border + empty track, drawn whole), `fill` (greyscale, multiplied by the stat colour, cropped to the value), `shine` (untinted highlights, cropped the same way), optional `alert` (red frame faded in at critical health). Section grooves and shading are baked into the sprites; only dynamic effects stay procedural (leading-edge glint, ki-charge sweep, surge/form-charge strips, reserve cap line, downed-ally overlay). Icons sit inside a square `capsule` sprite that shares its outline with the bar. `XenoverseHUD`/`AlternativeHUD` are the legacy texture HUDs (`legacy 1`/`legacy 2`); they use `HudRender.blit` so bar widths are sub-pixel too.
- Animation is per rendered frame, never per tick: `HudSmoother` (wall-clock exponential smoothing, jumps after a >1 s gap), `HudBarAnimator` (front + damage/heal ghost chip), and `HudBar` (bundles both plus the counting number and `HudStatNumberAnimator` fade/pulse). `HudBar.drawValue` keys the number animator on the REAL value, not the counting text, or the colour pulse is cancelled every frame. `SurgeBarState.fraction` integrates time, so call it once per frame (only one main HUD is active).
- `HudPlayerState.of(player, data)` is the per-frame snapshot shared by the main HUDs and the party rows (works for any tracked player: `StatsSyncS2C` reaches trackers every 10 ticks).
- Shared by every style: the side meters (`HudSideMeters`; `KiReserveHUD` = Frost Demon reserve tinted with the player's ki/aura colour, max = `maxEnergy * reserveMaxRatio`; `RageMeterHUD` = Mutant rage in dark green, or the Saiyan False Super Saiyan charge in red). Also shared: `PartyHUD`.
- Party HUD data: `PartyPackets.sendHudSync` (from `TickHandler`, same 10-tick cadence as the stats sync) sends each party member every online ally (nearest first, capped at `SYNC_MAX_MEMBERS` = 16) with name/HP/Ki/distance, world position, base aura colour and a `marker` flag as `HudSyncS2C` -> `PartyHudCache` (entries go stale after 2.5 s, cleared on disconnect). `PartyHUD` only draws the first `HUD_MAX_MEMBERS` (3). When the ally entity is loaded client-side the row reads live entity health and the synced capability instead, so bars move every frame; otherwise it shows the packet values, the distance, and the skin face.
- Party markers (`client/gui/hud/PartyMarkerOverlay`, registered first so every HUD draws over it; user toggle `partyMarkers` in the config menu): a Roblox-style arrow with the name and distance over each party member's head, any distance, through walls. The server decides visibility (`marker`): same dimension, within `gameplay.partyMarkerRange` (2000, the Instant Transmission menu range at level 10), alive, not spectator, and the same filters as the Instant Transmission list (`hasAntiKiCloak`, `isInstantTransmissionBlocked` = god form without `godforms`, upgraded android) plus the ki-sense rule that a player at 0% release is hidden. The client projects the head position with `CameraProjectionCapture` (projection x view captured at `AFTER_LEVEL`, camera position); loaded allies use their interpolated entity position, far ones the packet position through three `HudSmoother`s. Hidden closer than 2.5 blocks and when the point is off screen. Sprite `HudSprites.PARTY_MARKER` (`hud_party.png` 200,0 32x32), tinted with the ally's base aura colour or red when down; size and text scale use the HUD reference unit.
- Head portraits (`client/render/HeadPortraitRenderer`): renders the third-person `DMZPlayerRenderer` directly (never through the entity dispatcher, which would pick the head-less POV renderer in first person). While `HeadPortraitRenderer.isActive()`, `DMZPlayerRenderer` skips mask capture/aura stencil/aura border/model scaling/body rotation/name tag, only runs the skin, hair and race-parts layers, and `renderRecursively` drops every bone that is not `head` or a descendant (ancestors contribute no cubes and no transform; the head's own animation is zeroed) so the portrait stays framed during any animation. Hair uses `HairRenderContext.menuPreview()` (static, never touches the world simulation state) and ignores the first-person/helmet hiding rules. The entity render writes depth: anything drawn over a portrait afterwards needs a positive Z translate.

## Client Menus

Every DMZ menu extends `client/gui/character/util/ScaledScreen` (the tabbed character menus through `BaseMenuScreen`). Menus draw in "UI coordinates" inside `beginUiScale`/`endUiScale`; mouse input is converted with `toUiX/toUiY`, scissors with `toScreenCoord` (scissors ignore the pose, so add any slide offset by hand).

- Scale is LINEAR, like the HUD: `uiScale = guiHeight / REFERENCE_HEIGHT (270) * menuScaleMultiplier`, capped so the canvas never gets smaller than `getMinGuiWidth() x getMinGuiHeight()` (320x240 by default, 420 wide for `BaseMenuScreen`, 365x293 for the NPC dialogue / technique creator) and floored at `getMinUiScale()` (0.25). The UI height is therefore constant (270 / multiplier) at any window size or GUI scale, so a menu always covers the same share of the screen; the old `sqrt(availableScale)` formula is gone. `UtilityMenuScreen` overrides `computeDynamicScale` to keep its own (already linear) formula. `ScaledScreen.adjustMenuScale(+-1)` steps the multiplier by 0.05 and refuses to grow past the fit cap. The default multiplier is `GeneralUserConfig.DEFAULT_MENU_SCALE` = 0.75 (UI height 360, the size that reads well on every screen); the 2.1.x baseline in `previousConfigs` keeps 1.0 on purpose, so the version merge moves untouched configs to 0.75 and keeps values the player changed.
- Drawing: textures go through the float vertex-buffer blit (`ScaledScreen.blit(...)` -> `HudRender.blit`, plus `HudRender.nineSlice` and `HudRender.rect`), never `GuiGraphics.blit`, so slides and zooms are sub-pixel. The DMZ widgets (`CustomTextureButton`, `TexturedTextButton`, `SwitchButton`) implement `SubpixelWidget`; move them with `ScaledScreen.slideX/slideY(widget, base, floatOffset)` (integer part goes to the hitbox, the remainder to the draw position). Entity previews still need int coordinates, so screens translate the pose by the fractional remainder around `renderEntityInInventory`.
- Animation is per rendered frame on the wall clock: `BaseMenuScreen` open/close/panel-switch progress uses `System.currentTimeMillis` only (no `partialTick` term), panel offsets are floats, `renderMenuBackground` fades the dim layer with the open/close transition, and `ScaledScreen.frameDelta()/frameEase(tau)` (sampled in `beginUiScale`) replace the old `getDeltaFrameTime()*0.4f` and per-frame `approach01` steps. Not converted on purpose: the vanilla container screens in `client/init/menu/screens` (slot hit-testing is vanilla), the minigame playfields and the vanilla-styled utility screens; they only got float blits.
- Config menu (`ConfigMenuScreen`): options are grouped in collapsible categories (`Interface`, `Gameplay`, `Visuals`; expanded state is remembered for the session in a static set) with a search box on top that filters by option or category name and forces matches open. Saga rows are headers (background plate, rotating arrow sprite, bold label, `completed/total` main-quest counter, `[L]` for locked/placeholder sagas), quests with side branches get a small rotating arrow instead of the old `> `/`v ` text, and the secret-sidequest section is a sub-header. `navigatorEntries` is still the logical list (rebuilt every 10 ticks); `mergeNavigatorRows` diffs it into the persistent `navRows` display list, keeping removed rows as ghosts under their closing parent, `updateNavigatorLayout` eases one open-progress per expandable row and lays blocks out recursively (drawer slide + nested scissor per block), and `navPlacementAt` hit-tests the same placements for hover and clicks. ## Interactive Tutorial

`client/gui/tutorial`: a non-blocking first-time guide. A screen calls `TutorialManager.request(this, id, steps)` when its content is ready (idempotent; no-op when tutorials are off or the id was already seen). Nothing else in the screen changes: the overlay is drawn from `ScreenEvent.Render.Post` and input is intercepted from the `ScreenEvent.*.Pre` events, so every screen (scaled or not) can host one. A host that implements `TutorialHost` (all `ScaledScreen`s) supplies its UI scale and canvas size; rectangles are given in the host's UI coordinates through suppliers, so they follow resizes and animations.

- `TutorialStep` (builder): text/title keys, format-arg supplier (re-evaluated every frame), highlight rect supplier(s), `when` condition (skipped when false), `onEnter/onExit` hooks, `passthrough` (clicks inside the highlight reach the screen), `centered`, `width`, `noSkip`, custom `TutorialButton`s (text or +/- icon; `STAY`/`NEXT`/`FINISH`). Without a flow button the popup shows Skip + Next/Got it. Enter/Space = next, Esc = skip (marks the tutorial as seen); every other key and click is swallowed while a tutorial runs. Closing the host aborts without marking it seen.
- `TutorialOverlay`: dim layer built as the complement of the (animated) highlight rects in one `POSITION_COLOR` batch, pulsing accent frame, popup = 9-slice of the `menusmall.png` panel + `characterbuttons.png` buttons, placed right/left/below/above the highlight union (first that fits). It clears the depth buffer and draws at z=900 because screens render entities and text at z up to 500.
- State lives in `general-user.json`: `tutorialsEnabled` and `tutorialsSeen` (list of ids). Config menu -> Interface has the toggle and "Show Tutorials Again". No configVersion bump (2.2.0 is unreleased; missing keys fall back to field defaults).
- Tutorials: `race_selection` (welcome + disable, model/arrows, racial skill), `customization_class` (requested when the Aura/Class tab opens), `hud` (`HudTutorialScreen`, a transparent screen opened by `CharacterCustomizationScreen.finish()` on character CREATION only; waits for `hasCreatedCharacter` to sync, highlights the main HUD boxes from `HudLayout`, offers the HUD editor), `stats_menu` (menu size with +/-, name, level, TPs, each stat with the statistics rows it affects, TPC, TP multiplier; forces the list view while active), `skills_general` / `skills_techniques` (one shared id for Ki/Strike/Evasion) / `skills_forms` (requested from `refreshButtons`, i.e. on tab change), `quest_difficulty` (while the difficulty modal is up) and `quest_menu` (selects the first unfinished main quest, forces the saga panel open, fakes a hover on the target preview).
- `SkillsMenuScreen` injects a client-only `SAMPLE_ENTRY` row while the general/technique tutorial runs and the player owns no real entry; it never touches `Skills`/`Techniques` (the techniques getter returns the live capability map). Button init and detail rendering guard against that id.
- `TutorialHintHUD` (registered last in `ModClientEvents`): "Press [key] to begin your adventure" in the tracked-quest HUD slot while the player has no character, no screen is open and tutorials are enabled. With `forceCharacterCreation` on, the creation screen opens by itself and the hint is rarely seen.

## Hair Shading

Strand colours are pixel-shaded in `client/render/hair/HairMeshBuilder`; the configured hair colour (character, form, stack form, strand/tip/segment overrides, aura/form tints) is only the base of a hue-shifted palette, so nothing in configs or save data changed.

- `HairColorRamp`: 9-stop ramp per base colour, built in OKLCH and cached per RGB (256-slot direct-mapped cache, rebuilt on miss). Stop 4 is the exact base; shadows lose lightness, gain chroma and turn towards blue-violet, highlights gain lightness, lose chroma and turn towards yellow. Near-grey bases (black, white, silver) get a cool tint instead, so they are not flat either.
- Shade field = root-to-tip term (`LENGTH_SHADE`, ring arc-length 0 at the scalp, base colour at mid length) + occlusion term (`OCCLUSION_SHADE * (OCCLUSION_PIVOT - ao)`, per ring corner) + facing term per face (`FACING_SHADE * (normal.y - FACING_PIVOT)`, head space, so undersides lean to the shadow hue instead of going khaki under the vanilla diffuse light).
- Pixel quantization (`pixelFace`): every visible face is split into 1x1 model-pixel cells (`CELLS_PER_UNIT`); each column samples the field per row, adds a per-column jitter (`COMB_JITTER`, seeded by strand/face/column so the comb pattern continues along the strand) and snaps to `SHADE_STEP` levels clamped at `DARKEST_SHADE` (4 tones: -0.5, 0, 0.5, 1). Consecutive rows with the same tone are merged into one flat-coloured quad, so a face costs `columns x runs` quads. Internal caps and the far LOD emit one quad per face (centre shade). `DMZHairLayer.wantsPixelDetail`: menus/editor always, world only within 32 blocks of the camera, never in the Iris shadow pass. Detail costs ~2-2.6x the vertices of the flat mesh.
- `HairOcclusion`: ambient occlusion at the 4 corners of every joint ring, from the other strands (segments as spheres, cheap Quilez sphere occlusion) and the 8x8x8 head box. Computed on the REST pose and cached per `CustomHair` identity + revision (`WeakHashMap`), so it costs nothing per frame; editing a style recomputes it (~0.5-1 ms). During a transition `HairEntityState.updateShading` samples the from/to results by arc length and lerps them, so segment-count changes are fine.
- Texture `textures/entity/races/hair.png` is a 16x16 grayscale fibre tile at 1 texel per model pixel, aligned with the cells (V along the strand, per-strand/per-face offsets); it relies on the default GL_REPEAT wrap (no `.mcmeta`). The hairbase layer (`hair_base.png`, `DMZSkinLayer`) still uses the flat published colour.

## Skin Pixel Editor

`client/gui/character/pixel/PixelEditorScreen` (opened from `CharacterCustomizationScreen`) lets the player tag pixels of their own 64x64 skin and draw a custom tattoo by painting directly on the 3D model, Blockbench style. Data lives in `Character#skinPixels` (`common/stats/character/SkinPixels`, NBT key `SkinPixels` inside `Character`): `EyeMarks` and `HairMarks` are 64x64 byte masks in skin-atlas coordinates (eye markers 1 brow / 2 sclera / 3 iris, hair marker 1; base and overlay regions share one mask), `Tattoo` is raw RGBA of `TattooSize` 64/128/256. Every array is deflated in NBT; `SkinPixels.parse(tag, strict)` inflates with exact expected lengths, compressed-size caps and marker range checks (strict mode throws, used by the server; lenient mode drops bad parts, used by `load`).

- Sync: the pixel data is stripped out of `StatsSyncS2C` and `AppearanceSyncS2C` (they are sent on many events) and `Character.load` keeps the in-memory copy when the key is absent. The dedicated `SkinPixelsSyncS2C` is sent after the login/dimension-change `StatsSyncS2C` (`StatsCapability.syncSkinPixels`), on `PlayerEvent.StartTracking` (only to the new tracker), after the async storage load (`StorageManager.applyLoadedData`) and after `UpdateSkinPixelsC2S` (rate limited, validated with `parse(strict)`), to tracking players and self. Persistence goes through the normal `Character.save()` so all three storage backends carry it; `copyFrom` clones it on respawn.
- Rendering (`client/render/util/SkinPixelTextures`): per-player `DynamicTexture`s registered as `dragonminez:pixels/<uuid>/<layer>`, rebuilt when the `SkinPixels` revision or the player's skin `ResourceLocation` changes, evicted after 1200 ticks unused and cleared on logout. Marker masks are shaded: the skin is read back from the GL texture (`SkinPixelTextures.download`, only if it is 64x64) and each marked pixel stores its luminance relative to the brightest marked pixel, so the form tint keeps the skin's own shading. The tattoo texture is the RGBA drawing.
- `DMZSkinLayer`: when `SkinGathererProvider.rendersPlayerSkin(character)` (bodyType 0 on a humanoid logic key or a `useVanillaSkin` race, never Oozaru), `renderSkinPixelEyes` paints sclera (white) + iris (form `eye1Color`) and brows (form `hairColor`) on the head only while a form/stack form defines that colour, with alpha = charge progress while charging towards such a form (`resolvePixelPaint`), so the base form keeps the untouched eyes. `renderSkinPixelHair` paints the hair mask over the whole model ALWAYS (user request): the character's `hairColor` in base, the form/stack colour when transformed and the charge lerp in between (`resolveSkinHairColor`, same rule as the hairbase, and outside the pixel editor it prefers the colour published by `DMZHairLayer` when there is one, so it follows the hair's form tint/aura tint and transition fade; inside the editor it ignores it because the editor's hair preview always publishes the base colour, even while `FormPreview` shows a form), so changing the hair colour recolours the skin's hair too; it is skipped for the bald preset (`HairPresets.BALD_PRESET_ID`). Custom tattoo = `Character.TATTOO_CUSTOM` (-1) in `tattooType`; `SkinGathererProvider.gatherTattooLayers` emits the dynamic texture like a shipped `tattoo_N.png`.
- Painting on the model (`client/render/util/SkinPaintContext`, a static scope like `HairRenderContext`): the editor renders the local player twice per frame inside its viewport. The first pass is a pick pass: `DMZSkinLayer` draws only the body geometry with `ModRenderTypes.skinPaintPick` (emissive shader, no lighting, depth write) and a 256x256 id texture whose texel (u, v) is the colour (u, v, checksum); one `glReadPixels` under the cursor gives the texel under the mouse with 1/4-skin-pixel precision (used for 128/256 tattoos). Overlay texels of the id texture take the skin's alpha so transparent hat pixels do not block the head. Then the depth is cleared and the visible pass renders normally. While the context is active `DMZPlayerRenderer` only runs the skin/hair/race-part layers (no armor, capes, items, aura), `BoneVisibilityHandler` shows or hides the six `*_layer` cubes from `showOverlay`, `DMZHairLayer` and the hairbase honour `showHair`, and `DMZSkinLayer` draws the mark overlays (marker masks tinted brow orange / sclera cyan / iris magenta / hair green) plus the hovered-texel highlight on top. The static pose reuses the hair editor's pause: the viewport renders inside `HairRenderContext.editorPreview(preview)` with a `Preview` whose `physicsEnabled()` is false (the character's own base style, no pick recorder), which is what `PlayerGeoAnimatableMixin` gates on; the player's `tickCount`/walk animation are never touched (resetting them makes GeckoLib's `animTime` jump and the model wobble). The highlight is a 512x512 `DynamicTexture` (`HIGHLIGHT_RES / res` sub-texels per texel) where each hovered or previewed texel gets a white frame with a black inner ring, uploaded per frame only in the dirty rectangle, so the selection reads as an outline instead of a filled square. The cursor position used for picking is the one tracked from the screen's own mouse events, so simulated input (labs) works too.
- Editor: modes EYES (3 guided steps: brows, eye white, iris; opens zoomed on the head), HAIR (2 steps: base layer, overlay layer; 3D hair hidden by default) and TATTOO (free brush with the customization colour sliders + hex field, resolution 64/128/256 with nearest resampling, overlay cubes hidden). Top bar: Undo, Redo, Clear, Overlay (visibility + paint target; only the vanilla layout `SkinAtlas` regions of the visible layer are paintable, the tattoo only base regions), Hair, Eraser, Save, Cancel. Controls mirror `HairEditorScreen` for the camera: a left drag that starts outside the model orbits (yaw + head pitch through `setXRot`), right or middle drag pans, wheel zooms with the same `lerp(0.3)` smoothing. A left press on the model starts a stroke instead (the pick pass decides at press time): dragging is the freehand brush (consecutive samples joined only when at most 8 texels apart, so no streaks across atlas faces), Shift+drag is the axis-locked line, and a click then Shift+click draws the A-B line (Bresenham in texture space); Alt or the Eraser toggle erases. Ctrl+Z / Ctrl+Y / Ctrl+X, 10-action undo/redo (`PixelEditHistory`, whole-layer snapshots). Edits are made on the live `Character` (preview updates through the revision bump); Save sends `UpdateSkinPixelsC2S`, Cancel restores the snapshot taken on open. The left panel's Preview row cycles transformations with `client/gui/character/util/FormPreview`; while a form is previewed the mark overlays are hidden so the real paint shows. `HairEditorUi`/`HairEditorTextures`/`HairEditorSounds` were made public to share the panels, buttons and sounds.
- Saiyan tail (`SaiyanTailMeshBuilder`): same palette and pixel quantization for the visible tail bones `tailN`. `DMZSkinLayer.renderForBone` captures each non-hidden tail bone matrix (validated per render with `HairRenderCapture`); `SkinGathererProvider.gatherBodyLayers` keeps the visibility rule and `bodyColor2` colour but calls `BodyLayerSink.saiyanTail(color)` instead of re-rendering the whole model with `tail1.png` (the default still does that, so other sinks keep the old flat tail). Shade = root-to-tip along the tail direction + a rounded per-cell facing (normal from the cube axis, so the top of the tail reads lit and the underside in shadow) + comb jitter; texture `tail_fur.png` (16x16 grayscale fur) at 2 texels per cell. Same LOD as the hair (`DMZHairLayer.wantsPixelDetail`). The fusion borrowed tail uses its own instance in `DMZRacePartsLayer` (`DonorBoneRenderer.visit` poses the donor `tail1` chain and feeds `reset/add(bone, pose, normal)/emit`); the coiled tail (`tailenrolled`, raceparts) is still flat.

## Mutant Rage Meter

The `mutant` effect (lottery in `MutantManager`/`MutantEvents`) no longer grants permanent legendary-form access. It drives a rage meter: `Resources.rage` (0-100, NBT `Rage`) and `Status.rageActive` (NBT `RageActive`), both synced by the regular `StatsSyncS2C`. All logic lives in `server/events/players/RageEvents`; tuning is `general-server.json` -> `mutant.rage` (`GeneralServerConfig.RageConfig`).

- Gain: `RageEvents.onFinalDamage` is called at the very end of `CombatEvent.overrideVanillaArmorReduction` (LivingDamageEvent, LOWEST) so it sees post-mitigation damage. Damage taken counts when it is >= `significantDamageTakenRatio` of max health; damage dealt counts only against worthy targets (players, or mobs whose max health is >= `significantTargetHealthRatio` of the attacker's, and never a full-health one-shot). Gain is proportional to the health fraction removed. Hits are classified MELEE / STRIKE (`MainDamageTypes.isStrikeAttackDamage`) / KI (`isKiblastDamage`) / OTHER; changing category within `varietyWindowSeconds` raises a variety step (up to `varietyMaxSteps`, +`varietyBonusPerStep` each), repeating it lowers one. Only significant hits refresh the combat timer (in-memory, per player).
- Access: `TransformationsHelper.hasMutantLegendaryAccess` = mutant + legendary group + (rage full OR rage active) -> one fake `legendaryforms` level in `hasFormSkillAccess` (level 0 passes even without a skill entry). `isRageBorrowedForm` = the form's `unlockOnSkillLevel` is above the real skill level. These run on both sides (radial menu, `SelectFormC2S`).
- Spending: a full meter while in a legendary-group form sets `rageActive`; it drains over `activeDurationSeconds`, and gains are scaled by `activeGainMultiplier` meanwhile. Leaving the legendary group stops it. At 0 a borrowed form is reverted down the previous-form ladder (same pattern as `ExecuteActionC2S.descendForm`) until the player lands on an owned form or base; owned forms are kept. A borrowed form without an active meter (relog, command, config change) is reverted on the next tick.
- Power (`StatsData.applyMutantFormPowerModifier`, legendary group only): borrowed form = bonus x `(1 - powerBonusReductionNoSkill)` (default 0.34 -> 66%); owned form while `rageActive` = bonus x `(1 + powerBonusBoostWithSkill)`; otherwise untouched. `powerBonusReductionNoSkill` kept its key on purpose (removing it makes `JsonLoadReport` warn about an unknown field in every existing config); only its default changed from 0.67, so existing files keep 0.67 until edited or until the next config version bump three-way-merges it.
- Decay: out of combat for `fullIdleSeconds` (full) / `partialIdleSeconds` (not full) the meter drains at 100 per `idleDrainSeconds`. Death resets it.

## Fusions (Metamoru, Pothala, Medi-Bug Beetle) and FusedData

Three fusion types, all executed by `server/util/FusionLogic` (`FusionType` in `DMZEvent.FusionEvent`, string in `Status.fusionType`): METAMORU (dance via the FUSION action mode, same race only, no androids, level-gap check, x1.25-2.0 bonus, duration scales with the average `fusion` skill), POTHALA (matching left/right earrings with the same pair ID within 20 blocks, any races, x1.75-2.5, earrings break when the timer ends) and BEETLE (x1.25-2.0 like Metamoru, any races like Pothala, full `fusionDurationSeconds`). The leader keeps playing; the partner becomes a spectator riding the leader.

- Pair IDs: `PothalaPairItem` issues a random unique ID (`PothalaPairSavedData`) the first time the pair ticks in an inventory and copies it to both halves. `MediBugBeetlePairItem` reuses it and splits into two `medi_bug_beetle` items with the same ID. A paired beetle (`MediBugBeetleItem`) sets a 30 s vanilla item cooldown on the beetle item when eaten (blocks eating the second one) and registers a pending window in `BeetleFusionTracker` (in-memory, server). Two pending players with the same ID within 20 blocks start the Pothala pose (`FusionLogic.startPotaraPose(..., beetle=true)`, `Status.potaraBeetle`, NBT `PotaraBeetle`); the first eater leads. The pose completion in `TickHandler` executes `executeBeetle` or `executePothala` from that flag.
- `FusedData` (`common/stats/FusedData`, NBT `Fused` inside the StatsData tag, only on the leader) is the leader's gameplay view while fused: race/class/stats stay the leader's, skills/techniques/masteries are merged. `StatsData.getSkills()`/`getTechniques()` and `Character.getFormMasteries()`/`getStackFormMasteries()` return the fused copies; `getBaseSkills()`/`getBaseTechniques()`/`getBaseFormMasteries()` are the real saved data (`save()` always writes the base fields). Skills merge by max level (active flag from whoever owns a level); techniques by union (max experience on duplicates; partner revive and form-loadout grants skipped); stack masteries by max.
- Cross-race forms: when races differ, the partner's form groups are exposed with a race qualifier `race@group` (`FusionForms.qualify`). `ConfigManager.getFormGroup` resolves qualified names, so active/selected groups can hold them. Form skills (SkillsConfig + both races' form skills) are NOT merged cross-race: the leader keeps its own levels and the partner's go to `FusedData.partnerFormSkills`, read through `FusionForms.formSkillsFor(data, group)`. Partner masteries are stored under qualified keys. Mutant access is per origin (`FusionForms.hasMutantFor`): a mutant partner only enables the partner race's legendary group; `MutantManager.isMutant` is true if either member is mutant so the rage meter runs. Foreign `androidforms` and false-form groups are never exposed; an android partner only contributes god groups. Enumeration for UI/logic goes through `FusionForms.allFormGroups`.
- Appearance: `mixAppearance` averages body/hair/aura colours (restored from `Status.originalAppearance` at the end). While fused, `Character.getActiveFormData()`/`getActiveStackFormData()` return a presentation copy (`FusionAppearance.present`, cached per character + raw form) whose body/hair/aura overrides are blended 50% with the fused base colours instead of replacing them. Foreign forms keep their custom model, model scaling and extra layer (a Bio-Android leader in the partner's Metal Core becomes the giant cabled Frost Demon), but drop hair type and forced hair and always keep the leader's head bones. When the active model belongs to the partner race's family (`FusedData.usesPartnerModel`), the form only contributes geometry and its own overlays: `SkinGathererProvider.gatherBodyLayers` textures the body with the LEADER race's base skin (`baseLook`: leader race, body type and gender, no form) under the fused/form colours, then adds the form overlays that live in the race resolvers (`emitFrostDemonFormLayers`: Mecha, Metal Core; `emitBioAndroidFormLayers`: Xeno), while the SSJ4 fur keeps coming from `DMZSkinLayer.resolveSsj4Overlay`. `DMZSkinLayer.renderFace` ignores form custom models in that mode, so the face is the leader's race face, and `DMZPlayerModel` treats body type 0 as non-vanilla (no slim arms) when the leader's base skin is not the player skin. A Frost Demon in the Saiyan SSJ4 is therefore the muscular SSJ4 model with Frost Demon skin and face plus the SSJ4 fur. Render code uses `TransformationsHelper.presentNextForm`/`presentNextStackForm` for charge lerps.
- Fused hair (`common/util/FusionHair`, built once on the server in `FusedData.build`, BEFORE `mixAppearance` so the original colours are read): `FusedData.hairSource` is NONE, LEADER (only the leader wears hair: own styles, own original colour), PARTNER (only the partner does: copies of the partner's 5 slot styles and colour) or FUSED (both). "Wears hair" = `HairManager.canUseHair` + not the bald preset + non-empty base style. FUSED fuses every slot pair (`leader.getHairStyle(slot)` x `partner.getHairStyle(slot)`, identical pairs computed once) and runs `HairSanitizer`. Per grid slot: both strands -> blend with a per-slot partner weight 0.15-0.6 (skewed low, so the leader's silhouette dominates); the length only moves 35% of the way when the partner strand is shorter (keeps the leader's spikes); rotation is a quaternion slerp; segment overrides are resampled by arc length (cumulative scales converted to absolute and back, joint rotations/offsets density-corrected). Leader-only strands lean half that weight towards the partner's 8-neighbourhood average. Partner-only strands: FRONT (bangs) are always adopted, blended 65% towards the partner over the leader's neighbourhood; other faces are added only for high-weight slots with leader neighbours, shaped 80% like the leader. Colour is split by zones, not per strand: the grid is cut into mirror-canonical patches (face quadrants: FRONT is one patch, TOP front/back halves, BACK upper/lower, sides upper/lower x front/back), patches are ordered by a hash and taken greedily until ~45% of the fused strands (`PARTNER_COLOR_SHARE`) wear the partner's strand colour or `hairColor`; the rest keep the leader's own strand colours or inherit, so the leader keeps ~55% and the result reads as a two-tone fusion (Gotenks/Vegeks) instead of a few streaks. The shape weight hash and the patch order use the mirror-canonical ids and a seed from both UUIDs, so results are symmetric and stable for a pair. `Character.getHairStyle`, `rendersHair()`, `hasVisibleHair()`, `rendersHairBase()` and `getRgbRenderHairColor()` consult the fused data (the base hair render colour is the dominant source's colour, not the averaged `hairColor`, which is still used for forms and body layers). The Hair compound is cached raw on the client and reused when an identical tag arrives (`FusedData.fromTag(tag, previous)`), so the hair objects (and their occlusion cache) survive the periodic `StatsSyncS2C`.
- Racial traits (`common/util/FusionTraits`): `partsOf(race, activeHeadBone, saiyanTail)` lists a race's parts by category (TAIL, EARS, ANTENNA, HORNS, CREST, WINGS, OTHER): raceparts head bones by prefix (`ears*`, `horns*`/`cuernos*`, `majin*`/`antennas*`), namekian `antennas1`, majin `ears3`, Frost Demon `orejas` + tail, Bio-Android `orejas`, `cabeza2`, `alas` + tail, Saiyan tail (replaces any other tail of that race). `plan(leader, partner, partnerModel, partnerHeadBones)` first chooses one owner per category (the leader wins, OTHER by bone name, and the Saiyan tail always wins the TAIL slot), then compares the choice with the parts the rendered model already contains: the leader's model-integrated parts normally, or the partner's when the leader wears a partner-race form model. Chosen parts the model does not contain are drawn (`borrowed`; the leader's own raceparts bones are never listed because the existing code draws them), and model parts that lost their category are hidden (`hiddenBones`: `tail1`/`cola` for tails, else the bone; `BoneVisibilityHandler` applies them to `tail1`, `cola`, `orejas`, `alas`, `cabeza2`). So a Bio-Android leader in the Frost Demon Metal Core hides the Frost tail and ears and gets its own Bio tail, ears, crest and wings drawn on top. In a partner-race form whose raw data has `keepBaseFormHeadBones` false, the partner's raceparts head bones are skipped (e.g. no horns on a form that has none). Partner head bone, Saiyan-tail flag, body type and gender are stored in `FusedData`; the plan is cached per leader race/head bone/tail. Rendering is in `DMZRacePartsLayer.renderFusionParts` (head/body anchors, skipped for Oozaru and first person): raceparts bones like the leader's own (horns `#1A1A1A`, ears/antennas body colour 1, OTHER hair colour), the Saiyan tail from `human.geo.json` `tail1`, pixel-shaded by `SaiyanTailMeshBuilder` with the per-bone matrices from `DonorBoneRenderer.visit` (or `tailenrolled` when the leader's tail is wrapped), and Frost Demon/Bio-Android parts from their base race models with that race's full texture stack (`SkinGathererProvider.gatherDonorLayers` with the partner's body type and the fused colours from `resolveBodyColors`). `client/render/util/DonorBoneRenderer` draws a donor bone subtree at the anchor pose: it takes the baked model straight from `GeckoLibCache` (no `GeoModel.getBakedModel`, which would switch the animation processor), unhides it, copies rotation/position/scale from same-named player bones or uses the rest snapshot plus the `base.tail` formula for `tailN` bones, and restores values, GeckoLib change markers and hidden flags afterwards (the donor models are shared with real players).
- Writes while fused: skill purchases/upgrades, technique create/import/delete and Gero's android upgrade are refused for both members (`message.dragonminez.fusion.action_blocked`). Grants (quest/wish/world boss/Guru/Old Kai) use `StatsData.grantSkillLevel`/`grantTechnique`, which write the base and raise the fused view. At the end `FusedData.reconcileInto` adds technique XP and mastery gained during the fusion (qualified mastery keys go back to the partner), syncs the world-boss revive slot, and `FusionLogic` reverts any active form/stack form the leader does not own and clears qualified selections.
- `ProgressionSyncS2C` sends base skills/techniques plus `Fused`; `StatsData.load` drops the fused view when a packet carries `Skills` without `Fused`. Fusions end on login/logout/death/gamemode change, so `Fused` never survives a relog.

## False Super Saiyan (Saiyan)
A hidden Saiyan-only form that cannot be bought, selected or kept: it is granted by the same rage meter the Mutant uses (`Resources.rage`) and it ends when that meter empties. Logic lives in `server/events/players/FalseSuperSaiyanEvents`, the shared predicates in `common/util/FalseSuperSaiyanHelper`; tuning is `general-server.json` -> `falseSuperSaiyan` (`GeneralServerConfig.FalseSuperSaiyanConfig`).

- Data: form group `falseform` (`formType` `falseform`, form `falsesupersaiyan`, `unlockOnSkillLevel` 99) built in `DefaultFormsFactory.createSaiyanForms`. `falseform` is not a skill name, so `Skills.isUnlockedAtLevel` can never unlock it; on top of that `TransformationsHelper.getUnlockedForms` and `getOrderedFormsForRace` skip the type outright, which hides it from the skills menu, the character preview, the radial wheel and the Ultimate base-form pick. `getNextFormCandidate` returns null while it is active and `ExecuteActionC2S` ignores descend, so the player can neither climb out of it nor drop it manually; `formStackable` false keeps Kaioken/Ultimate off it.
- Ownership of the meter: Mutant first. `RageEvents.onPlayerTick` returns early (instead of zeroing the meter) when `FalseSuperSaiyanHelper.ownsRageBar`, and every false-form path requires the player NOT to have the `mutant` effect, so exactly one system drives `rage` at a time. `RageMeterHUD` paints the bar red in false-form mode and keeps the Mutant green otherwise.
- Requirements to charge: Saiyan, created and alive, not a Mutant, `superforms` skill level 0, `minLevel` <= level < `maxLevel` (100-200), no active form or stack form, health <= `healthThreshold` (20%), and not `knockedDown`.
- Zenkai interaction: zenkai only fires on a lethal blow, so a Saiyan chipped down to 10% never triggers one — that case must be able to charge, which is why there is no zenkai requirement by default. The optional `requireZenkaiSpent` (default false) narrows charging to the `Zenkai` cooldown running OR `RacialData.zenkaiPermanentUses` having reached `saiyan.permanentMaxBuffs` (`meetsZenkaiGate`, also skipped when racial skills / zenkai are disabled). Independently of that flag, while `Status.knockedDown` is set (the zenkai knockout) the meter neither gains nor drains, so a zenkai never eats the charge.
- Gain/drain: while `canCharge` holds the meter fills on its own at `idleGainPerSecond` (10/s, so ~10 s of standing under 20% health) and never drains — meeting the requirements is enough, hits only speed it up. On top of that `FalseSuperSaiyanEvents.onFinalDamage` (right after `RageEvents.onFinalDamage` in `CombatEvent`) adds damage DEALT to worthy targets (`gainPerDealtHealthFraction`) and damage TAKEN over `significantDamageTakenRatio` of max health (`gainPerReceivedHealthFraction`, the larger of the two), both proportional to the health fraction removed, capped by `maxGainPerHit` and scaled by `activeGainMultiplier` once transformed. The health check runs on the PRE-hit health, so the blow that drops you under 20% is the one hit that does not count. Draining only happens when `canCharge` is false (healed back over the threshold) or once transformed, and then only `combatGraceSeconds` after the last hit either way, at 100 per `drainSeconds` / `activeDrainSeconds`. Set `idleGainPerSecond` to 0 to go back to a purely hit-driven meter.
- Transform/end: a full meter while `canCharge` transforms on the next tick (no ki/stamina cost, `TRANSFORMED` effect, `TRANSFORM_ON` sound). Once transformed ONLY the meter matters — the health threshold is an entry condition, checked in `canCharge`, which the active branch never calls, so healing back up does not drop the form. It ends at 0, on losing the base requirements, or on death. The form also carries zero energy/stamina/health drain so `TickHandler.handleActiveFormDrains` never reverts it, and that method's tailless-Saiyan rule (which reverts ANY active form when the SELECTED group is `oozaru`) is skipped for it — otherwise a tailless Saiyan with Oozaru selected in the wheel would lose the form on the tick it started.
- Power-up state: while the meter is charging the player reads as powering up — `Status.forcedAura` (NBT `ForcedAura`) lights the aura and `Status.forcedCharge` (NBT `ForcedCharge`) raises the hair (`HairStyleResolver` `kiCharging`) and counts as `activeCharging` in `TickHandler`, so ki refills on its own. Both keys are additive and independent of the player's own `kicontrol` aura toggle. `chargingKi` is deliberately NOT reused: the client re-sends its own key state every tick (`ClientStatsEvents`) and `MovementInputUpdateEvent` freezes movement while it is set. On transform `forcedCharge` clears and only `forcedAura` stays; `setChargeState` clears both (plus `rageActive`) for any non-Mutant Saiyan that is neither charging nor transformed, which also unsticks the flags if a form is cleared by a command or another system.

## Stat Curves (VIT health, DEF flat mitigation)

Two stats scale on a curve instead of a straight line: the per-point scaling starts at the class `*_scaling` value and grows quadratically up to `*_scaling_max` (`RaceStatsConfig.StatScaling`, defaults = 4x the minimum via `DEFAULT_VIT_SCALING_MAX_RATIO` / `DEFAULT_DEF_SCALING_MAX_RATIO` in `ConfigManager.setupScalingStats`) at the "knee", then stays at the maximum. The knee is a fraction of the highest reachable stat (`general-server.json` -> `gameplay.vitCurveKneeLevelMode/StatMode` and `defCurveKneeLevelMode/StatMode`, default 0.225 in level mode and 0.45 in stat mode; halved on 2026-09-22 so the ramp is felt early). The shared math is `StatsData.curveScalingAt` (per-point rate) and `curveValue` (its integral, so total value is continuous).

- VIT drives `getHealthBonus` (`getVitalityScalingAt/Max/CurveKnee`).
- DEF drives ONLY the flat mitigation: `getFlatDefense`/`getMaxFlatDefense` feed `rawFlatMitigation`, the adaptive mitigation ratio and the `cancelDamageMitigationThreshold` check in `calculatePostMitigationDamage`, plus `getFlatMitigation`/`getMaxFlatMitigation` for the stats screen. `getDefense`/`getMaxDefense` stay LINEAR on purpose and still feed the percentage reduction (`baseDefense / (k + baseDefense)`, capped), the block formula (`getDefenseLegacyUnits`), the ki disk check and the shadow dummy; giving the curved value to the percentage would hit `baseDamageReductionCap` at about half the resistance it does today.
- A race config without `DEF_scaling_max`/`VIT_scaling_max` (files generated before the key existed) falls back to the minimum scaling, i.e. no curve, until the file is regenerated.

## Enemy AI (`common/init/entities/ai`)

All hostile mobs decide in real time; there are no tier-specific goal sets anymore. Four tiers (`AiTier`, ids 1-4, persisted as the existing `AITier` NBT int and quest/raid/tournament `AITier`/`aiTier` JSON fields): `NOVICE` (natural spawns, story on EASY), `SMART` (story NORMAL, tournament default), `ELITE` (story HARD, Cell Jr, Mini Janemba), `EXPERT` (world bosses; on HARD the final bosses listed in `AiTierResolver.FINAL_BOSSES`). `AiProfile` holds every per-tier knob (reaction delay, decision interval, which abilities are allowed, dodge rules, cast commit chance, lockouts, heat budget, aim lead/error, target retention). Quests resolve the default tier through `AiTierResolver.storyTier(difficulty, entityType)`; `QuestFieldSessions` waves now do the same.

- `DBSagasEntity` owns an `EnemyBrain` (`getCombatBrain()`), ticked from `tick()` after the maneuver tick. The brain reviews the target every 20 ticks (`TargetSelector`: Novice keeps/nearest, Smart attacker-first plus pack focus, Elite/Expert score weakest/exposed party member with retention), scans allies every 10 ticks (`SquadCoordinator`: faction key from quest team / raid id / tournament match / entity family; flank slots, melee crowd, firing-line check, staggered heavy casts), scans hostile ki every 1-4 ticks (`ThreatScanner` → `IncomingThreat` with kind/eta/damage/origin distance/sidestep viability) and reacts after `reactionDelay`. Offense is a utility scorer over MELEE / COMBO / CAST / APPROACH (walk, dash) / FLANK / STRAFE / KITE / TELEPORT / HOLD with per-tier noise; casts must pass `SkillEconomy` (heat per skill tier, shared category lockouts, STRONG lockout, max consecutive casts then a forced melee window, mobility uses per 30 s) and the entity's own cooldowns.
- `CombatMemory` (transient, inherited across transformations) tracks cast/combo outcomes (HIT/MISS via `EnemyAiEvents` on `LivingHurtEvent`), melee whiffs, damage taken, and per-attacker technique history (strongest technique seen and when). Elite/Expert use `expectsStrongerSoon` to decide whether to spend or save the zanzoken on an incoming attack.
- Defensive moves: `performSidestep` (perpendicular hop, all tiers under their rules), `performBackstep` (the old `setEvade` flag, after melee hits), zanzoken, `performDashAway` (explosions), and a reactive `KI_BARRIER` cast (`startSkillReactive`) for Elite/Expert. Giants (`hasGiantBody`: scale > 2 or multipart) never dodge, strafe or kite; tournament fighters never kite.
- Aim: `aimDuringCast` faces a per-cast aim point; Elite/Expert lead the target by its observed velocity, Novice/Smart carry a fixed per-cast angular error.
- Non-saga enemies (Red Ribbon, dinos, DinoFly, sabertooth, Namek warrior) run `EnemyMeleeBrainGoal` (flank slots, unreachable-target give-up, low-HP flee for animals, Novice sidestep rule) and `PartyAwareTargetGoal`; `HurtByTargetGoal.setAlertOthers` gives them pack aggro. Giant fish keeps its lunge goal but uses the party-aware target goal.
- Character-specific mechanics (Saibaman/Chaoz kamikaze, Majin Vegeta, Yakon, Akkuman, Drum/Tao, Murasaki, Nam, Daimaō trap, Janemba abilities) live outside the brain and stay active on every tier; forced casts still go through `startCasting`, so they are charged to the economy.

## World Boss Fights (Janemba, Turles, Metal Cooler Core)

`server/world/worldboss` has six files. `WorldBossManager` owns the lair, arena, spawn and respawn of every boss, the saved data (`WorldBossManager.Data`, file `dragonminez_worldbosses`) and the registry of active fights (keyed by boss key, ticked from `WorldBossManager.tick` every tick of every level, each session only in its own dimension); everything about a single FIGHT lives in `WorldBossSession`. `WorldBossRewards` also keeps the 30-minute results cache behind `/dmzworldboss results`, and `WorldBossContribution`/`WorldBossCombatEvents` are unchanged. Bosses are declared as `WorldBossLair` implementations nested in that interface and listed in `WorldBossManager.LAIRS` (keys are constants on `WorldBossEntity`: `JANEMBA`, `TURLES`, `METAL_COOLER_CORE`): `WorldBossLair.Janemba` (Otherworld, deterministic 1000-block ring from `seed ^ salt`, first non-air block scanning Hell from y 92, builds the Hell arena itself) and `WorldBossLair.Turles` (overworld, waits for `StructurePlanSavedData.isBuilt(TREE_OF_MIGHT_SALT)`, lair = the Tree of Might clearing from `TreeOfMightShapes.planned(...).arenaX/arenaFloor/arenaZ`, no arena build). Client state lives in one file too: `ClientWorldBossState` (lair states per key) with nested `Player` (knockout/revive state) and `Contribution` (HUD scores); its `clear()` wipes all three on disconnect. Everything else is keyed by `WorldBossEntity.getWorldBossKey()`: saved-data entry, missing-boss counter, `isRegistered`/`onBossRemoved`/`onBossTransformed`/`onBossDefeated`, `WorldBossStateS2C` (carries the key; `ClientWorldBossState` is a map; the Hell Ogre dialogue reads `janemba`) and `/dmzworldboss locate|tp|reset|ready [boss]` (`tp|reset|ready` default to `janemba`; `locate` without a boss lists every lair, styled like `/dmzlocate`: clickable green coordinates that suggest `/dmzworldboss tp <key>`, horizontal distance when in the same dimension, then a status line alive / respawn countdown / waiting, with a "lair not built yet" note). A new boss = a lair class, an entry in `LAIRS`, a key, the entity (with `getWorldBossKey`) and optionally a `worldBoss.rewards.<key>` default. A session starts when the boss wakes (`WorldBossEntity.wakeUp`) or when `discoverAwakeBosses` finds an awake boss after a restart, and ends on the kill (`finishVictory`), on a leash reset (`finishDefeat`, from `returnToSleep`) or on a wipe. Tuning is `general-server.json` -> `worldBoss` (`GeneralServerConfig.WorldBossConfig`); the config is synced to clients like the rest of the file, so the HUD reads the linger time and the results screen the category weights from it.

- Participants: every player with a character that is within `contributionRange` (150) of the boss when the audience is refreshed (every `audienceRefreshSeconds`). Joining installs the hidden `worldboss_revive` technique (`ReviveTechniqueData`, `TechClassType` `REVIVE`, `TechniqueType.REVIVE`) into slot `reviveSlot` (1-based, default 4) and remembers what it displaced in `Techniques.reviveDisplacedTechnique` (NBT `ReviveDisplacedTechnique`); `uninstallRevive` puts it back when the fight ends, when the player leaves the dimension or on login without a session. `Techniques.equipTechnique/equipOrSwapTechnique/removeTechnique` refuse to touch the revive or its slot, so the menu, `/dmztech` and `DeleteTechniqueC2S` cannot move or delete it; the skills menu never lists it because its tabs filter by `instanceof Ki/Strike/EvasionAttackData`.
- Contribution (`WorldBossContribution`, one `Score` per player per boss key): damage dealt to the boss or its minions (`WorldBossCombatEvents.onDamageDealt`, split MELEE/STRIKE/KI/OTHER like `RageEvents.categorize`), damage mitigated (`DMZEvent.PlayerDamageMitigatedEvent`, posted at the end of `CombatEvent.overrideVanillaArmorReduction` with the defense/block split, plus `DMZEvent.BarrierAbsorbEvent` for ki barriers and the Android barrier, credited to the barrier's OWNER), damage received (`finalDamage` of the same mitigation event, keyed by the attacker's entity id so minions show separately) and healing (`LivingHealEvent` at LOWEST, credited to `HealContext.getAllyHealer()` when set, otherwise to the target as self-healing; skipped when `HealContext.isSystemHeal()` or `PassiveEventHandler.suppressHealingBonus`, which covers food, senzu and the revive restore; natural regen and the healing liquid never fire the event). Points = the four totals x their config weights; share = points / everyone's points.
- HUD (`client/gui/hud/WorldBossContributionHUD`, extras element `boss_contribution`, up to 8 rows, the local player replaces the last row when ranked lower): fed by `WorldBossContributionS2C` to the audience at most every 2 ticks when a score changed and at least once a second, cached in `ClientWorldBossState.Contribution` (stale after 6 s). Rows alternate between share and compact points every 10 s; bar length is relative to the leader and tinted with the player's BASE aura colour (sent by the server, so untracked players keep their colour). The last packet on a kill carries `finished=true` and the HUD lingers `meterLingerSeconds` (15) for everyone who was in range; a wipe or reset sends `cleared=true`.
- Knockout: a lethal hit on a participant (the lethal branch of `overrideVanillaArmorReduction`, after the racial `onLethalDamage` so a Zenkai still wins, plus a `LivingDeathEvent` fallback for sources that skip the DMZ pipeline) becomes `WorldBossSession.knockOut`: `Status.knockedDown` with `KNOCKDOWN_DURATION`/`KNOCKDOWN_INVULN` = `KNOCKOUT_TICKS` (999999), forms cleared, charges cancelled, Glowing, a 5-second title/subtitle with the revives left, and `WorldBossPlayerStateS2C` so the client draws the desaturated red-bordered screen (`KnockoutScreenRenderer` + `shaders/post/knockout.json`, `loadFailed` guard, flat vignette fallback). Lives are only consumed by a successful revive; a player at 0 lives still gets knocked out instead of dying. Everyone knocked out at once = wipe: the knocked-out players are killed, the boss goes back to sleep. Any other end of the fight without a kill (`finishDefeat`: leash reset, `/dmzworldboss reset`, boss gone for 10 s, boss found asleep) RELEASES the downed players instead: they get up with the revive restore and keep their lives. While a session is active the boss counts as engaged (`WorldBossEntity.hasEngagedPlayer` -> `WorldBossManager.isFightEngaged`) if any participant that is alive, not knocked out, not spectator/creative is within `contributionRange` of the anchor or within the 64-block leash of the boss itself; Yuse's anchor-only leash still applies on top. Without this the Super Janemba (it flies and warps) drifted past 64 blocks from the anchor and the boss reset the moment the last player near the anchor was knocked out. A session is bound to its boss UUID (`resolveBoss`; `onBossTransformed` rebinds it to the next form) so a `reset` that spawns a new boss cannot inherit the old scores. `enforceKnockouts` re-applies the state every second (login clears the flag, the async storage load can overwrite it) and re-installs the revive technique if a stats reload dropped it; relogging while down keeps you down, changing dimension leaves the fight.
- Revive: slot key -> `WorldBossReviveC2S(lockOnTargetId)` -> `WorldBossSession.tryStartRevive` (needs the technique, no `TechniqueCooldown_worldboss_revive`, target = the locked player, else the downed participant under the crosshair, else the closest one within `reviveRange`, and the target must have lives left). The cast runs `reviveCastSeconds` (15) in `tickCasts`; any `LivingHurtEvent` on the caster, moving more than a block or the target getting up cancels it, a cancel by damage/movement puts the technique on `reviveInterruptCooldownSeconds` (15). Revives stack: progress lives per TARGET (`reviveProgress`, +1 per active caster per tick), so two casters get the ally up in half the time, a helper who joins late shortens what is left, and a caster who drops out keeps the progress accumulated so far (it clears when nobody is casting). Completion restores `reviveRestoreRatio` (25%) of max health, ki and stamina (through `HealContext.asSystemHeal` so it is not counted as healing), takes a life and sets the full `reviveCooldownSeconds` (90) on every caster involved. Both sides get `WorldBossPlayerStateS2C` every tick: the caster's bar is `WorldBossReviveOverlay` (same place as the ki charge bar), the target sees the action-bar message; `ClientStatsEvents.onMovementInput` freezes the caster while `ClientWorldBossState.Player.isCasting()`.
- Rewards (`WorldBossRewards`): `worldBoss.rewards.<bossKey>` is a list of `WorldBossRewardEntry` objects with the same fields as a quest reward (`type`, `item`/`count`, `amount`, `skill`/`level`, `command`, `formGroup`/`formName`, `code`) plus `chance`; each entry is turned into a `QuestReward` through `QuestParser.parseReward`, so quest reward types and addon-registered ones work. ## Search Flight (360) And Over-Shoulder Camera

Both are client-only and hang off two hooks: `EntityMouseHandlerMixin` (`Entity#turn` for the local player; it also applies the steerable-beam turn scale, by re-entering `turn` behind a guard when neither system takes the input) and `CameraMixin` (`Camera#setup` HEAD runs `OverShoulderCamera.beforeSetup` then `FlightOrientationHandler.frame`, once per rendered frame, before vanilla reads the player's rotation).

Fast search flight (`client/flight/FlightAttitude`, `FlightOrientationHandler`, movement in `FlySkillEvent.handleFlightMovement`):

- `FlightAttitude` is pure JOML (no Minecraft types, so it compiles standalone for an offline harness). Frame: local +X right, +Y up, -Z forward, so the quaternion is exactly the camera-to-world rotation `Ry(180 - yaw) * Rx(-pitch)`. It holds two orientations: `aim` (what the mouse steers and the camera shows) and `body` (slerps after the aim, `BODY_FOLLOW_RATE`), which is what the model is drawn with and what the velocity follows.
- Mouse input is queued and consumed exponentially (`INPUT_TAU`) and scaled by `general-user` `flightTurnSensitivity` (default 0.75 of the vanilla gain, config menu -> Gameplay). Yaw turns around the world vertical while shallow (with the sign flipped when upside down, so it still reads as screen-right) and blends to the aim's own up axis when steep, so the mouse never reverses past vertical; pitch is always local. That is what makes loops work: there is no pitch clamp and no Euler state.
- Auto-levelling (`level`): roll is pulled back to the horizon at `LEVEL_RATE`, faded out near vertical. It levels to the NEAREST horizon: past 90 degrees of roll error the target is the inverted horizon, so after half a loop the player keeps flying upside down (requested after the first playtest; the earlier automatic half roll was removed) and only pitching back over the vertical returns to upright.
- `decompose` writes the canonical yaw/pitch (pitch always within +-90, so the server's clamp in `absMoveTo` no longer corrupts the look vector while inverted) plus a camera roll. Going over the top flips yaw and roll by 180 together; `FlightOrientationHandler.writeRotation` shifts `yRotO`, the head and the body yaw by the same delta so nothing interpolates across the flip. A rotation written by anything else (lock-on, teleport) is detected by comparing with the last written values and re-synced, keeping the roll.
- Camera roll = attitude roll + `CAMERA_BANK_SHARE` of the cosmetic bank (the bank part only when `cameraMovementDuringFlight` is on); `GameRendererMixin` applies it. The cosmetic bank comes from the smoothed yaw rate plus the strafe keys; double-tapping a strafe key plays a model-only barrel roll. `DMZPlayerRenderer` draws the local player with `getModelRotation()` and cancels GeckoLib's own body yaw with the same `rotLerp` it uses; other players keep the yaw/pitch transform without roll.
- Movement: direction is steered towards the body's forward preserving speed (`TURN_SPEED_FAST`), falling back to the old vector lerp only for reversals (`TURN_REVERSAL_DOT`). Fast flight has hysteresis (enter `FAST_FLYING_THRESHOLD`, leave `FAST_FLYING_EXIT_THRESHOLD`); without it a sharp turn dropped below the threshold and flickered the mode, the animation and the mouse handling.

Over-shoulder (`client/render/camera/OverShoulderCamera`):

- While active in third-person-back (and not fast flying, riding, spectating or in the beam clash cinematic) the camera is decoupled: the mouse drives `cameraYaw/cameraPitch`, the `Camera#move` redirect sets that rotation before applying the shoulder offsets, and every frame the player's real rotation is rewritten to look from the eye at the point under the crosshair. That rotation is what the server, melee hitboxes, ki attacks and the vanilla pick use.
- The crosshair point comes from a ray along the camera's forward starting at the player's depth (blocks `AIM_BLOCK_RANGE`, entities `AIM_ENTITY_RANGE`), recomputed once per client tick and smoothed as inverse depth (fast towards near, slow towards far). With a lock-on target the point is the target's centre and `LockOnEvent` steers the camera angles (`steerToward`) instead of the player. The deviation from the camera is clamped (`AIM_MAX_*_OFFSET`) except when locked on.
- Rotation changes made by anything else are absorbed into the camera angles as deltas; leaving the mode writes the camera angles back to the player so the view does not jump.
- `InGameHudMixin` redirects the first-person check in `Gui#renderCrosshair` so the crosshair (and the block shield) draw while decoupled.
- In fast flight the shoulder offsets are rotated by the camera roll (`computeMove(..., roll)`), otherwise the character would swap sides when the view goes inverted.

## Beam Clash

Server-authoritative tug-of-war between two head-on MAJOR ki beams (`common/combat/clash`): `BeamClashManager` detects collisions every level tick, `BeamClash` runs the struggle and `ClashParticipant` scores each side's presses. Clashing fighters are invulnerable and NPC owners are frozen (`setNoAi`) for the duration.

- Push: `biasT` (0..1, A wins at `WIN_THRESHOLD` 0.8) drifts by `DRIFT_PER_TICK × (pushA − pushB)` where push = momentum × stat weight × traction. Momentum bursts on hits (`BURST_PER_PERFECT_PRESS`) and decays (`MOMENTUM_DECAY`). Everything shown — the beams' locked lengths and the HUD bar — is `BeamClash.visualBias`, which remaps the [0.2, 0.8] band onto the whole gap, so the winning beam visibly pushes the other back to its owner's hands and the breakthrough surge starts at the loser. `clashPoint` (midpoint of the two locked tips) is synced every tick.
- Timing meter (`ClashMeter`): deterministic and input-independent, a pure function of `(seed, ticks since clash start)`. Cycles of 44–64 ticks alternate sweep direction; each cycle rolls its own target window (centre at 42–86 % of the sweep, half width 0.065–0.09). Only the first press of a cycle counts (a miss burns it); PERFECT (≤ 35 % of the half width) is efficiency 1.0, GOOD tapers to 0.5. NPCs press at the tick the marker is closest to the centre, scaled by `npcAccuracy`. The class must behave identically on both sides: the client renders it at frame rate from `ClientLevel.getGameTime()` and the server re-simulates presses with it.
- Networking: `BeamClashStateS2C` every tick (start game time, meter seed, visual advantage, both beam colours, opponent id, clash point). `BeamClashInputC2S` carries the meter time the player saw and the marker position it saw. `ClashParticipant.registerPlayerPress` accepts claims in `[serverTime − (latency + 2 ticks, capped at 12), max(serverTime, real elapsed) + 3]` (the upper bound uses real time because a client's clock runs ahead of a lagging server), verifies the claimed marker against the re-simulated one, keeps claims monotonic, and after `STRIKE_LIMIT` (4) implausible claims dampens every burst of that participant to 0.4 for the rest of the clash (logged as a warning). Robotic timing (six consecutive hits within 0.12 half-widths of each other) is dampened the same way. `PacketRateLimiter` allows one press packet per tick.
- Client (`client/clash`, `gui/hud/BeamClashOverlay`, `render/effects/BeamClashScreenRenderer`): `ClientBeamClashState` grades presses locally with the same meter for instant PERFECT/GOOD/MISS feedback and stamps them with the meter time the HUD last rendered (fallback: game time − 0.5). `BeamClashCinematicCamera` forces third person, orbits the clash point at 14°/s starting from a side profile (distance 7.5 + 0.825 × fighter separation, max 24, wall-clamped, height 1.2 + 0.12 × distance) with a struggle shake and a 0.84 FOV push-in. `BeamClashScreenRenderer` runs `shaders/post/beam_clash.json` at `AFTER_LEVEL` (manga speed lines confined to the outer ~15 % of the screen, re-rolled 9×/s, near-black at 60 % opacity; a flat dark border is the fallback when the shader fails to load). `FullscreenPostEffect` is the shared lazy PostChain wrapper with the depth-copy trick, also used by the knockout screen.
- Ticking: `BeamClashManager` runs on `LevelTickEvent`, which fires once per loaded dimension. Detection is per level, but a clash is only advanced and synced on the tick of its own level (`BeamClash.level()`); before 2026-09-23 every clash advanced once per dimension, so with 6+ dimensions the meter ran 6× too fast and inputs were graded against a server that was far ahead of the client (the "menu goes too fast / wrong inputs" complaint).
- Losing: `BeamClash.resolve` stuns the loser (`MainEffects.STUN`, `LOSER_EXHAUST_TICKS` = 70) so it cannot move, dash, dodge, parry, block or fire while the winner's breakthrough connects. The final `BeamClashStateS2C` carries `exhaustTicks` for the loser; `ClientBeamClashState.isExhausted()` makes `FlySkillEvent` freeze a flying loser in place instead of the usual stun drop, and the HUD shows a pulsing EXHAUSTED label.
- Lab: `client/lab/BeamClashLab` (inert unless `-Ddmz.lab=beamclash`; `dmz.lab.exit`, `dmz.lab.only=a,b`) builds a flat world, summons `saga_vegeta` firing a Galick Gun, fires a Kamehameha back through the real `setupKiHamePlayer` + `addFreshEntity` + `fireHability` path, drives the QTE with scripted policies (perfect, good edge, miss early, spam, AFK, stale/marker cheats, overpowered NPC, flying loser), writes `run/screenshots/beamclash_lab/results.txt` and frame captures. Traps: player-style `setup*Player` methods do not add the entity to the level; the integrated server pauses when the window loses focus, so the lab disables `pauseOnLostFocus` and closes pause screens.

## Tournaments

Server logic lives in `server/world/tournament/Tournament` (nested `Bracket`, `Run`, `Progress` SavedData `dragonminez_tournaments`, `RingAnchor`, `Manager`, `Service`); definitions are `config/dragonminez/tournaments/<id>.json` (`TournamentDefinition`, shipped `baba` = GAUNTLET and `cell` = BRACKET, hosts mapped in `TournamentDefinition.HOST_NPCS`); the client is `client/gui/tournament/TournamentBracketScreen` (a `ScaledScreen`) plus `TournamentOverlay` (titles/notices). Packets: `TournamentPackets.OpenBracketS2C` (whole screen state, `push=true` only refreshes an open screen, `push=false` opens it), `PhaseS2C` (countdown phases, replaced the old `CountdownS2C` in the same registration slot), `RivalS2C`, `ActionC2S` (`OPEN_BRACKET`/`SIGN_UP` need the host NPC within 12 blocks; `ACCEPT_RULES`/`DECLINE_RULES` resolve the run by player).

- Run phases (`Run.Phase`, persisted with `phaseDeadline` in game time): `RULES` -> `INTERMISSION` -> `PREVIEW` -> `BOUT` -> back to `INTERMISSION` until the run ends. Nothing starts by itself: every bout must be accepted with the Ready button.
- Sign-up (`Manager.signUp`): the draw is made immediately (`Bracket.draw`) but stays hidden (`Run.revealed=false`; the client receives `Bracket.HIDDEN_SLOT` = `"?"` seeds via `Bracket.hiddenSeeds()`); only the semifinalist and champion are shown beforehand. Every member gets the screen forced open (`Service.openForAll`) in the rules view and must answer within `rulesAcceptSeconds` (default 60). Decline (or no answer, or logging out during `RULES`) = `dropOut`: no re-entry cooldown, the player's seat is replaced by a random unused contender (`Bracket.replaceSeed`; gauntlet seats are shared so nothing to replace). Nobody accepts -> `cancelRun`. Everybody answered -> `settleRules` reveals the draw and starts the first intermission.
- Intermission = the accept window, `nextRoundSeconds` (default 30, min 5). `startIntermission` clears `Run.ready`, forces the screen open for everybody and sends `your_turn`/`turn_of` chat lines; the fighter(s) of the bout see a Ready button (`ActionC2S.READY` -> `Manager.ready`), the status line and the quest-notice card count down, and hovering the opponent shows the same intel as the quest enemy preview (ki skills and combos behind `bulma_scouter_threat_db`, read from the client-side dummy entity; no Battle Power). When every fighter of the bout is ready (both in PvP) -> `PREVIEW` (`Manager.PREVIEW_SECONDS` = 5): the screen is forced open for everybody with the countdown bottom-right and closes itself when it ends or when the `BOUT` push arrives. Deadline without Ready -> `next_round_expired` + `eliminate` for each late fighter (the other side advances by walkover). Then `beginMatch` -> `startBout`: teleport to the ring, `ActiveMatch.fightAt` = now + `COUNTDOWN_SECONDS` (3), NPC `setNoAi` + `setCombatFrozen`.
- Freeze: `Status.matchFrozen` (NBT `MatchFrozen`, transient in practice: `TickHandler` recomputes it every tick from `Manager.isInGrace` and sends a `ResourceSyncS2C` on change; login/respawn/dimension change clear it). It is part of `Status.isStunned()`, so every existing client key gate, `MovementInputUpdateEvent` block and server C2S stun check applies; `ExecuteActionC2S`/`SelectFormC2S` check it explicitly, and `ArenaProtectionHandler` cancels `PlayerInteractEvent`/`LivingEntityUseItemEvent.Start` during the grace window. Screens stay usable.
- Exclusion zone: `Manager.clearBystanders` runs every match tick per fighter (`EXCLUSION_RADIUS` = 15): any `LivingEntity` inside that is not the fighter, their opponent, another active fighter, a tournament NPC or a spectator is teleported to the radius edge (horizontal direction, same Y) and pushed outwards; players get a `keep_away` action-bar message once per second.
- Phase feedback: `PhaseS2C` goes to every participant once per second with `fighter=true` for the two people in the next bout. During `NEXT_ROUND` (the accept window) everybody gets the live card in the quest-notice HUD slot (`QuestNoticeHUD.setLive`, a supplier-backed sticky notice drawn in slot 0 ahead of the queue; the fighter's card is the red FAILURE tone and says to press Ready). During `PREVIEW`/`COUNTDOWN` fighters get overlay titles instead (`TournamentOverlay.render`: "The duel begins in N", the big 3-2-1 and FIGHT!). `CLEAR` on run end.
- Screen (`TournamentBracketScreen`): panel = 9-slice of `menubig.png` covering 80% of the UI canvas; header (title + stars centred, format/lethal chips top-right, status line centred), party chips centred with no label (★ leader, ✓ accepted/ready, … pending, ✗ out, ⚔ fighting, tooltip), content area, footer (hint left, preview countdown right, DMZ buttons centred). Views: `SIGNUP` (Enter for the leader), `LOCKED`, `RULES` (only real rules, numbered, built from `OpenBracketS2C.Rules`: accept window, elimination + cooldown, leaving the arena, bout time limit, interference, countdown freeze, lethal/knockout, party acceptance; Accept, Decline needs a second click within 3 s), `BRACKET` (Ready button while `awaitingMyReady()`). BRACKET format is drawn as a vertical tree (seeds at the bottom, winners climb, trunk at the centre with the semifinalist/champion hanging on the right, ★ champion seat on top); GAUNTLET stays horizontal. Content is scaled down only until ONE axis fits (`renderLadder`), the other axis scrolls (wheel + draggable thumb + click on the track); rules always scroll vertically.

## Training Minigames

Server-verified since the 2.2 rework. Pure-Java, deterministic game logic lives in `common/training` (`MinigameLogic` base + `RhythmLogic`, `MemoryLogic` = Shadow Boxing, `PrecisionLogic`, `KiControlLogic` = id `control`, `GravityLogic` = id `gravity`; `MinigameLogics` is the factory and holds `CHALLENGE_STAGES`). The logic has NO Minecraft imports on purpose so it runs identically on client and server (and in offline harnesses); it uses `java.util.Random(seed)`, no trig, and events carry quantized sub-tick fractions (`MinigameEvent.FRAC_STEPS` = 256) and quarter-unit click coordinates, so the client must apply the quantized event it sends, never the raw input.

- Flow: `MinigameStartC2S(id, origin, stage)` -> `MinigameSessionManager.start` validates (MENU needs the game known; MASTER needs the game's master NPC within `NPCActionC2S.isNpcInRange` and no disposition blocker; CHALLENGE needs Old Kai + his requirements for stage 0 and the server-side `ChallengeProgress` for later stages), creates the logic with a server seed and answers `MinigameStartS2C`. The client (`BaseMinigameScreen`) plays the same logic locally and every 20 ticks sends `MinigameInputC2S` (events of ticks `[fromTick, toTick)`, varint tick deltas). The server replays the chunk; it invalidates the session (no reward) on a tick gap, more than 200 ticks per chunk, more than 12 events per tick, a malformed event, or pacing ahead of wall-clock time (`toTick * 50ms <= elapsed + 3 s`). Progress (`MinigameResultS2C` non-final) goes back after each chunk; the final result is sent on finish (client finished/ESC/closed screen, 15 s without input, 4 h cap, logout pays silently). Old `TrainingRewardC2S`/`TrainingAnimationC2S` stay registered only to keep packet ids; the reward packet is a no-op and the server now drives the training animation.
- Reward = `rewardUnits` (accumulated per tick by the logic: `levelMult x perfMult / 1200`, level multiplier from `minLevelRewardMultiplier` at level 1 to 1.0 at the game's `difficultyCapLevel`, performance multiplier lerped between `min/maxPerformanceRewardMultiplier` from the EMA `performance`) x `tpPerMinuteCoefficient x TPC^rewardCostExponent` x game `rewardMultiplier` x `getTpSourceMultiplier(TpSource.TRAINING)` x (1 + `mentorBonus` when the session started from the master's menu AND the game was already known). `tpsLimitPerGame` <= 0 means unlimited. When manual TP purchases are disabled (TPC = `Integer.MAX_VALUE`) the reward uses `minTPCost` instead. `tpGainBoosts` falls back to the default boost list for a `TpSource` missing from an older `general-server.json`. Every `addTrainingPoints` grant gets the STORY multiplier in `TPGainEvents.onTPGain`, including grants that already applied their own source multiplier (`applyTpBoosts`: passive, travel, mined, crafted, kill, hit, minigame reward). That stacking is intentional design, not a double-count bug; do not remove it. Training points are a `double` saved as `TrainingPointsD` plus a float `TrainingPointsF` copy so older versions still load them; load prefers `D`, then `F`, then the legacy int `TrainingPoints`. Internal code reads/writes them with `Resources.getTrainingPointsExact`/`setTrainingPointsExact`; the float `getTrainingPoints`/`setTrainingPoints` are kept only for addon binary compatibility (same for the float overloads of `StatsData.calculateStatIncrease` and `NumberFormattingUtil`, and the `Player` overloads of `GravityLogic.getJumpFactor/getFlyFactor/isFlightHardStopped/getFallExtra`).
- Learning: a game is learned only through its master: `learnRequiredRuns` (3) master-origin runs that reach `learnRequiredLevel` (5). Progress is `Character` NBT `MinigameLearnRuns` (compound id -> count; additive, missing = 0), synced with `StatsSyncS2C`. Known games are never removed.
- Ultimate Challenge (Old Kai): `UltimateChallenge` (client) chains `CHALLENGE_STAGES`; each stage is a CHALLENGE session whose logic stops at `TrainingConfig.getChallengeTargetLevels(id)` cleared: the root `challengeTargetLevels` (10) unless the minigame's own `challengeTargetLevels` is > 0 (Rhythm = 6, because a song run is capped at level 10 and levels come slower there). Only the server's `ChallengeProgress` advances stages and grants `NPCActionC2S.grantOldKaiChallengeReward`; the old `NPCActionC2S("oldkai", 1)` path no longer grants anything.
- Games: Rhythm = 4-lane Guitar-Hero-style highway (lanes A S K L / arrows / `RHYTHM_*` keybinds; `LEAD_IN_TICKS` countdown; notes judged in song milliseconds `(tick - 60 + frac) * 50`; health meter instead of a miss window; in Free Training the level raises scroll speed and the allowed note tier, in song mode difficulty follows the song). It plays either Free Training (seeded generator) or a music disc chart: `RhythmChart` JSON in datapack folder `rhythm_charts` (`RhythmChartRegistry`, looked up by `item` then `sound`; format `{item, sound, bpm, durationMs, notes: [[timeMs, lane, lengthMs, tier, sub]]}`, tier 0-3 = density layer, `sub` 0-255 = salience rank inside that layer within a +-4 s window, so `Note.level() = (tier + sub/256) / 4` is a continuous 0..1 intensity; charts without `sub` still load), and the server sends the encoded chart inside `MinigameStartS2C` so datapack charts never desync. Song difficulty: the client analyses a disc as soon as it is selected in the dropdown (Play stays locked with a phase status bar: `RhythmAutoCharter.PHASE_ANALYZING/MAPPING/BUILDING`), then shows the recommended difficulty and a 4-button picker (Easy/Normal/Hard/Expert, `RhythmLogic.DIFFICULTY_*`); the choice travels in the start option as `<item>|<difficulty>` (`RhythmLogic.buildOption/optionTrack/optionDifficulty`, echoed back in `MinigameStartS2C`), and each difficulty is a `TrainingConfig.SongDifficulty` (`rhythm.easy/normal/hard/expert`: `startIntensity`->`endIntensity` and `startTravelMs`->`endTravelMs` interpolated linearly over song progress, plus `rewardMultiplier` shown in the UI and applied server-side in `RhythmLogic.rewardRate` together with `songRewardMultiplier`). A note spawns only while `level() <= intensity()`, so the ramp inside a song is gradual (Easy 0.20->0.42, Normal 0.35->0.65, Hard 0.55->0.88, Expert 0.75->1.0 with travel 1150->780 ms, i.e. Expert peaks above the old fixed ramp but starts softer). `RhythmLogic.recommendedDifficulty` picks the highest difficulty whose end density (`RhythmChart.densityAt`) stays under `rhythm.recommendedMaxNotesPerSecond` (3.0). Harness (skilled bots, vanilla discs): Easy ~0.8, Normal ~1.12, Hard ~1.29, Expert ~1.48 units/min.
- Analyser pipeline (`RhythmAutoCharter.generate(id, item, sound, left, right, phase)`, phases `PHASE_ANALYZING/TEMPO/SEPARATING/MAPPING/BUILDING` reported through an `IntConsumer` so the menu can show them): STFT of both channels (mono when `right == null`) -> local tempo + beat grid from the mix onset function (`localPeriods`: autocorrelation tempogram over 6 s windows every 1.5 s, 60-180 BPM in 0.5 BPM steps with the 110 BPM log-prior, Viterbi across windows with `TEMPO_CHANGE_COST` per octave of change, linear interpolation to a per-frame period that `trackBeats` uses for its search range and penalty; `chart.bpm` is the median) -> silence gate (-32 dB vs the 95th percentile of smoothed energy; onsets in gated frames are dropped, which is what leaves real gaps in songs with a full stop) -> vocal separation -> two note lists. Vocal separation is DSP only (no ML): stereo centre extraction (`min(|L|,|R|) * phase coherence * balance`, 100-5000 Hz; mono songs use the whole mix), HPSS soft mask (median filters +-7 frames / +-7 bins) to keep only the harmonic part, harmonic-summation salience on a half-semitone f0 grid (MIDI 43-84, 6 harmonics) with a Viterbi pitch track, and a per-frame activity score = smoothed vocal/mix energy ratio x peakiness gate. The song counts as vocal only if >= 18% of the non-silent frames are active AND >= 30% of the active frames glide (pitch moves 0.04-0.5 semitone per frame, which separates a voice from a piano), so vanilla discs get no vocal variant. The instrumental list runs the v4 onset pipeline on `mix - vocal`; the vocal list segments the pitch track into notes (new note on a strong vocal onset or when the pitch leaves the running mean by > 1 semitone for 5 frames), keeps notes >= 70 ms whose mean f0 peakiness is >= 2.5 (drops breaths and instrument bleed), snaps to the grid within 45 ms, gives holds (capped at 2.5 s) to tier <= 1 notes >= 450 ms, and contains ONLY the sung notes: instrumental stretches stay empty on purpose so the rest/break countdown covers them (the user dropped the earlier instrumental fill for that reason). A vocal onset only splits a note when the vocal energy rises >= 1.3x across it, otherwise vibrato chops sustained notes into 200 ms pieces. Both lists go through the same salience tiers/sub ranks, so the four difficulties apply to either.
- Chords: a tonal onset with a second spectral peak >= 3 semitones away gets a partner note; when the main note is tier 0 and the partner is >= 92% as strong (`CHORD_STRONG_RATIO`) the partner is tier 1 / sub 255 (appears at the end of Normal and through Hard), otherwise it stays tier 3 as before. A first try with 85% and `main + 1` doubled the Normal density and pushed every recommendation to Easy, so keep chords rare. Percussive onsets never spawn partners.
- Latency wizard (`RhythmCalibrationScreen`, opened from the "Latency N ms - calibrate" link above the song list): plays a hi-hat tick every 500 ms with `SimpleSoundInstance.forUI`, ignores the first 4 ticks, takes 12 key/mouse taps measured against the actual play() time of the nearest tick (negative when early), and offers the median as `rhythmAudioOffsetMs` (Apply saves `general-user` through `ConfigManager.saveGeneralUserConfig`). The first time the Rhythm menu opens (tutorial id `TutorialManager.RHYTHM_CALIBRATION`, stored in `tutorialsSeen` like the other tutorials but NOT gated by `tutorialsEnabled`) the screen opens in mandatory mode: no Back button, ESC ignored, only Apply (which marks it seen) or Retry; the Ultimate Challenge path skips it. It is audio-only on purpose: the taps must follow the sound, so the measured value includes output latency, input latency and the player's own bias, which is exactly what the in-game judgement needs to cancel.
- Timing: the STFT hop is 128 samples (5.8 ms); every frame-count constant is written as `frames(n)` = n frames at the old hop 256 so the tuned v4 behaviour is preserved (`FRAME_SCALE`). Onset times are refined to the frame with the steepest spectral rise around the flux peak (`refineOnset`) and shifted by `ONSET_LAG_MS` = +33 ms, calibrated with the harness `OffsetTest` (synthetic clicks/tones at known times; without it the analyser placed notes 33 ms early with a +-4 ms spread). Re-run `OffsetTest` and re-calibrate that constant after any change to the FFT size, hop, flux lag or peak picker. `rhythmAudioOffsetMs` (general-user, 60 ms) remains the per-player playback latency knob.
- Chart variants: `RhythmChart.vocalNotes` (JSON key `vocal`, binary encode appends a second note block; old charts decode with an empty list), `hasVocals()`, `notesFor(variant)`, `densityAt(intensity, variant)`. The start option is `<item>|<difficulty>|<variant>` (`RhythmLogic.optionVariant`, `RhythmChart.VARIANT_INSTRUMENTAL/VOCAL`); the server drops a vocal list that fails `validateNotes` and echoes the effective variant. The menu offers the Instrumental/Vocals toggle only when the chart has vocals; the recommendation is recomputed per variant.
- Bundled songs (`common/training/BuiltinSongs`, keys `song:ill_forget_about_you_in_time` and `song:oh_yeah`): the two owners' picks ship as streamed sound events `dragonminez:minigame.<stem>` (`assets/dragonminez/sounds/minigame/*.ogg`, registered in `MainSounds`), are always listed first with a star, need no disc, and never count as learnable.
- Pre-made charts (all 39 DMZ discs, the 2 songs and the 3 vanilla discs that carry voice-like content: 5, 11, Pigstep; the other vanilla discs are left to the live analyser on purpose so the automatic mapping can be shown off) are built offline with Demucs stems (`Desktop/Alejo/Demucs`, see its README; dev-only, nothing of it ships) and stored twice: `data/dragonminez/rhythm_charts/<key-stem>.json` for the server (`RhythmChartRegistry` matches `item`) and `assets/dragonminez/rhythm_charts/<key-stem>.json` for the client menu (`RhythmClientCharts.readBundled`, key stem = item id with `:` -> `_`, lower case, e.g. `dragonminez_music_disc_menu_music_12.json`, `song_oh_yeah.json`). Every chart carries `audioHash` = SHA-1 of the analysed OGG and `audioPrint` = content fingerprint (`RhythmAudioPrint`: base64 of the mono loudness per 500 ms block, 0.5 dB steps). Do NOT rely on the SHA-1 alone: the release jar runs PackSquash (`optimizeResources`, which defaults to ON in `build.gradle.kts` despite its comment) and it re-encodes every OGG to 40050 Hz, so the jar's bytes never match the source files (it shifts timing by a constant ~3 ms, harmless for the charts). Client flow (`RhythmClientCharts.analyze`): exact SHA-1 match -> use the bundled chart; otherwise decode, fingerprint and `RhythmAudioPrint.compare` (duration within 600 ms, mean level difference <= 1.5 dB after removing the overall gain, correlation >= 0.95) -> use the bundled chart, else log "Bundled rhythm chart ... ignored" and analyse live. Validated: all 41 shipped songs vs their PackSquash copies match (worst 0.25 dB / 0.994) and 1640 different-song pairs never match (closest 2.6 dB / 0.90). Server side: the start option carries the hash of the chart the client actually uses as a 4th field (`item|difficulty|variant|hash`, `RhythmLogic.optionHash`); when the client accepted the bundled chart that is the bundled hash, so `MinigameSessionManager` keeps the datapack copy; a different hash makes it drop the datapack chart (`RhythmChart.matchesAudio`) and take the client's live chart. Charts without a hash (old datapacks) are always accepted.
- Stems mode (`RhythmAutoCharter.generate(..., instrLeft, instrRight, vocalMono, phase)`, harness `ChartTest` when `<name>.vocal.f32` + `<name>.instr.st.f32` exist): the vocal stem replaces the centre extraction as the voice signal, the instrumental stem feeds the note onsets, and vocal activity is simply vocal/mix energy ratio > 0.12 above a -30 dB floor (song gets a Vocals variant when >= 15% of the live frames are active, `STEMS_ACTIVE_MIN_FRACTION`; 8% let in tracks with a few seconds of choir). This is what decides Instrumental/Vocals for the shipped charts, so it is exact for them: Cha-La Variations and the other Kikuchi cues come out instrumental, Kuririn Arrives by Boat / Goku's Dinner Bird / Sad Brothers keep their choir parts as Vocals.
- Live voice detection (unknown discs): the old heuristics (energy ratio, glide, stereo balance, syllable dips) proved useless on orchestral anime OSTs, so the decision comes from `RhythmVoiceModel`, a 123 -> 16 -> 1 tanh MLP generated by `Demucs/train_vad.py` from Demucs-labelled frames of 80+ songs (DMZ discs, the two songs, vanilla discs and vanilla background music). Inputs (`voiceFeatures`): 24 log bands (100-5000 Hz) of the mix and of the centre signal, per-song median-subtracted, plus their +-8-frame means, the centre bands' local std, the HPSS vocal/mix ratio, f0 peakiness and stereo balance. A song is vocal only if the mean smoothed probability over live frames >= `MODEL_MEAN_PROBABILITY` (0.40) and >= 8% of frames are active. Honest status: on the training songs instrumentals stay <= 0.24 and real vocal songs reach 0.45-0.71, but a hold-out test with the vocal songs removed showed the model does NOT generalise to unseen singers (it memorises); so for unknown discs expect it to say "instrumental" most of the time, which is the intended conservative failure (the full-mix chart still follows the vocal onsets). Vanilla background music was added as negatives only. A real fix needs a proper singing-voice CNN, which is out of scope for a Forge mod without native ML deps. The model file is generated: never hand-edit it, re-run steps 3-4 of the Demucs README after changing the features. The debug hooks `RhythmAutoCharter.DEBUG` / `FEATURES` are null in game.
- Learned songs: finishing a disc song (song completed, health > 0, not a builtin, not CHALLENGE) with accuracy >= `rhythm.learnSongAccuracy` (0.75) adds the item id to `Character.learnedSongs` (NBT `LearnedSongs`, string list, copied in `copyFrom`, synced through `StatsSyncS2C`); `MinigameResultS2C.songLearned` shows the line on the results screen. A learned song is listed and accepted by the server without the disc even when `requireDiscInInventory` is on.
- Rest/break: `RhythmLogic.updateRest` marks `resting` when every live note is done, the last spawned note ended >= 300 ms ago and the next note at the current intensity is >= `REST_MIN_MS` (3 s) after it; `restRemainingMs` counts down to the moment that note starts scrolling (`timeMs - travelMs`). While resting `onKeyDown` ignores lane keys (no ghost penalty), the keycaps render grey and the screen shows a countdown disc (`drawRestCountdown`). The flag is part of the checksum.
- Song menu (`RythmGameScreen.renderReadyCustom`, replaces the shared rules panel through `BaseMinigameScreen.renderReadyCustom`): a two-column NPC panel, left the scrollable song list (Free Training, then the two bundled songs, then discs sorted by `sortKey` = title heuristics that strip bracketed parts, take the last ` - ` segment, drop ` by ...` and franchise prefixes such as "dragon ball z"; each row shows a star/note prefix, the title and the duration, learned discs in green), right the details (title, credit line parsed from the disc's display name by `parseDiscInfo` = `"[Music Disc - ]Source - Title[ by Artist]"` -> shown as `Artist - Source`, vanilla discs map `C418 - cat` to artist C418 / source Minecraft, plain names fall back to "Music disc"; the DMZ discs' lang entries follow that pattern, duration + BPM + a green Learned tag, the analysis status with animated dots and a progress bar, or the recommended difficulty + the 4 difficulty buttons + the variant toggle + the TP multiplier) and the Play button, whose label shows the short phase name with animated dots while analysing and which stays locked until the chart exists. Up/Down browse, Left/Right change difficulty, Tab toggles the variant, Enter/Space play. `rhythm.requireDiscInInventory` gates disc charts; the client starts the disc sound when song time reaches `-rhythmAudioOffsetMs` (general-user). The mod ships NO charts: datapack charts are optional (server owners/addons); otherwise the client generates one and stores it locally in `<gameDir>/dragonminez/rhythm_charts/<item>.json` (stamped with `generator` version and the SHA-1 of the disc audio, so a resource-pack song or a newer generator regenerates it). `Personal DMZ AI Docs/MinigameHarness/rhythm_charts.py` is the offline Python twin used for tuning. Every minigame has ONE 256x256 sprite sheet in `textures/gui/minigame/<game>.png` (generated by `Personal DMZ AI Docs/MinigameHarness/minigame_sheets.py`); rows v=240+ are a shared UI strip (menu-style 3-slice bar frames H/V, 5 fill colours, full/empty hearts) drawn by `BaseMinigameScreen.drawBarH/drawBarV/drawHearts`. Progress bars animate through `SmoothValue` (Gravity's bar also anticipates the approach to the next pillar); the HUD level/grade/TP values pop or count up. Gravity = Flappy-style pod (downscaled `item/saiyan_ship.png`) through rock pillars on a 560x180 field over a bordered dark-blue translucent panel; every hitbox constant lives in `GravityLogic` next to the sprite sizes. Shadow Boxing (id `memory`) is a key-sequence game: random A-Z/0-9 keycaps (`MinigameEvent.CHAR_BASE` + 0..35, so input keys go up to 41 and the held mask is a long; the input packet sends type and key as separate bytes), a per-key timer and a total timer, wrong or slow keys trigger a fast drain, running out of total time costs one of the run's lives and deals a new combo; combos grow to 8 keys. Rhythm progress per hit is normalised so a level takes `targetSecondsPerLevel` at the current note density (`RhythmChart.densityAt(intensity)` over the playable span, or the free generator's analytic density). Discs without a datapack chart: the server rejects with `reject.no_chart`, the client decodes the disc OGG with LWJGL `STBVorbis`, runs `RhythmAutoCharter` (pure-Java analyser, 6-12 s per song at hop 128, cached in memory and on disk by `RhythmClientCharts`, `GENERATOR_VERSION` 6; bump it whenever the chart output changes so stored charts regenerate) and resends `MinigameStartC2S` with the chart bytes; the server accepts it only if `RhythmAutoCharter.validate` passes against the disc length.

Precision's approach ring is a pixel-art sprite picked from 13 pre-drawn radii (`RING_FRAMES`, must match `minigame_sheets.py`) and each target shows its click order (1..n, by ring radius).
- HUD extras (TP so far, mentor bonus, learning, challenge) are one centred DMZ-font line at `INFO_LINE_Y`; screens keep `HUD_RESERVE` free at the top. Every bar has a small legend (`drawLegend`, keys `gui.dragonminez.minigame.legend.*`). The rules panel wraps to the screen width and scales down to fit the height (`readyToUiX/Y` convert clicks). Rhythm lanes read the `rhythm_left/down/up/right` keybinds (defaults A S K L, `KeyConflictContext.GUI` so they don't clash with WASD; ids unchanged, so old options keep their old keys) and the lane caps show the bound key; the song picker is a dropdown ("Select Song", Free Training + carried discs). Precision also clicks with SPACE at the mouse position. The auto charter (`RhythmAutoCharter`, generator v4; `rhythm_charts2.py` is the v3 Python twin, v4 adds: tiers from GLOBAL salience rank (top 30/55/78%) then demoted by the local density budgets, percussive onsets get lanes by spectral centroid instead of pitch rank, and a `fastStart` nerf scales the budgets over the first 25% when the intro is already dense) detects onsets with a semitone SuperFlux plus a high-frequency percussive term, snaps to the beat grid only where a 4 s window is rhythmically confident (above chance), otherwise keeps the real onset time (piano/rubato), maps lanes by the note's pitch rank among notes within 3 s (melody contour), and assigns tiers by salience under per-tier density budgets (1.0/1.8/2.7/3.6 notes/s, min gaps 260/180/130/100 ms), so low levels play only the most salient notes. Precision ramps `startingMaxCircles` -> `maxCircles` over `maxCirclesFullLevel` levels. Bumping `GENERATOR_VERSION` in `RhythmClientCharts` regenerates every stored chart.
- Start/pause flow: the rules panel has a Play button (Enter/Space also start). ESC while playing pauses: held keys are released as real events, the logic stops ticking (no reward accrues), every sound is paused via `SoundManager.pause()` (keeps Rhythm's disc in sync; always resumed on resume/finish/close), and a keep-alive empty chunk (`fromTick == toTick`, checksum 0) goes to the server every 5 s so the 15 s idle timeout doesn't close the session. Resume fades the panel out and runs a 3-2-1 countdown before ticking again; Finish ends the session immediately.
- `/dmzminigame play <minigame> [targets] [masterBonus]` / `learn <minigame|all> [targets]` (`MinigameCommand`, nodes `dmzminigame.self/others`). `play` stores a 60 s one-shot `CommandGrant` and sends `OpenMinigameS2C`; the client opens the screen with origin `COMMAND` (appended to `MinigameOrigin`), and the server only starts a COMMAND session with a matching grant (mentor bonus from the grant; COMMAND sessions never count learning runs). `learn` adds the game(s) to known and clears learn runs.
- Difficulty ramps with `difficulty() = min(levelsCleared, difficultyCapLevel - 1)`, so every game plateaus: levels keep counting after the cap but parameters stop scaling. Defaults were tuned with an offline bot harness (human-model bots per tier against the real logic classes + replay determinism check) to give roughly equal reward units per minute across games for a skilled player; re-run a similar harness before retuning. `GravityLogic` limits how far consecutive gap centres can move (`baseMaxGapShift`) so every pillar pair stays reachable.

## Config System

Runtime config root: `config/dragonminez`. Managed by `common/config/ConfigManager` (static; initialized from `DMZCommon.init()`).

Files loaded/generated:

- `general-user.json` (client-only prefs — never synced), `general-server.json`, `combat.json`, `training.json`, `skills.json`, `techniques.json`, `entities.json`.
- Per race (`DEFAULT_RACES` = human, saiyan, namekian, frostdemon, bioandroid, majin; custom race folders auto-detected): `races/<race>/character.json`, `races/<race>/stats.json`, `races/<race>/forms/*.json`.
- Stack forms: `forms/*.json`.
- (`<world>/dragonminez/wishes/*.json` is wish data owned by `WishManager`, not ConfigManager — see Wishes.)

Versioning rules:

- Config version is a **semver String** `"X.Y.Z"` (`ConfigManager.CONFIG_VERSION`, mirrored by each config class's `CURRENT_VERSION`/`configVersion`). `parseSemver` requires exactly 3 numeric components; anything else (all legacy `double`/`int` versions like `21.0`, `21.10`, `12`) is treated as outdated and forces an upgrade. Do NOT go back to numeric versions — `21.10` as a `double` equals `21.1`.
- Outdated or missing-version default config files are MOVED to `config/dragonminez/oldBackup/<same relative path>` (`backupOldConfig`) and regenerated (the three-way merge re-applies the author's still-valid edits). `oldBackup/` is excluded from config scans. The `old_` filename prefix is only a skip-filter for user-authored form files — it is NOT the backup mechanism.
- **Unparsable (malformed-JSON) files are NEVER moved or overwritten** — that would throw away the author's in-progress edits. `loadAndValidate` returns in-memory defaults for the session and leaves the file exactly as-is; the same guard covers default form files (`createOrLoadRace`/`createOrLoadStackForms` only write a default when the file is genuinely missing). Malformed race/stack/user form files, and malformed quest/saga/sidequest/wish files, are likewise skipped (not regenerated). All of these are recorded in `JsonLoadReport` so the author is told which file to fix; a syntax fix + `/dmzreload` restores their values. This is deliberate: brand-new custom quests/forms that are broken are reported, not salvaged.
- Regeneration merges **three-way** against the previous release's defaults bundled at `resources/data/dragonminez/previousConfigs/<same relative path>` (`loadBaselineObject`): if the user's value equals the old default it upgrades to the new default (propagates balance changes); if it differs it is kept (respects user edits). New default keys are added; user-added map keys are kept. With no baseline file (custom races/forms, or newly added defaults) it falls back to "preserve any value differing from the new default".
- **Per-release workflow:** before shipping, copy the previous release's generated `config/dragonminez` tree into `resources/data/dragonminez/previousConfigs/` (excluding `oldBackup`/`old_*`), then bump `CONFIG_VERSION`. Skipping this silently weakens the merge for everything without a baseline.
- The pre-`21.2` `DEFENSE_SCALING_FOLD` migration (×0.12) applies only to legacy numeric-version stats files and only folds user-modified `defenseScaling` values, avoiding double application.
- Default race/form files are regenerated only when missing or invalid/outdated. Unknown custom races and user-defined form groups are loaded and preserved (`putIfAbsent` over defaults); custom races skip default form generation entirely.

Known dead code / traps inside ConfigManager:

- The `config_defaults` template mechanism (`saveDefaultFromTemplate` reading `/assets/dragonminez/config_defaults/<name>`) points at a resource directory that does not exist; first-run generation silently falls back to no-arg constructor defaults. Do not assume templates seed files.
- The 7-arg `applySyncedServerConfig(...)` batch method is unused dead code; real sync is the per-file `applySpecificSyncedConfig` path.

Aura style (2D vs 3D) keys:

- Every aura type field is doubled: `auraType` / `extraAuraType` name a **2D** billboard sprite set (`textures/entity/races/aura/<type>_aura.png` + `_cross.png`, default `kakarot`), while `auraType3D` / `extraAuraType3D` name a **3D** shader style (default `smooth`). Present on `FormConfig.FormData` and, for the base look, `RaceCharacterConfig`. Only `smooth` and `sparking` exist in 3D; anything else falls back to `smooth` via `Aura3DRenderer.resolveType` (the single fallback point — the getters are plain Lombok and may return null/empty, which is how a blank value still means "don't override the race-level type"). The 2D names were deliberately NOT renamed to `auraType2D`, to avoid breaking configs already in the wild.
- Which of the two a viewer sees is NOT a config decision: see Player State (`Character#aura3D`) and `client/render/effects/AuraModeState`.
- The look of the 3D `smooth` aura is data: `FormConfig.Aura3DStyle`, stored as `aura3DStyle` (and `extraAura3DStyle`) on `FormData` and as `aura3DStyle` on `RaceCharacterConfig` for the base look. Keys: `size` [x,y,z], `flamePeaks`, `waveFrequency`, `waveSpeed`, `waveAmplitude`, `noiseDetail`, `upwardBias`, `coreAlpha`, `rimAlpha`, `rimPower`, `rimThreshold`, `coreColor`/`rimColor`/`noiseColor` (hex, empty = derived from the aura colour / no noise tint), `bloomIntensity`, plus four sparking-only keys: `spikeDensity` (spike columns, capped at 32 because the mesh has 128 segments and a spike needs four to resolve), `spikeBurstRate`, `spikeRarity`, `bandStart`. Every getter is null-safe, so a deleted key falls back to the base default. Tuned per-form presets live in `DefaultFormsFactory` (`aura3D()`, `kaiokenAura`, `darkAura`). Both 3D styles read the block; each ignores the keys that do not apply (sparking has no `flamePeaks`, `waveFrequency`, `upwardBias` or `noiseColor`, and reads `waveAmplitude` as spike reach and `waveSpeed` as surge speed). The alpha defaults are tuned for the hollow smooth shell: a sparking aura wants `coreAlpha` 0.18, `rimAlpha` 0.85, `rimPower` 6, `rimThreshold` 0.02, since it fills its interior.

2D aura orientation (`AuraRenderer#executeAuraShaderDraw`, `#applyAxisBillboard`). The sprite is an **axis-locked** billboard, never screen-aligned: its vertical is pinned to the aura's own axis (world up, or `flightAxis` while flying fast) and it only spins around that axis. A screen-aligned card tips with camera pitch, which both leaned the flame and swung its `AURA_2D_GROUND_OFFSET` lift along the camera's up instead of the world's, sliding the sprite off the character (up to ~105 px at 60 degrees of pitch with over-shoulder) and swinging its apparent width over a 2x range as you looked around. `applyAxisBillboard` takes the world direction the sprite's +Z should end up facing: the reverse of `Camera#getLookVector` when upright, which keeps the card parallel to the screen sideways so it never skews when the player sits off-centre; the line from the camera to the aura's centre while flying, where the axis IS the line of sight and the view direction has no usable horizontal component; and the look vector itself for the ground `_cross` disc, which reproduces the old `Ry(-yRot)` exactly. There is no over-shoulder compensation any more - the old `SHOULDER_LEAN_*` roll existed only to hide the screen-aligned tilt and now fights it.

- Upright, everything that used to read `Camera#getXRot` is measured off the line from the camera to the sprite's centre instead. `elevation` (that line against the aura axis) drives the cross-fade to the `_cross` ground sprite from `AURA_2D_CROSS_START_DEG` and the `pitchSquash` that comes with it, and decides whether the disc is flipped because the camera is genuinely underneath. Camera pitch only equals that elevation when the aura sits dead centre in the frame; over-shoulder, a wall-clamped camera, another player off to the side, or an oversized form all break the equivalence. **Flight deliberately keeps `flightAxisAlignment`** (the camera's look vector against the flight axis): there the axis is the player's own view, that reference is what the fade was tuned against, and the geometric line would collapse the cross to a foreshortened sliver whenever the camera is offset sideways.
- A wall can clamp the third-person camera inside the sprite, where it is a screen-wide wash with no silhouette left. `AURA_2D_NEAR_FADE_*` fades it out over roughly its own half width (`finalScaleX * SPAN`, bounded by `MIN`/`MAX` so a big form's aura never dims at ordinary third-person range, gone at `FLOOR` of that distance). This is the only alpha the 2D path takes from the camera.
- `KiSenseAuraRenderer` deliberately stays screen-aligned: it is a radially symmetric glow blob centred on the entity, not a flame that has to stand up.

3D aura rendering (`client/render/effects/Aura3DRenderer`, `AuraRenderer`). Both styles share one pipeline: a shell of revolution, all relief as vertex displacement, real-time motion from `AuraRenderer#advanceMotions`, and redrawn bloom.

- `smooth` mesh: an egg-shaped shell (`AuraMeshFactory#getDropletMesh`, 96x96, position only). All flame tongues are vertex displacement in `aura_smooth.vsh`: `flamePeaks` vertical ridges x bands climbing at `Phase`, plus a tileable runtime noise texture (`AuraNoiseTexture`). `Peaks` is rounded to an integer and the noise repeats once per turn, so nothing seams where `atan` wraps.
- `sparking` mesh: a narrower egg (`AuraMeshFactory#sparkingProfile`, 72 rings x 128 segments, position/colour/normal; the colour is unused, there is no vanilla position+normal format). `aura_sparking.vsh` covers the shell with a grid of cells (`spikeDensity` thin columns x 18 rows, half that for the coarse ones x 12 rows); each cell fires, holds and kills its own spike on its own beat, and the grid climbs at `CLIMB_RATE` x `waveSpeed` (1.25s to cross the shell at the default, against the smooth aura's 0.8s). A spike lives about a third of a second, so it pops in and out as it rises rather than reading as a drawn-up flame. The spread of the per-cell draws is load-bearing and deliberately wide (length coefficient of variation ~0.97, beat rates 0.55x-1.55x, free per-column row offsets): raising the floors in `spikeLength` lines the shell with an even fringe, which reads as regular. The spread also drags the average length down, which is why `THIN_REACH`/`BIG_REACH` are larger than the displacement you actually see; tune those together. The needles cut into the outline band in the fragment stage climb at the same rate; the two constants have to be changed together. Spikes are suppressed to 15% away from the silhouette and rooted at the base, but deliberately kept alive over the crown: without them the round top of the egg reads as a smooth dome, which is exactly what the climbing tongues hide on the smooth aura. Shape is load-bearing: width over height is 0.66 and the widest band stays taller than it is wide (1.33:1). A wider shell, a flatter shoulder, a spike envelope that does not fade over the crown, or an outline band that is not damped on the near-horizontal caps (`vUp`) each turn the silhouette back into a rounded box.
- Motion is real-time and per aura owner (`AuraRenderer#advanceMotions`, once per frame per player), and both styles read it rather than the per-frame `alphaProgress` ramp, so ignition is frame-rate independent: `growth` ignites the shell in ~0.25s and shrinks it when the aura ends (ghost auras), each layer's shown `AuraStyle` eases towards its target (~0.5s) so transformations morph, and `phase` accumulates `waveSpeed` so speed changes never jump. Charging a form blends the style towards the next form by charge progress. Merged auras share the leader's motion state.
- `growth` drives more than size. Smooth swells the shell then bursts its tongues (`pow(Growth, 6)`); sparking swells the shell, runs a front up from the feet that lights the spike field, fires one overshoot as it passes, and on the way out pulls the spikes straight up and raises `bandStart` to 1 so the outline thins away instead of fading flat.
- Both styles draw the shell once into the bound target and queue a redraw of the same shell with `BloomPass` 1 through `AuraRenderer.captureBloom` (see Bloom below). Nothing draws its own pixels through a `BloomPipeline` framebuffer: the old MRT capture path made the aura's visibility depend on that framebuffer surviving every resize, so a broken mask could cost the effect itself instead of only its glow. Sparking draws through `ModRenderTypes.getCustomAura`, whose stencil shard keeps it off the player's body; the redraw framebuffer attaches the main depth-stencil, so that survives the redraw.

Bloom, shared by every effect (2D/3D auras, lightning, flight trails, ki attacks): `client/render/shader/BloomPipeline`, fed by `EffectBloomRenderer.render` at the end of `PlayerEffectsRenderHandler#renderEffects`.

- One full-resolution mask per frame, premultiplied by coverage. Every effect is queued with `AuraRenderer.captureBloom`/`captureAuraBloom` (ki attacks are their `KiRenderTask`s, replayed with `bloomMode` 1 and `EffectBloomRenderer.bloomPass` set) and redrawn through `beginRedraw`/`endRedraw` into a framebuffer of mask colour + the main target's depth-stencil, so walls and the player's stencil mask still hide the glow. The same path runs under Iris.
- That framebuffer is re-attached on the first `beginRedraw` of every frame (`BloomPipeline#attachRedraw`), never cached by texture id. A window resize (maximise, fullscreen) recreates the main target and the mask, and NVIDIA hands the freed texture names straight back, so a cache keyed on ids kept the framebuffer on the deleted textures; it still reported `GL_FRAMEBUFFER_COMPLETE`, and every glow (auras and ki) was gone for the rest of the session. Any other raw framebuffer built on another target's textures needs the same treatment.
- The ki tasks of a frame run back to back in one shared state (blend on, default blend func, depth test on, no depth writes, no culling), once normally and once in bloom mode. A task that flushes a `RenderType` in the middle (`KiWaveRenderer#renderGalickLightning`, the Soul Punisher's `endBatch`) must call `EffectBloomRenderer.restoreKiState` afterwards: the RenderType's clear state leaves blending and the depth test off, so everything after it drew opaque and through walls, and wrote its full colour into the mask (which is why the Final Flash and Galick Gun used to glow much harder than every other attack).
- `resolve`: 2:1 downsample + separable blur at 1/2, 1/4, 1/8 (`bloom_down`, `bloom_blur`), then one blended composite into the main target (`bloom_composite`: bright colours glow additively with tone mapping, dark colours are laid over as a veil). The former `ki_bloom` PostChain is gone; `program/ki_blur_h.fsh`/`ki_blur_v.fsh` remain because `utility_blur` uses them.
- Under Fabulous graphics the whole effects stage draws into the main target (`BloomPipeline.bindMainIfFabulousLayer`): the weather target it would otherwise land in has cleared depth and sorts behind the terrain.
- Core shader JSON `blend` blocks must equal vanilla's (`add`, `srcalpha`, `1-srcalpha`, non-separate). Any other translucent mode latches `BlendMode.lastApplied`, after which vanilla shaders overwrite their callers' blend functions; the GUI vignette then paints the world black until an opaque post pass runs. Apply the shader first and set separate functions through `RenderSystem` afterwards (`Aura3DRenderer#drawShellMesh`, `BloomPipeline#resolve`).

Aura border (`client/render/effects/AuraBorderRenderer`, shaders `aura_border`, `aura_border_field`): a flaming outline that hugs the silhouette of any entity, independent of the 2D/3D aura. It is screen-space, not a mesh.

- Capture: an entity renderer wraps its buffer source with `AuraBorderRenderer.begin(entity, source, colorOrNull, partialTick)` and releases it with `end(...)` around `super.render`. The wrapper is a second `TransformationMaskBufferSource` (raw colour = per-frame border index in the red channel), so hair, armour and held items are in the silhouette and the skin/hair layers' capture toggles keep working (they forward to a nested outline source). Passing `null` as colour means "inactive": the border fades out over real time and the state is dropped. Captures are only accepted between `AFTER_SKY` and the effects stage, never in the Iris shadow pass, never for the first-person camera entity.
- `process` (end of `PlayerEffectsRenderHandler#renderEffects`, both the vanilla and the Iris path): flushes the mask into its own target with a copy of the main depth, then per entity (far to near) builds a blurred coverage field at 1/2, 1/4 or 1/8 resolution (picked from the on-screen thickness, scissored to the entity), draws the flames over the scene and redraws them into the bloom mask through `BloomPipeline.beginRedraw`.
- The mask flush MUST run with an identity `RenderSystem` model-view: at `AFTER_PARTICLES`/`AFTER_WEATHER` vanilla has the camera rotation pushed on the model-view stack, and the captured vertices are already in view space. Without it the mask is rotated twice and is simply empty in third person (it only "works" for geometry wrapped around the camera).
- Thickness is world-sized (`THICKNESS_PER_HEIGHT` x bounding-box height, projected), so the border keeps its proportion with distance and fades out below `FAR_FADE_PIXELS`. Noise is anchored to the entity's projected centre and scaled by the thickness, so it neither swims nor changes scale when the camera moves. Flames rise along the projected world up.
- Flames over something nearer than the entity are hidden by comparing the linearised scene depth with a per-entity depth (`DepthParams`). Verified under Fancy, Fabulous and Oculus + Complementary.
- Users: Ki Surge on players (`AuraBorderRenderer.playerColor`, active aura colour; the server no longer forces `auraActive` during a surge, see `TickHandler`), and supervillain saga NPCs (`SagaSupervillainLayer.borderColor` + a translucent skin tint).

Form lightning (`client/render/effects/LightningBoltRenderer`, shader `lightning_bolt`): the Dragon Ball style bolts around players with a lightning form or a Ki Surge (`AuraRenderer#renderSparksImpl`, third and first person) and around saga NPCs with `isLightning` (`DBSagasRenderer#executeLightningShaderDraw`). The old noise-displaced cross mesh (`lightning` shader, `AuraRenderer.getLightningMesh`) is still what `KiWaveRenderer` and `SPMajinCandyRenderer` use; leave it alone.

- A bolt is a flat ribbon rebuilt on the CPU every frame: a seeded polyline arcing around the body (uneven segment lengths, alternating kinks, pointed at both ends, up to two short forks), transformed to view space and expanded there with mitred joints so it always faces the camera. `u` runs -1..1 across the ribbon; the fragment stage turns it into a white core, a solid coloured outline and a soft halo, which is the whole look. Vertices are already in view space, so it draws with an identity model-view through its own `VertexBuffer`, never through `BufferUploader` (the model-view trap above).
- Timing is per burst, not per frame: two staggered tracks each fire a burst per period (`CHARGED_*` while the aura is active, `IDLE_*` otherwise) of one or two bolts spread over separate sectors and heights of the body, so one to four bolts from different sides are up at a time. A bolt's shape is seeded from entity id + track + cycle + index; it pops in at full strength, re-strikes once while it holds (`STRIKES_PER_LIFE`) keeping its anchor, and then always gets its own `FADE_TICKS` of thinning fade-out. `emitBurst` evaluates the previous cycle as well as the current one, because a bolt's delay + hold + fade can run past the end of its burst period; evaluating only the current cycle cut those bolts off in a single frame. Frame rate never changes the cadence.
- The stroke is deliberately thin with a strongly uneven width (swelling and pinching from joint to joint), uneven segment lengths, kinks that usually but not always alternate side, and short barbs at the joints; regular alternation reads as a sawtooth, not as drawn lightning. Charged bolts are wider only so they survive inside the aura.
- First person is its own placement (`drawFirstPerson` / `screenPath`), anchored to the CAMERA: bolts are laid out in camera space on a plane `FIRST_PERSON_DEPTH` ahead, sized from the projection matrix so they cover the same share of the screen at any FOV. Each bolt picks a spot anywhere on screen with a bias towards the edges (`FIRST_PERSON_EDGE_BIAS`, a power curve on the distance from the centre) and runs roughly along that edge, so the crosshair area stays mostly clear; it is drawn at about a quarter opacity (`AuraRenderer.LIGHTNING_FIRST_PERSON_ALPHA`). A bolt that appears in front stays where it appeared until it is gone, whatever the player does with the view: anchoring to the body made them swing with the body yaw, and anchoring to the world left them behind the player after a turn; both were rejected. Under Iris there is no depth test, as with the other effects. Bloom is a queued redraw of the same seeded geometry.

Trails. Two ribbon trails share one idea (positions sampled once per entity tick, drawn as a camera-facing ribbon in camera-relative world space with the view rotation as model-view) but not one look:

- `AuraTrailRenderer` (shader `aura_trail`) is the fast-flight aura trail of players and, through `submitEntityTrail`, the trail of both nimbus clouds (`FlyingNimbusRenderer`, `BlackNimbusRenderer`: 64 samples against the aura's 26, recorded only while the cloud moves and eaten from the tail when it stops). Entity trails are queued as `PlayerEffectQueue` entity effects so they draw in the effects stage with bloom, recover the view rotation from the entity's own render pose, are skipped in the Iris shadow pass, and are tracked in `ENTITY_TRAILS` so `forget` (which only knows about players) does not wipe them every frame. They use less white in the core and a weaker bloom (`ENTITY_CORE_WHITE`, `ENTITY_BLOOM`) or a yellow cloud's trail burns out to plain white. The nimbus entities no longer spawn their ambient and boost-trail `KINTON` particles; the boost burst is still particles.
- `KiTrailRenderer` is the comet tail of the small ki projectile (`KiProjectileRenderer`, render type 0 only). It is drawn with the ki attack shader itself so it matches the ball: `shapeMode` + `localPosMode` + `flameMode`, with the ribbon's across/along coordinates packed into the vertex colour. For that, `kiattack` now reads the vertex colour's alpha as a fade in `localPosMode` (the only other `localPosMode` mesh, `KiSpiralMesh`, writes 255). The tail is capped by length (`MAX_LENGTH` x projectile size), not by sample count, because projectile speeds differ a lot. It runs inside the projectile's `KiRenderTask`, so the bloom pass comes for free.

Aura colour balance: the 3D smooth aura tones its resolved colours down (`AuraStyle.BRIGHTNESS`, since the shell is lit by its own rim on top of the scene), and the 2D aura maps its sprite through `AuraRenderer.applyAuraColors` — one place for the four colour bands, brightened to sit at the same strength. Change both together.

Client/server config sync:

- On login (and `/dmzreload`), the server sends EVERY config file except `general-user` (`CLIENT_ONLY_CONFIG`), one gzip-compressed `SyncServerConfigS2C` per file; the first packet carries `reset=true` which begins a fresh sync batch. Payloads route by path into `SERVER_SYNCED_*` fields, and all `get*Config` getters return synced values while `serverSyncActive` and the caller is on the logical client (`ConfigManager.useServerSync()` checks `EffectiveSide`), so a singleplayer/LAN host's server thread always reads its own loaded config, never the client's synced copy. `/dmzreload` no longer calls `clearServerSync()` server-side; clients reset through the `reset=true` batch packet. The client clears sync on disconnect (`ConfigManager.clearServerSync()` in `ForgeClientEvents`).
- `/dmzconfig` (ConfigCommand) live-edits single keys via `updateConfigValue` → `reloadSpecificConfig`, which **bypasses** version checks, oldBackup, and the three-way merge (straight deserialize + single-file sync). The in-game editor `DMZConfigEditScreen` persists via `saveRawConfig`. Only full `reload()`/`initialize()` run the validation+merge pipeline.

## Quest System

Quest data is world-save JSON, loaded by `common/quest/QuestRegistry.loadAll(MinecraftServer)` from `ForgeCommonEvents.onServerStarting` and `/dmzreload`. Runtime world structure:

```text
<world>/dragonminez/
  sagas/        # saga manifest JSON (recursive scan)
  quests/<questFolder>/   # quest files, loaded alphabetically (01_...json ordering)
  sidequests/   # side-quest JSON (recursive scan)
```

Key behaviors:

- Default generation: sagas require BOTH `storyModeEnabled` AND `createDefaultSagas`; side quests require only `createDefaultSideQuests` (independent of story mode). Runtime load gates are separate: sagas load only when `storyModeEnabled`, side quests only when `sideQuestsEnabled`.
- Default files are now **version-upgraded in place** by `QuestUpgrader` (the quest-side analogue of the `ConfigManager` three-way merge). Every generated quest/saga/side-quest is stamped with `"defaultsVersion"` (`QuestUpgrader.DEFAULTS_VERSION`, a semver string). On load, `QuestDefaults`/`SagaDefaults`/`SideQuestDefaults` route through `QuestUpgrader.upgradeOrWrite`: missing → write fresh; stamp equals current → skip (fast path); stamp missing/older → three-way merge the user file against the shipped baseline (`resources/data/dragonminez/previousQuests/<same relative path>`) and the new code default. Merge rule (matches the config merge, plus a conflict flag): user==old-default → take new default (balance fix propagates); new==old → keep user; **both changed → keep the user's value and record a conflict** (never destructive). User-added keys preserved; arrays (objectives/rewards) merge only when structurally aligned, else whole-array conflict → keep user. The pre-merge file is copied to `<world>/dragonminez/oldBackup/<relative>` only when the merge made a substantive change (a pure re-stamp does not back up).
- **Per-release baseline workflow (required, like `previousConfigs`):** before shipping a release that changes default quest values, snapshot the *previous* release's generated quest tree (`<world>/dragonminez/{sagas,quests,sidequests}`) into `resources/data/dragonminez/previousQuests/` (same relative layout), then bump `QuestUpgrader.DEFAULTS_VERSION` and apply the new values. With no baseline for a file, the merge falls back to "preserve any user value differing from the new default" (non-destructive, but that release's balance fixes won't auto-apply to edited fields).
- Upgrade results accumulate in `QuestUpdateReport` (cleared each `loadAll`): a summary is logged and written to `<world>/dragonminez/quest_update_report.txt`. The whole feature is gated by the `autoUpdateQuests` server-config flag (default true; false = legacy generate-only-if-missing). The in-chat notification is no longer quest-specific — `loadAll` pushes a one-line summary into the unified `JsonLoadReport` (see below), which surfaces it to players on login.
- **Unified JSON load report (`common/diagnostics/JsonLoadReport`):** a single in-memory collector of load-time problems across all runtime JSON — configs, quests/sagas/sidequests, and wishes. Loaders record `ERROR` entries when a file is malformed/failed (`ConfigManager.loadAndValidate` parse failures, `ConfigLoader` form-file skips, `QuestRegistry` saga/quest/sidequest parse skips, `WishManager.loadWishConfig` skips — each carrying the deepest Gson cause with its `line/column/path`) and `UPDATE` entries when defaults were auto-upgraded. Each subsystem tags its entries with a `source` (`"config"`/`"quests"`/`"wishes"`) and clears only that source at the start of its own load, so `/dmzreload config` doesn't wipe quest findings. `server/events/DataReportEvents.onPlayerLogin` shows the report to **every** player on login (not just ops), gated by the `developer.reportJsonProblemsInChat` server-config flag (default on). Purpose: let server owners/addon authors who hand-edit these files see exactly which file broke and where, instead of a silent reset-to-defaults. Console logs and `oldBackup/`/report files remain authoritative.
- Six default sagas: saiyan → frieza → android, then future and buu both branch from android, movies requires buu.
- Saga quest key is `sagaId:numericId` (the JSON `id` int, not the filename — duplicate ids in one folder silently collide). Side-quest key is the JSON string id.
- Objective types: ITEM, KILL, INTERACT, STRUCTURE, BIOME, DIMENSION, COORDS, TALK_TO, DRAGON_SUMMON, SKILL. Reward types: TPS, ITEM, ALIGNMENT, COMMAND, SKILL, TRANSFORMATION, KI_TECHNIQUE.
- **Reward difficulty (per reward, in `QuestParser.parseReward`):** each reward carries an `EnumSet<Difficulty>` (`QuestReward.difficulties`, default = all) parsed from an optional `difficulty` field (aliases `difficulties`/`difficultyType`/`minDifficulty`). The value is an **explicit allow-set**, accepted as a JSON array (`["NORMAL","HARD"]`), a comma/space string (`"NORMAL, HARD"`), or a single name (`"HARD"`); unknown tokens are dropped, absent/empty = all difficulties. `isUnlockedFor(d)` is set membership — NOT a minimum threshold, so `"NORMAL"` means Normal-only and `["EASY","HARD"]` is expressible. The old `hard:`/`normal:` **type-string prefix was removed** (a leftover `"type":"normal:ITEM"` now fails to match and the reward is dropped). `SyncQuestRegistryS2C.serializeReward` mirrors this: plain type name + a `difficulty` array (only when the set is a strict subset), re-parsed client-side via `QuestParser`. `QuestService.claimAvailableRewards` gives a reward only when `isUnlockedFor(pqd.getDifficulty())`, scaling ITEM/TPS/ALIGNMENT amounts by `Difficulty.questRewardMultiplier()`; SKILL/TRANSFORMATION/KI_TECHNIQUE/COMMAND are unlocks and don't scale. Tree + NPC panels group rewards by difficulty-set via `QuestTextFormatter.groupRewardsByDifficulty`/`describeRewardDifficulties` (header lists the set, e.g. "Only: Normal, Hard"; locked groups greyed). Defaults (`QuestDefaults`/`SideQuestDefaults`) tag rewards with the `onlyOn(reward, "NORMAL", "HARD")` helper.
- `loadAll` builds indexes (objective type, quest giver, turn-in) used by `QuestService`. `loadAll` does NOT sync to clients — `SyncQuestRegistryS2C` is sent from `StatsCapability.syncToClient()` on login and from `ReloadCommand`; reloading quests outside those paths leaves clients stale until relog.
- `SyncQuestRegistryS2C` carries two JSON strings capped at 1 MiB each; the standalone-quests blob excludes SAGA-type quests (sagas travel in the sagas blob).
- Kill objectives: contiguous KillObjectives in a sequential quest unlock and count as one block (`QuestEvents.isKillObjectiveUnlocked` walks back to the block start). Default `CountMode.QUEST_SPAWNED_ONLY` requires the killed entity to carry `dmz_quest_key` + `dmz_quest_objective_index` + `dmz_quest_owner` tags (written by `QuestService.spawnKillObjectives`, which also writes stat/AI-tier/transformation-override tags).
- Quest failure: party wipe fails only quests that have at least one KillObjective; `failQuest()` increments failureCount and resets progress.
- `PlayerQuestData` NBT: `difficulty`, `questState`, `difficultyChosen`, `partyState`, with legacy migration from `difficultyStates`/`hardModeEnabled`. Party join adopts the leader's difficulty wholesale.
- Server code uses `getQuest()/getSaga()`; client GUI uses `getClientQuest()/getClientSaga()` — cross-side calls silently return empty.

Quest update rules: preserve filename ordering conventions, translation-key titles, and user-authored addon quests when changing the parser schema.

## Otherworld Death And Baba Temporary Revive

Server logic is `server/util/BabaReviveService` plus `server/events/players/BabaReviveEvents`; state lives in `Status` (`isAlive`, `tempReturnTimer` ticks, `tempReturnsUsed`, `tempReturnReadyAt` Overworld day time, `deathCount`, `forceHalo`) and the cooldowns `Revive` (`REVIVE_BABA`), `BabaKnockout`, `BabaAggroGrace`. Tuning is `general-server.json` -> `gameplay`.

- Death with the Otherworld active (`ForgeCommonEvents.onPlayerDeath`): `deathCount++`, `REVIVE_BABA` = `reviveCooldownSeconds` (scaled by `1 + babaHardcoreCooldownGrowth * (deaths - 1)` when `babaHardcoreEnabled`) if the player was truly alive; a death while temp-revived (only `BYPASSES_INVULNERABILITY` sources such as `/kill` or the void, everything else becomes a knockout) instead sets `tempReturnReadyAt` one Overworld day ahead, like an expiry. Timer/KO cleared, `isAlive=false`, and `requestSpiritArrival` flags the player so `TickHandler.handleOtherworldTransfer` moves them to `OtherworldDimension.SPIRIT_ARRIVAL` even when they respawned inside the Otherworld (any other dead player without an active timer is moved as soon as they are outside it). Creative and spectator players are never moved. Dead players keep every ability (space pod, shared TP, False SSJ, Mutant, forms); the only dead-only rules left are the Otherworld ones (free stamina, no hunger, `otherworldDeadTpMultiplier`) plus Saiyan Zenkai and the Bio-Android self-destruct, which require `isAlive` because both leave the user knocked out.
- Baba (Otherworld `baba` master, through `MasterTextScreen` -> `NPCActionC2S("baba", 1)` -> `handleBabaRevive`) never teleports; King Yemma does (`handleEnmaReturn` -> `teleportToLivingWorld`, allowed when alive or temp-revived). `babaTemporaryRevive=false`: Baba sets `isAlive=true` (old behaviour). `babaTemporaryRevive=true` (default): after `REVIVE_BABA` and `tempReturnReadyAt`, Baba sets `tempReturnTimer = babaTempReturnSeconds * 20` and `tempReturnsUsed++`; the player stays dead (halo) but walks the living world. Both NPC dialogues read the synced config and the player's state to pick their lines and enable their button; `baba_earth` never revives.
- Timer (`tickTempReturn`, once per second from `TickHandler`): paused in the Otherworld and while knocked out; otherwise drains `20 * form * dimension * escalation` ticks. `form` = `1 + Σ max(0, drain - 1)` over the active form and stack form, where `drain` is `FormData.getOtherworldTimeDrainAt(mastery)` (linear from `otherworldTimeDrain` at 0 mastery to `otherworldTimeDrainMastered` at max; defaults in `DefaultFormsFactory`: tier 1 forms 1.5→1.1, SSJ grade 2 1.75→1.2, grade 3 2.75→2.0, tier 2 2.0→1.25, tier 3 3.0→2.5, tier 4 3.0→1.5, mastered SSJ 1.3→1.0, false SSJ 1.25→1.1; Kaioken/Ultimate 1.0). `dimension` = `babaTimeMultiplierPerWorld[<dimension id>]` else `defaultBabaTimeMultiplier` (defaults: nether 2, end 3, HTC 5, others 1). `escalation` = `min(5, 1.5^(tempReturnsUsed - 1))`. Action-bar warnings at fixed thresholds. Expiry: `tempReturnReadyAt = overworld dayTime + 24000` (sleeping skips it), teleport to the spirit arrival, `/dmzrevive` or the `revive` wish (`reviveFully`) clears everything and sets `isAlive`.
- Knockout instead of dying: a lethal hit on a temp-revived player outside the Otherworld (`CombatEvent` lethal branch after the racial and world-boss hooks, plus a `LivingDeathEvent` HIGHEST fallback that cancels the death and sets 1 HP; `BYPASSES_INVULNERABILITY` sources still kill) runs `tryKnockOut`: timer −= `max(20% of remaining, 5% of babaTempReturnSeconds)` (floored at 1 tick so the expiry fires when the KO ends), `knockedDown` + `KNOCKDOWN_DURATION`/`KNOCKDOWN_INVULN`/`BabaKnockout` = 600 ticks, `BabaAggroGrace` = 900 ticks, forms/charges/surge cleared, Glowing, quest failure as on death (`QuestEvents.handlePlayerQuestFailure` + `EntitiesEvents.cleanupQuestEntities`), nearby mobs drop their target. While `BabaAggroGrace` runs, `LivingEntityMixin.canBeSeenAsEnemy` returns false and `BabaReviveEvents` cancels `LivingChangeTargetEvent` towards the player. While `BabaKnockout` runs every heal is blocked (`LivingHealEvent`, the three `DMZEvent.*RegenEvent`s, and the direct `setHealth` paths: healing liquid, Dende/Piccolo, negative form health drain) and `tickKnockoutRecovery` refills linearly to 33% HP and 50% ki/stamina over the 30 s. Because it reuses `knockedDown`, Majin absorption and Namekian assimilation treat the downed player as a free capture.
- Shared party TP (`TPGainEvents.shareWithParty`) uses `canReceiveSharedTp`: same dimension, within `instantTransmissionPlayerRangePerLevel * earner IT level` (no IT = no share), member not creative/spectator, no anti-ki cloak, not IT-blocked (Android upgrade / god ki), not a fusion follower. No battle-power window and no alive check.
- HUD: `BabaReturnTimerHUD` is a small bottom-right panel (`HudElement.BABA_TIMER`, Extras group, default anchor 1/1, offset -6/-2, scale 0.8; `HudRender.panel` background shared with the notifications and the boss contribution panel), all text centred in the `smooth` font: the label, the remaining time (a `HudSmoother` glides through the intermediate seconds instead of jumping on each 10-tick sync), and a tag line that fades in/out: `(xN)` when the effective multiplier is above 1 (green up to x2, orange up to x3, red above), `Paused` in the Otherworld or `KO` while knocked out. The whole panel fades with the state.
- `MasterTextScreen` re-evaluates the Baba/Yemma line and button every second from `tick()` (cooldown countdown, button enabling itself), and any dialogue longer than 4 lines gets a mouse-wheel scroll with a thin scrollbar instead of overflowing the box.

## Wish And Dragonball Systems

Two interleaved pipelines — definitions (ball sets, radars, dragons) and wishes — with three sources: hardcoded bootstrap, external addon packs, and per-world overrides. There is **no in-jar datapack wish/definition JSON**: `DragonDefinitionReloadListener` and `DragonWishRegistry` are `SimpleJsonResourceReloadListener`s rooted at `dragonminez/dragonballs` but both IGNORE the scanned datapack JSON and call `DragonBallPackManager.loadAll()` instead. Adding standard datapack JSON under that path does nothing.

- `DragonBallDefinitions` holds bootstrap maps (hardcoded earth/namek sets, shenron/porunga, radars, recipes) plus runtime maps set on reload. `syncRegisteredBlocks()` copies Forge `RegistryObject<Block>` refs from bootstrap into same-id runtime definitions after every reload — addon packs cannot introduce new blocks at runtime; new blocks need a `Main*` deferred register.
- `DragonBallPackManager.loadAll()` scans folder and `.zip` packs under the game-dir `dragonballs` root (plus sibling candidates), routing files by suffix (`definitions/{ballset,radar,dragon,wishes}.json`, `assets/...`). It runs three times per boot/reload (bootstrap static init, definition listener, wish listener).
- `WishManager.loadWishes(server)` runs at `onServerStarting` (not on datapack reload): starts from addon-pack wishes, then merges `<world>/dragonminez/wishes/*.json` (auto-creating default `shenron.json`/`porunga.json`). World-save wish files are **plain JSON arrays**; the dragon id is the filename stem, and a file fully replaces that dragon's wish list. The `{"dragon": ..., "wishes": [...]}` object wrapper is the addon-pack format only. Note: a vanilla `/reload` re-runs the listeners but NOT `WishManager.loadWishes` — world-save overrides need `/dmzreload` or restart.
- Wish types (registered in `common/util/gson/WishTypeAdapterFactory`, 12 total): `item`, `command`, `tps`, `multi_wish`, `item_list_wish`, `skill`, `passivereset`, `recustomize`, `relocatestats`, `changedifficulty`, `resetstory`, `revive`. Every wish accepts an optional `"repeatable": false` (null/absent = repeatable) that stops the same entry from being picked twice in one summon. `revive` (`ReviveWish`, `maxTargets`, shenron 3 / porunga 1) is the only wish with targets: it truly revives up to `maxTargets` online dead players chosen by the wisher (`BabaReviveService.reviveFully`), so Porunga revives one per wish but can take the revive wish three times. `recustomize` (`ReCustomizeWish`) arms a per-player server token when granted; `UpdateCharacterC2S` (class swap + full heal) only applies by consuming it. The token expires after 15 minutes and is cleared on logout, so cancelling the screen cannot leave a free heal armed.
- Grant flow: owner right-clicks `DragonWishEntity` → `WishesScreen` (shenron 1 wish, porunga 3). Left click adds a pick, right click removes the last pick of that row; a picked row shows its slot numbers (`1`, `2 - 3`) top-right inside the gold outline. On opening, the screen asks `RequestReviveTargetsC2S` → `ReviveTargetsS2C` for the online players that are dead (`GrantWishC2S.isRevivable`), and a revive row cannot be picked while that list is empty. Confirm opens an in-screen picker for every revive pick that has no targets yet, then sends `GrantWishC2S` (the dragon's entity id + index + target UUID list per slot) → server only accepts that exact dragon (owned by the sender, not granted, within 50 blocks, wish screen id matching), re-resolves targets (online, dead, deduped, capped at `maxTargets`), drops non-repeatable duplicates, caps at `wish_count`, grants (`Wish.grant(wisher, targets)` for targeted wishes) → entity despawns after 100 ticks, resets weather/time, and rescatters balls via `DragonBallsHandler.scatterDragonBalls`.
- Scattering (`server/events/DragonBallsHandler`): first spawn scatters full sets (and records `SpawnedCopies`), later scatters add at most 1 per star capped at `copies`; if the configured `copies` grows after the first spawn, `topUpCopies` (server start and every scatter) adds only the difference per star, so carried balls do not inflate it (worlds without `SpawnedCopies` estimate it from the highest tracked count). Positions are XZ-random around world spawn, tracked as "pending" in `DragonBallSavedData` (per-level SavedData, key `dragon_balls_data`, with legacy Earth/Namek key migration; sets whose definition is missing are kept on save) and placed on the heightmap when their chunk is loaded (`ChunkEvent.Load`, plus a 20-tick per-level maintenance pass that only uses `getChunkNow`, never force-loads). Tracking mirrors the world: `DragonBallBlock#onPlace`/`#onRemove` register/unregister any placement or removal path (players, commands, mods, our own generation), `ChunkEvent.Load` adopts untracked ball block entities, and an active entry whose block is gone (crash rollback, region edits, chunk regen) is dropped and respawned elsewhere — on chunk load or in the maintenance pass for loaded chunks. Ball items (`DragonBallBlockItem`) cannot be damaged; a ball item lost by despawn (`ItemExpireEvent`), `/kill` (`KILLED`) or the void respawns as a pending ball (never on plain `DISCARDED`, which is also how hoppers pick items up). Item removals by clear-lag mods that call `discard()` are not detectable. Radar sync (`RadarSyncS2C`) includes pending balls; changes mark it dirty and it is sent once at the end of the server tick (plus every 100 ticks), with immediate per-player syncs on login, respawn and dimension change. Summons: the dragon is spawned before the balls are removed (a blocked spawn keeps the balls), is persistent (no vanilla despawn) and registers a `Summon` (UUID, set, expiry) in the level's `DragonBallSavedData`; an ungranted dragon leaves after `DRAGON_WAIT_TICKS` (10 min of game time). If it is unloaded when it expires the maintenance pass rescatters its set and the dragon silently discards itself when it loads again (record gone + `SummonExpiresAt` set). `DragonWishEntity` rescatters on any destroying removal (`KILLED` or `DISCARDED`) only while it still owns its record; dragons from older saves (no `SummonExpiresAt`) register one on their first tick.
- Admin command `/dmzdragonballs` (`server/commands/DragonBallsCommand`, nodes `dmzdragonballs.status` / `dmzdragonballs.regenerate`): `status` lists every set (placed/pending vs `copies` × stars, waiting dragons); `status <set>` lists each star's positions per dimension with click-to-TP (pending ones show `?` as Y) and the time left for each waiting dragon; `regenerate <set>` drops stale entries in loaded chunks and adds pending balls in the set's home level until every star tracks `copies` (`DragonBallsHandler.regenerateSet`). It is the recovery tool for sets whose balls are held by players who never come back; those carried balls are not counted, so the set can end up above `copies`.
- `DragonBallDataPackResources` is a synthetic PackResources that only injects crafting recipes for addon radar items.

## Storage

`StorageManager` (`server/storage`) selects the player-data backend from `general-server.json` (`StorageConfig`, default `NBT`):

- `NBT`: `activeStorage == null`; the whole custom layer (StorageManager/DataSyncHandler/JsonStorage/DatabaseManager) is inert and persistence is purely the vanilla capability path (`StatsProvider` INBTSerializable → player `.dat`).
- `JSON`: `<world>/dragonminez/playerdata_json/<uuid>.json` (pretty-printed via NbtOps/JsonOps).
- `DATABASE`: MariaDB via HikariCP (`jdbc:mariadb` only); gzip NBT in a `MEDIUMBLOB` keyed by uuid. Hikari `poolSize` and async `threadPoolSize` are separate config keys.

Behavior and caveats:

- Vanilla `.dat` capability persistence is ALWAYS on. JSON/DATABASE modes double-persist: the custom store async-loads on login (`DataSyncHandler` on `PlayerLoggedInEvent`) and its data overwrites vanilla-loaded values on the server thread, then a full `StatsSyncS2C` is pushed. Logout saves via `DataSyncHandler`.
- The DB "fallback" is a log message, not a code path: on connection failure `DatabaseManager` stays the active storage and silently no-ops; durability comes only from the vanilla `.dat` path. Nothing switches to JsonStorage/NBT.
- `savePlayer` serializes NBT on the server thread and submits only the IO to the executor; it skips saving when `!isDataLoaded && !hasCreatedCharacter` (blank pre-character guard).
- Auto-save is a hardcoded 5-minute `scheduleAtFixedRate` (not config-driven), JSON/DATABASE only.
- `DMZEvent.PlayerDataLoadEvent` fires before apply (tag mutable), `PlayerDataSaveEvent` after serialize / before write.
- Login load is async but ordered: `loadPlayer` chains behind the player's pending `saveChains` future (so a quick relog reads the finished logout save) and marks the UUID in `pendingLoads` until the apply lands on the server thread. While pending, `savePlayer` skips (the vanilla-loaded values are not authoritative yet) and progression packets (quest actions/claims, NPC actions, wishes, stat/skill purchases) are ignored via `StorageManager.isLoadPending`. The apply only runs if that `ServerPlayer` is still the online instance. A slow load is never discarded: after 30 s it only logs a warning and keeps saves paused until the real result applies (discarding it would let the vanilla snapshot overwrite the authoritative JSON/DB record, e.g. progress made on another server sharing the DB). A load that throws is retried (3 attempts, 5 s apart); if it still fails the UUID goes to `failedLoads` and `savePlayer` skips that player for the rest of the session. Both backends currently catch their own errors and return null (= no record), so that path only covers unexpected exceptions. `reload()` re-requests pending/failed loads after re-initialising, because loads queued on the old executor never complete.
- Auto-save hops to the server thread (`server.execute`) before serializing; never call `savePlayer` from the scheduler thread directly.
- `/dmzreload` reload saves online players, then `shutdown()`+`init()`; note the async executor is recreated without shutting the old one down (leak on repeated reloads).
- Never block the server thread with DB/filesystem work; never log credentials; preserve `StatsData` NBT key names (cross-backend contract).

## Worldgen And Dimensions

Split between Java registration, datagen output, and static resources:

- Custom dimensions (`server/world/dimension`): Namek, HTC (Hyperbolic Time Chamber), Otherworld, and Sacred Kai (`SacredKaiDimension`, with `SacredKaiFeatures`). `OtherworldRegionLoader` loads pre-generated `.mca` regions at server-about-to-start / server-started / Otherworld level load, gated by `worldGen.otherworldActive`.
- Demon Realm (`dragonminez:demon_realm`, Dragon Ball Daima): one stacked dimension, Y -64..767, three floors separated by crusts, travelled top to bottom (outer to inner ring of the Daima schematic). Top = Third Demon World (pink sky, yellow Makai sand/grass, Makai stone/strata mesas, lilac sand patches, teal agave/bush vegetation, gas vents, floating rocks; its chasms are the Sea of Darkness: `dark_sea_cloud` above crust B, which blinds and deals 25% max health magic damage per hit). Middle = Second Demon World (lime sky, Namek grass/turquoise rock islands, vanilla water sea at `SECOND_SEA`=318 filled by the `demon_realm_sea` feature because sea level must stay at `WORLD_BOTTOM` or the aquifer picker floods the void with lava/water, ajissa trees, majilite ore). Bottom = First Demon World (red sky, reddish demon rock, red ash, magma patches, rock spires only inside `NoiseThresholdCountPlacement` fields so most ground stays walkable, rare crimson crystals; `demon_horn` is registered for a future structure but not generated). All layout constants live in `DemonRealmGeneration`; each crust has an unbreakable `demon_realm_crust` core and is crossed only by giant tunnels (radius 90 ± 10 edge noise, grid every 2048 blocks; Third→Second at 0/0 through crust B with a crater lip, Second→First at 700/450 through crust A inside a raised crater island so the sea cannot drain) carved by the custom density function `dragonminez:tunnel_distance`, with a passable emissive orange `light_shield` membrane placed at each core by `demon_realm_tunnel_shield`. Lighting: shader packs ignore `ambient_light`, so the floors must receive real sky light. Worldgen places the pink-floor and crust blocks (`DemonRealmBlocks.SkylitBlock` / `SkylitSandBlock`: makai stone, strata, sand, grass, dirt, lilac sand, crust) with `natural=true`, which makes them light-transparent, so the skylight source runs straight down to the Second Demon World; player-placed copies default to `natural=false` and stay opaque. The First Demon World sits under water and Namek blocks, so `demon_realm_ambient_light` places invisible level-15 `minecraft:light` blocks every 5 blocks, 2 above the ground (same trick as the Tree of Might). Gas vent mounds only fill 3 blocks of support (a long `groundColumn` hung pillars under floating islands). Biomes are 3D: the router `depth` is a Y gradient and each biome owns a depth span (`DemonRealmGeneration.depthAt`), so features filter by floor with `BiomeFilter`; surface features use the `dragonminez:surface_in_band` placement (scans down inside a floor band) because heightmaps only see the top floor. Client: `CustomSpecialEffects.DemonRealmEffects` draws a per-floor gradient dome, translucent moons and planets (middle floor) and a red sun (bottom floor) from `textures/environment/demon_realm`, tints clouds per floor (`DMZCloudsRenderer` height overload) and `adjustFog` (via `ForgeClientEvents.onRenderFog`) only pulls the terrain fog start in to 65% of the far plane on the two upper floors. No player access yet (no portal, pod destination or death routing).
- TerraBlender: `ModCommonEvents.commonSetup` registers `OverworldRegion` (weight 40; adds the rocky biome additively) and overworld surface rules.
- `server/world` also contains `biome`, `data` (SavedData like `DragonBallSavedData`, `RaidSavedData`), `feature`, `gen`, `npc` (alignment-driven placement/spawning), `raid` (Raid/RaidManager/RaidTypes/waves/rewards), `structure` (incl. `StructureSpawnPlanner` precompute, `VillagePoolInjector`, placement types, processors), `tree`.
- Raid defeat (any raid): a participant farther than `leashDistance` from the centre keeps counting as active for a 15 s grace (`Raid.LEASH_GRACE_TICKS`, action-bar countdown `raid.dragonminez.leash_warning`); death, logout and dimension change still drop them at once. When no participant is active the raid fails and `RaidFeedback.mourn` shows the `defeat` block of the raid JSON to every online participant (`title`, `subtitle`, signed `alignment` delta applied with `ResourceSyncS2C`; defaults -20 Namek, -10 Earth). `/dmzraid stop` cancels without the defeat. Raid music plays at 0.5 volume (`RaidMusicManager.MUSIC_VOLUME`).
- Saiyan Assault raid (`saiyan_assault` in `config/dragonminez/raids/`, Earth counterpart of the Namek `frieza_invasion`): triggered by the procedural `saiyan_crater` structure (`BossStructures.SaiyanCraterStructure`, vanilla `RandomSpreadStructurePlacement` 40/20 chunks with a villages exclusion zone, `TOP_LAYER_MODIFICATION` step so it clears trees; only new chunks get craters). The crater piece places an open `SpacePodEntity` and a supervillain scout during worldgen (stats from the raid `trigger` block: `health`/`meleeDamage`/`kiDamage`/`aiTier`, with code defaults when the block is missing). `RaidSiteManager` (one `Kind` per raid site: Saiyan crater in the overworld, Namekian ruins on Namek) scans loaded chunk starts around players every 40 ticks, posts the chat key `announceMessage` once per player within 80 blocks, adopts the scout by its `dmz_raid_site` tag (or places a crew in craters generated before the crew existed), and records each site in the per-dimension `dragonminez_raid_sites` SavedData so it is spent after the scout dies or vanishes. Namek counterpart: the `namek_ruins` structure (`BossStructures.NamekRuinsStructure`, static structure set `worldgen/structure_set/namek_ruins.json`, random spread 40/20 with a `village_ajissa` exclusion zone, `beard_thin`) places 3-4 real Namekian house templates (sacred style in `sacred_land`, ajissa elsewhere, jigsaw blocks replaced, entities ignored) around a scorched plaza, ruins them deterministically per block (roofs collapse with height, ki blast spheres, broken glass, scorch marks; block entities are kept) and puts a supervillain Frieza soldier in the plaza; the old 5% natural-spawn trigger is off by default (`spawnChance` 0). Killing the scout runs the normal `raid_wrath` omen. Mobs are `SagaSaiyanInvadersEntity.Soldier`/`Elite`/`Oozaru` (saga AI; elites add `GENERIC_KI_WAVE` and the NPC-only `KI_MEDIUM_BALL`; Oozarus add `OOZARU_FIST`/`OOZARU_SLAM`). Final-wave elites (`canTransform` + `transformHealth`/`transformMeleeDamage`/`transformKiDamage` spawn fields, written as `dmz_quest_tf_*_abs`) throw a fake moon and transform into Oozarus through `finishTransformationSpawn`. They render through the player renderer: `SaiyanInvaderRenderer.Puppet` is a client-only `RemotePlayer` whose `StatsData` is filled from the synced `Look` (body type 1, hair preset, hair/skin colour, armor set, scouter). The puppet implements `GeoAnimatable` itself and registers the saga controllers (`DBSagasAnimationHandler` predicates take the owning NPC explicitly), and `DMZPlayerModel` gives puppets `saga_base.animation.json` with the player files as fallbacks, so they move with saga clips on the player model; `DMZRacePartsLayer`, `DMZPlayerRenderer.shouldShowName` and `DMZThirdPartyLayerForwarder` special-case the puppet.
- Tree of Might (nested `TreeOfMight*` classes of `server/world/structure/BossStructures`, the single file that holds every world boss lair and raid structure (tree, Gete Star, Saiyan crater, Namek ruins); the Turles world boss lair, see `WorldBossLair.Turles`): a procedural structure, no `.nbt`. `TreeOfMightShape` uses no Minecraft types so it can be rendered offline; it builds a deterministic skeleton from a seed plus ground samples (trunk with flare and bark ridges, buttress roots, limbs and branches that follow the canopy underside, a hollow noise canopy ~340 blocks wide, ~225 hanging roots, 6-10 of them ending in a `might_tree_fruit_block`, glow lichen patches on the visible wood, a flat clearing that is the boss arena) and rasterizes any chunk region into a byte buffer (`NONE/FOLIAGE/ROOT/WOOD/FRUIT/LICHEN`, lichen faces in a parallel mask using `Direction` 3D data order). `TreeOfMightWriter` turns one chunk of that buffer into blocks: clears/flattens the arena, drops hanging roots until they hit natural ground, extends the base down into water/holes, adds lichen, places invisible level-15 `minecraft:light` blocks on a 6-block grid 6 blocks above the ground under the canopy (dim but even light, nothing hostile spawns in the shade), then writes `might_tree_wood`/`might_tree_root` (unbreakable), `might_tree_leaves` (opaque, breakable, no drops, not flammable) and the fruit (block only, no BlockItem, emissive faces + light 6, drops `might_tree_fruit`, never regrows). `TreeOfMightStructure` builds the shape in `findGenerationPoint` (seed = `TreeOfMightShapes.seedFor(levelSeed, startChunk)`, ground = `OCEAN_FLOOR_WG` noise heights); `TreeOfMightPiece` stores seed, centre, build limits, sea level, `ShapeVersion` and the ground samples in NBT and rebuilds the shape lazily through the shared `TreeOfMightShapes` cache. Placement: `BiomeAwareUniquePlacement` in `#dragonminez:is_swamplike`, salt `DMZStructureSets.TREE_OF_MIGHT_SALT`, `min_distance_from_spawn` 1000 (new optional codec field, honoured by `StructureSpawnPlanner.minRingFor`). Once released, any change to the shape math must bump `TreeOfMightShape.VERSION` and keep the old generator, or half-generated trees get seams at chunk borders.
- The canopy is wider than vanilla allows a structure to be: `ChunkGenerator.createReferences` only links chunks within 8 chunks of a start. Chunks farther out are filled by the `tree_of_might_canopy` feature (biome modifier `forge/biome_modifier/tree_of_might_canopy.json`, every overworld biome, `surface_structures` step, no placement modifiers): it reads the planned tree chunk from `StructureSpawnPlanner.publishedPositions`, rebuilds the same shape (`TreeOfMightShapes.planned`), writes that chunk with `TreeOfMightWriter` and adds a reference to the tree start so the materializer treats it as done.
- Big Gete Star (`BossStructures.GeteStarStructure` + `GeteStarShape`, the Metal Cooler Core lair): procedural like the tree. `GeteStarShape` (`VERSION` 2) is pure geometry over ground samples stored in the piece, so reloads rebuild the same shape: a 60-block unbreakable `gete_star_hull` sphere sunk ~40 blocks, `gete_star_circuit` seams, an equatorial belt, 9 antennas, 10 spider legs (Bezier tubes with a knee joint and a round foot pad, ~92-112 blocks out), 12 thinner tendrils, and a drained ring (coarse dirt, gravel, Namek dirt, tuff, rare `gete_debris_ore`) up to ~123 blocks; the whole box stays inside the 8-chunk reference radius. Inside: a hollow 36-radius chamber with a floor 10 below the sphere centre, 4 production alcoves, 3 doors to a ring corridor (radius 41-50) lined with red glass capsules, and a tunnel plus ramp to the outside along a random entrance angle; the core stands opposite the entrance. `BiomeAwareUniquePlacement` in Ajissa plains or sacred land, >= 1000 blocks from 0,0, salt `GETE_STAR_SALT`. The Namekian trader sells a map to it (`NamekTraderEntity.getOffers`, `CapsuleCorpMapTrade`); `/dmzlocate gete_star` also finds it.
- Old worlds: structures implementing `IncrementalStructure` (the tree and the Gete Star) are not force-placed in one tick and are never relocated. `StructureRepairManager.forcePlace` sets the start, then `Materializer` completes every already-generated chunk of the box (up to 14 chunks out) that lacks the structure reference, 48-block slices bottom-up (the tree visibly grows), ~4 ms per tick, only while the chunk is loaded; `ForgeCommonEvents.onChunkLoad` re-queues chunks after restarts. Chunks with more than an hour of `InhabitedTime` are skipped, so player bases are never overwritten (the tree gets a hole there instead). Each `Materializer` is bound to its `ServerLevel` (weak reference) and dropped on `LevelEvent.Unload` (`ForgeCommonEvents.onLevelUnload`); do not rely on `StructureRepairManager.reset()`, because `ForgeCommonEvents.onServerStopping` is an instance method in a statically registered class and never fires. Never keep `Structure` (or any registry object) across server instances: `MappedRegistry.getKey` is identity-based, and a chunk referencing a `Structure` from a previous world makes every save of that chunk fail with an NPE in `ChunkSerializer.packStructureData`.
- Generated resources (`src/generated/resources/`): dimensions, dimension types, biomes, configured/placed features, structures, structure sets, template pools, tags, recipes, loot tables, advancements, space pod destinations, dragon definitions/wishes.
- Static resources (`src/main/resources/`): structure `.nbt`, Otherworld regions, biome modifiers, worldgen JSON, weapon attributes.

## Integrations

- Forge, Minecraft, GeckoLib, TerraBlender, and Curios are mandatory (`mods.toml`).
- Legendary Tooltips, Epic Fight, and Better Combat are hard-incompatible (mods.toml + startup crash in the entry class).
- JEI APIs are compile-only (`JEIDragonMineZPlugin` in `common/compat`); runtime JEI is a client-only dev mod.
- WorldGuard compatibility (`WorldGuardCompat`) is reflective and defensive — no hard dependency.
- Lombok is used at compile time (`compileOnly` + annotationProcessor).
- Crowdin uses `assets/dragonminez/lang/en_us.json` as the source locale (`crowdin.yml` maps locale filenames).

## Datagen

`common/datagen/DatagenManager` (mod-bus `GatherDataEvent`) registers providers: recipes (`DMZRecipeProvider`, plus `DMZKikonoRecipeProvider` and `DMZPatternRecipeProvider` used by it; the latter emits `dragonminez:pattern_crafting` 6x6 shaped recipes for the Pattern Station (per-Pattern dye pixel art of its chestplate) and fails datagen if two Patterns share a grid), loot tables, block states, item models, block/item/entity-type tags, worldgen (`DMZWorldGenProvider`) + biome tags, advancements, space pod destinations, dragon definitions, and dragon wishes.

## Beta Access Verification

Beta/alpha builds (version contains `-beta`/`-alpha`) reject non-whitelisted players in `ForgeCommonEvents.onPlayerLogin`. `BetaWhitelist` loads asynchronously from `https://raw.githubusercontent.com/DragonMineZ/.github/refs/heads/main/allowed_betatesters.txt` at server start with a small hardcoded fallback list. The disconnect is detected client-side by `DisconnectedScreenMixin`, which adds a `Verify here` button opening `BetaAccessVerificationScreen` → browser to `https://downloads.dragonminez.com/beta-access/start?username=<minecraft_username>` (override with JVM property `dragonminez.betaAccessUrl`).

The matching `dragonminez-ai` bot flow is intentionally narrow: Discord OAuth → guild member → Patreon beta roles → existing Patreon link + whitelist PR auto-approval. Keep it a small verification bridge, not a general public API.

## CI And Release Automation

Workflows in `.github/workflows/`:

- `gradle.yml` — Java CI: builds on PRs and pushes to `main` touching Java/build files; submits the Gradle dependency graph.
- `languages.yml` — Crowdin check & upload (see Localization).
- `codeql.yml` — CodeQL analysis. PMD rulesets live in `.github/workflows/pmd/`.
- `dev-jar-upload.yml` — dev distribution: runs on pushes to **`main`** (paths-filtered to Java/resources/Gradle/workflow inputs) and manual dispatch. Builds and uploads ONLY the no-classifier jar `build/libs/dragonminez-<mod_version>.jar` (never `-slim`) via SSH/SCP to the VPS with pinned host keys (vars `DMZ_VPS_HOST`/`DMZ_VPS_PORT`; secrets `DMZ_VPS_USER`/`DMZ_VPS_SSH_KEY`/`DMZ_VPS_KNOWN_HOSTS`/`DMZ_VPS_UPLOAD_DIR`). Upload is atomic (temp name → move), chmod `0644`, SHA-256 verified, then prunes old artifacts keeping the two newest `dragonminez-*__*__*.jar`. After upload it notifies the Discord bot locally on the VPS at `http://127.0.0.1:8088/dmz-dev-jar` (bypassing Cloudflare) using `DMZ_RELEASE_BOT_WEBHOOK_SECRET`.
- `release-prepare.yml` — validates stable release candidates on `main`, builds the jar, writes manifest artifacts (via `scripts/release/prepare_release.py`), and posts the candidate payload to the Discord bot at `https://release-bot.dragonminez.com/dmz-release` (secret `DMZ_RELEASE_BOT_WEBHOOK_SECRET`).
- `release-publish.yml` — triggered by Discord-bot approval through `repository_dispatch` (`dragonminez_release_approved`) or manual dispatch with the same payload fields. Verifies the approved commit is still `origin/main` HEAD, rebuilds, compares the jar SHA-256 against the approved manifest (**mismatch is a warning, not a failure** — resource optimization is not byte-reproducible), publishes to Modrinth and CurseForge, updates `update.json` (via `scripts/release/update_forge_update_json.py`), and commits it back to `main`.

Rules:

- Do not publish GitHub Release jar assets from these workflows.
- Stable `main` releases only: versions containing `alpha`/`beta` are skipped or rejected.
- The Discord bot must not hold Modrinth/CurseForge tokens; those stay in GitHub Actions secrets.
- Python release helpers live in `scripts/release/` (`prepare_release.py`, `release_common.py`, `update_forge_update_json.py`, `release_tools_test.py`).

## Update Checklist For Future Agents

Before changing behavior:

- Identify whether data is code-owned, datapack-owned, config-owned, world-save-owned, or addon-owned.
- Prefer editing canonical loaders/default factories over hand-editing generated/runtime files.
- If a JSON schema changes, update parser, defaults, config version, sync packets, and docs together. For configs, also refresh the `previousConfigs` baseline at release time.
- If adding content, register it through the appropriate `Main*` class and ensure datagen/assets/lang are complete.
- If adding packets, add the packet class and APPEND its `NetworkHandler.register()` entry (never reorder).
- If adding reloadable data, wire a reload listener and a sync path if clients need it.
- If changing server config used by clients, remember sync is generic per-file, but nested layouts need routing in `applySpecificSyncedConfig`.
- If changing player state, update ctor/save/load/copyFrom/sync/storage expectations together.
- If changing worldgen/datagen, run `runData` and inspect generated resource diffs.
- If editing language files, run `scripts/check_lang.sh` or equivalent JSON validation.
- If editing code, run at least `.\gradlew.bat build` unless blocked, and state any blockers.
