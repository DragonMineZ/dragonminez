# DragonMineZ AI Context

This file captures project context that AI agents should read after `AI/Agents.md` and `AI/Memory.md`. Keep it factual and update it when the architecture, workflows, or important repo conventions change. Last full audit against the code: 2026-07-07 (v2.1.1).

## Project Snapshot

DragonMineZ is a Minecraft Forge mod for Minecraft `1.20.1`, Java 17, mod id `dragonminez`. The root project name is `DragonMineZ`; archives are named from `mod_id`.

This repo is data-heavy and player-customizable. Many systems load JSON from runtime folders in `config/dragonminez`, world save folders (`<world>/dragonminez/...`), datapacks, and external addon folders. Do not assume JSON is internal-only or safe to rewrite destructively.

Dependencies declared in `META-INF/mods.toml`: Forge, Minecraft, GeckoLib, TerraBlender, and **Curios** are all `mandatory=true`. Legendary Tooltips, Epic Fight, and Better Combat are declared `type="incompatible"`, and the `com.dragonminez.DragonMineZ` entry class additionally throws `IllegalStateException` at construction if any of them is loaded.

## Build And Run

Use the Gradle wrapper from repo root, usually PowerShell on Windows:

```powershell
.\gradlew.bat build
.\gradlew.bat runClient
.\gradlew.bat runServer
.\gradlew.bat runData
```

Important details:

- Java toolchain and compiler release are Java 17.
- `runClient` and `runServer` use `run/` as working directory; `runData` uses `run-data/` and writes to `src/generated/resources/`.
- `src/generated/resources/` is included as a main resource source set. `build` depends on reobfuscation tasks and re-runs `runData`.
- Gradle runs **offline** (`org.gradle.offline=true` in `gradle.properties`).
- The distributable jar is the no-classifier `jarJar` artifact (bundles `mariadb-java-client` and `HikariCP`); the plain `jar` task produces `-slim`. Never ship the slim jar.
- Client-only dev mods (JEI runtime, Oculus, Xenon, Free Cam, Huge Structure Blocks) are on the classpath only for `runClient` (`includeClientOnlyDevMods` in `build.gradle.kts`) because some mixin into vanilla codecs and would poison `runData` output.
- PackSquash optimizes bundled PNG/OGG/JSON before jar packaging; automatic on CI, off locally, forced with `-PoptimizeResources=true|false`. Options in `packsquash.toml`.
- There is no committed `src/test` suite. Validate with `build`, `runClient`, `runServer`, or targeted in-game scenarios.
- `scripts/check_lang.sh` validates language JSON with `jq`.

## Lifecycle

Primary boot path:

- `com.dragonminez.DragonMineZ` is the `@Mod` entry point. Its constructor first enforces the incompatibility list (legendarytooltips, epicfight, bettercombat), then calls `DMZCommon.init()`, then side-specific init through `DistExecutor` (`DMZClient.init()` on client, `DMZServer.init()` on dedicated server — the latter is log-only; commands register via event).
- Root-package helpers: `Reference` (MOD_ID), `Env`/`LogUtil` (logging).

`DMZCommon.init()` is the central registration and setup point, in order: `ConfigManager.initialize()`, `QuestRegistry.init()`, `WishManager.init()`, `NetworkHandler.register()`, `GeckoLib.initialize()`, then deferred registers on the mod bus — `MainAttributes`, `EntityAttributes`, `MainBlocks`, `MainBlockEntities`, `MainItems`, `MainFluids`, `MainSounds`, `MainTabs`, `MainEntities`, `MainVillagers`, `MainParticles`, `MainRecipes`, `MainMenus`, `MainEffects`, `MainEnchants`, `MainLootModifiers`, `MainStructurePlacements`, `MainStructureProcessors`, `MainStructureTypes`, `OverworldFeatures`, `SacredKaiFeatures` — plus `ModCommonEvents::commonSetup`, `MainGameRules.register()`, `MainDamageTypes.register()`. Note the structure/feature classes live under `server/world/...` but register from common init.

`ModCommonEvents` (mod bus) also registers entity attributes, adds player attributes (`STRENGTH`, etc.), registers `DragonBallSavedData` capability, adds a pack finder, and in `commonSetup` registers the TerraBlender `OverworldRegion` (weight 40, adds the rocky biome without replacing vanilla biomes) and `OverworldSurfaceRules`.

Server event flow (`common/events/ForgeCommonEvents`, forge bus):

- `onServerAboutToStart`: pre-loads Otherworld regions when `worldGen.otherworldActive`, and runs `VillagePoolInjector.injectAll`.
- `onServerStarting`: `StorageManager.init()`, `BetaWhitelist.reload()` (async), `WishManager.loadWishes(server)`, `DMZPermissions.init()`, `QuestRegistry.loadAll(server)`, `NpcAlignmentRules.load`, `NPCPlacementManager.load`, `WorldGuardCompat.init()`, then first dragonball scatter per ball set if `worldGen.generateDragonBalls`.
- `onServerStarted`: `StructureSpawnPlanner.precomputeAndWait`, Otherworld region load (double-check), `NPCPlacementManager.spawnForLoadedLevels`.
- `onLevelLoad`: `StructureSpawnPlanner.onLevelLoad`; re-runs Otherworld region loading when the Otherworld level loads.
- `onServerStopping`: `StorageManager.shutdown()`, `StructureSpawnPlanner.reset()`.
- `onAddReloadListeners`: `SpacePodDestinationRegistry`, `DragonDefinitionReloadListener`, `DragonWishRegistry`, and an inline listener calling `WeaponRegistry.loadAttributes`.
- `onRegisterCommands` → `DMZServer.registerCommands`.
- `ForgeCommonEvents` also hosts gameplay handlers: login/logout/death/respawn/dimension-change, melee/ranged crits, `LivingAttack`/`LivingDamage` mitigation hooks, equipment change, mob spawn finalize, villager trades.

Registration pattern:

- New content belongs in a `common/init/Main*` class registered from `DMZCommon.init()`.
- New packets must be registered in `NetworkHandler.register()`; see Networking below for ordering rules.
- New mixins require both a Java class and an entry in `dragonminez.mixins.json`.

## Player State

Player state is capability-based:

- Core classes: `common/stats/StatsCapability`, `StatsProvider`, `StatsData` (~1570 lines; state + most stat/form/combat math).
- `StatsCapability` registers the capability and attaches a `StatsProvider` to every `Player` in `AttachCapabilitiesEvent<Entity>`. `StatsProvider` implements `INBTSerializable` (`serializeNBT()→data.save()`, `deserializeNBT()→data.load()`), so vanilla `.dat` persistence is always active regardless of storage backend.
- `StatsData` owns exactly 12 sub-objects (ctor-constructed): `Stats`, `Status`, `Cooldowns`, `Character`, `Resources`, `Skills`, `Effects`, `SecondaryStatEffects`, `PlayerQuestData`, `BonusStats`, `Techniques`, `DynamicGrowthData`. (There is no `Training` object; training config lives in `config/dragonminez/training.json`.) Sub-objects live in `common/stats/character/`, `common/stats/skills/`, `common/stats/techniques/`, `common/stats/extras/` (DynamicGrowthData), and `common/quest/` (PlayerQuestData).
- NBT keys written by `save()`: `Stats`, `Status`, `Cooldowns`, `Character`, `Resources`, `Skills`, `Effects`, `SecondaryStatEffects`, `PlayerQuestData`, `BonusStats`, `Techniques`, `DynamicGrowth`, `HasInitializedHealth`. These are the save-format contract for all three storage backends — renaming any silently orphans existing NBT/JSON/DB data.
- `load()` is a per-key partial loader EXCEPT it hard-throws (`ClassNotFoundException`, wrapped in RuntimeException) when the `PlayerQuestData` key is absent. Treat `load()` as a full-document loader, not a safe partial merge.
- Clone (death/dimension): `onPlayerClone` revives caps, `newData.copyFrom(oldData)` (deep copies; PlayerQuestData round-trips through NBT), invalidates old caps. A client-side `static StatsData CLIENT_CACHE` preserves character-creation state across clone only.
- Login sync (`onPlayerLogin`): sends every config file except `general-user` via `SyncServerConfigS2C` (first packet `reset=true`), `SyncQuestRegistryS2C`, then per-player fixes (visited dimension, unlock `saiyan_saga`, form-selection defaults, clear stun/knockdown/strike-lock, skill-name repair, deactivate kisense) and a full `StatsSyncS2C`.
- Adding a state group requires updating ctor + `save()` + `load()` + `copyFrom()` together, and deciding which sync packet carries it.
- `Character#aura3D` (NBT `Aura3D`) is a purely cosmetic flag that does not belong to gameplay state: it mirrors the owning client's `general-user` `aura3DPersonal` option so that every OTHER client renders that player's aura in the style its owner picked. The client pushes it with `AuraModeC2S` when the option is toggled, and `AuraModeState.reconcileLocal` re-pushes it whenever a `StatsSyncS2C` for the local player disagrees — that self-heals the login race against the async storage load, plus respawns and dimension changes, without a dedicated handshake. The viewer's own `aura3DEntities` option governs NPC auras instead, since entities have no owner.

Sync packets (all decode into the same client-side `data.load(nbt)`):

- `StatsSyncS2C` = full `data.save()` (login, dimension change).
- `ProgressionSyncS2C` = `Stats` + `BonusStats` + `Skills` + `Techniques` + `PlayerQuestData` (after progression changes, `/dmzreload`).
- `ResourceSyncS2C` = `Resources` + `Status` only (respawn, resource changes). Because `load()` throws without `PlayerQuestData`, this packet relies on the client already having full data — be careful changing `load()` or packet contents.

Ticking is split across THREE PlayerTick handlers:

- `StatsCapability.onPlayerTick` (server, END phase) → `StatsData.tick()` which only ticks `Cooldowns`.
- `server/events/players/TickHandler` — the real gameplay loop: regen (every 20 ticks), sync (every 10), effects/secondary-stat-effects/techniques ticking, aura light, stun handling.
- `server/events/players/StatsEvents` — weights, food-regen queue, health. Also applies the max-health `AttributeModifier` (`DMZ_HEALTH_MODIFIER_UUID`); energy/stamina/poise are custom attributes from `MainAttributes` (`MAX_ENERGY`, `MAX_STAMINA`, `MAX_POISE`). `hasInitializedHealth` (persisted) gates the one-time full heal.

Race, class, form, stack-form, effect, mastery, TP, and stat calculations read `ConfigManager` live on every call — there is no memoization, so `/dmzreload` changes results immediately.

## Networking

`NetworkHandler` creates a Forge `SimpleChannel` named `dragonminez:network` (protocol "1.0", all versions accepted). ~54 C2S and ~25 S2C packet classes live in `common/network/C2S` and `common/network/S2C`.

- Packet ids come from a sequential `id()` counter, so **registration order defines the wire ids**. Append new packets; never reorder or insert mid-list, or client/server builds desync.
- Each registration is a `messageBuilder(...).decoder(...).encoder(...).consumerMainThread(handle).add()` triplet with explicit `NetworkDirection`.
- Helper send methods: `sendToServer`, `sendToPlayer`, `sendToAllPlayers`, `sendToTrackingEntityAndSelf`, `sendToTrackingEntity`.
- C2S categories: character creation/update, stat/skill changes, quests (accept/claim/unlock), wishes (`GrantWishC2S`), space pod travel, actions/forms/release limit, flight/dash/ki blasts, party, techniques, combat. S2C: stat/resource/progression sync, config sync, quest/wish registry sync, radar sync, animations, UI opens, party toasts, weapon registry sync, space pod destinations.
- Validate all C2S input server-side. Never trust the client for stats, unlocks, permissions, quests, wishes, or progression.

## Client HUD

Main HUD style is the client-only `style` string in `hud_layout.json` (`"default"`, `"minecraft"`, `"legacy 1"`, `"legacy 2"`; `client/gui/hud/HudStyle`). It replaced the old `alternativeHud` boolean, which is still read once for migration (`true` -> `"minecraft"`). Every other old HUD key (`xenoverseHudPosX/Y/Scale`, `healthBar/energyBar/staminaBarPosX/Y`) was removed from the UI and the code; the fields survive only as null, accessor-less ghosts in `GeneralUserConfig` so `JsonSchema` does not warn about unknown fields in existing files, and `getHudStyle()` nulls them so the next save drops them. All overlays are always registered (`ModClientEvents`); each one early-returns unless it is the current style, and every overlay skips itself while the HUD editor is open (`HudLayout.isPreview()`), because the editor draws the HUDs itself on top of its dim layer.

- Layout (`client/gui/hud/layout/HudLayout`, `HudElement`): position, scale and visibility of every element (`main`, `minecraft_left/right`, `party`, `reserve`, `rage`, `skill_1..4`) live in `hud_layout.json` -> `layout.<style>.<element>` (`HudPlacement`: screen anchor 0/0.5/1 per axis + offset + scale + visible + hotbar). Missing entries fall back to `defaultPlacement`, so defaults can change without touching user files. Offsets and scale are stored in REFERENCE units: `HudLayout.unit` = GUI height / 360, so an element covers the same share of the screen at any window size or GUI scale (what the menus do with `ScaledScreen`). Exceptions that stay in raw GUI pixels because they hug the vanilla hotbar: the Minecraft-style side blocks and the three `legacy 2` elements (`legacy2_health`, `legacy2_ki` = ki bar + release/form icon, `legacy2_stamina`, each placed on its own; that style has no `main` element). `HudLayout.resolve` returns the box a HUD must draw into; HUDs never position themselves.
- Technique hotbar (`TechniqueHotbarHUD`): its four rows are layout elements `skill_1..skill_4` (every style; base 120x13 reference units, default staggered as a ladder, mirrorable; excluded from the meter collapse chain). Both technique bars (slots 1-4 / 5-8) share those rows. Display rules: holding a bar modifier shows that bar at full opacity; on release rows fade out fast (`FADE_SECONDS`), except a slot whose `TechniqueCooldown_<id>` is running, which settles at `COOLDOWN_ALPHA` for the whole cooldown, blinks when the synced cooldown reaches 0 and fades out `READY_LINGER_MS` later. If both bars have a lingering slot in the same row, the one closest to ready wins. One `HudSmoother` per slot, so closing the bar glides straight to the reduced opacity. In the editor a right-click on any row mirrors all four (positions reflected inside the group bounds), Shift+drag moves the group, resizing a row rescales the group around it, and Reset on a row resets the four. The old `techniqueHotbarRightSide` key is a null ghost field in `GeneralUserConfig` (same trick as the other removed HUD keys).
- HUD layout file: the active style and every placement live in their own client-only config, `config/dragonminez/hud_layout.json` (`HudLayoutConfig`: `configVersion`, `style`, `layout.<style|extras>.<element>`), so players can share a layout by sending that one file. It goes through the normal `loadAndValidate` path (versioned, value-preserving regeneration; user-only map keys survive, so a file with a missing/old version still keeps its placements). It is loaded only on `Dist.CLIENT`, is never synced (`ConfigManager.isClientOnlyConfig` covers it and `general-user`), and `HudEditorScreen` re-reads it from disk when it opens (`ConfigManager.reloadHudLayoutConfig`), so dropping a shared file in and opening the editor applies it without a restart. The old `general-user` keys `hudStyle`/`hudLayout` are null ghost fields; `GeneralUserConfig.migrateLegacyHud` moves them (and the older `alternativeHud`) into the new file once, right after load, then nulls every HUD ghost and both files are saved. That method replaced the ghost-nulling side effect that used to live in `getHudStyle()`.
- Editor history: snapshot-based undo/redo (`HudEditorScreen.Snapshot` = style + deep copy of the layout), capped at `HISTORY_LIMIT` = 5 steps each way. One step per gesture: a drag/resize is recorded on mouse release (only if something changed), instant actions (mirror, hide/show, reset, style change) go through `act(...)`, and arrow nudges on the same element within 800 ms merge into one step. Undo/Redo buttons show the available count and dim when empty; Ctrl+Z / Ctrl+Y / Ctrl+Shift+Z work too. Cancel restores the snapshot taken when the editor opened.
- Mirroring: `HudPlacement.mirrored` (right-click in the editor; only where `HudLayout.canMirror` allows it: `main` of `default`/`legacy 1`, `party`, and the technique rows). Nothing is drawn with a negative scale: `HudBar.setMirrored` flips the sprite UVs and anchors fill/chips/glint on the right, `HudRender.spritePart(..., flipX)` / a negative region width in `HudRender.blit` do the flipping, text is re-aligned instead of flipped, `HeadPortraitRenderer` negates its yaw, and `XenoverseHUD.part()` mirrors every blit around the element width except the baked `STM` label, which is drawn unflipped at the mirrored spot.
- Dynamic collapse: a side meter within `DOCK_DISTANCE` of a screen edge (or chained to one) slides out through that edge while it is empty/not applicable, and everything linked behind it (other elements within `LINK_DISTANCE` on its far side, overlapping on the other axis) shifts by the freed space. Links are geometric, never stored. A meter that is not docked stays visible even when empty. Meter visibility is fed by `HudSideMeters.update` -> `HudLayout.setMeterVisibility`.
- Minecraft style: a side block whose placement has `hotbar=true` ignores its box and keeps the hotbar-glued behaviour (slides with the offhand slot / attack indicator, shrinks on narrow screens); dragging it away in the editor clears the flag, snapping it back onto the hotbar side sets it again.
- Editor (`client/gui/config/HudEditorScreen`, opened from the config menu entry `config.hudEditor`): dims the screen, redraws the HUDs in preview mode (meters forced visible with a sample value, party shows sample members when empty), drag to move with 5 px soft-snaps (screen edges/margins, centre of each axis, other elements' edges with a gap, the hotbar for Minecraft blocks) drawn as guide lines, 8 handles for uniform resize, arrows to nudge, Show/Hide per element, Reset (selected or all), Cancel restores the whole layout and the style it opened with, Done/Esc saves `hud_layout.json`. The HUD style is chosen HERE (Style button cycles `HudStyle`; there is no separate style option in the config menu any more). Title and buttons sit at the top centre and use the DMZ widgets (`TexturedTextButton`, which now honours `AbstractWidget` alpha, `TextUtil` bordered text, the `smooth` font); the buttons fade out while an element is being moved/resized and back in afterwards, while the title (top) and the hint (bottom) always stay visible.
- `ModernHUD` (`default`), `MinecraftHUD` (`minecraft`), `PartyHUD` and `KiReserveHUD` draw from sprite sheets (`textures/gui/hud/hud_default.png`, `hud_minecraft.png`, `hud_party.png`, `hud_reserve.png`); the layout lives in `HudSprites`. Sheets are authored at 2 texels per GUI pixel and every on-screen size is derived from the sprite sizes (`BarSkin.width()/height()/border()`), while UVs are normalised against the LOGICAL sheet size passed to `HudRender.blit` - so a resource pack may ship any resolution (blockier or HD) as long as it keeps the layout and aspect ratio. Changing a sprite's size means updating its `HudSprites` entry. Bar layers: `frame` (border + empty track, drawn whole), `fill` (greyscale, multiplied by the stat colour, cropped to the value), `shine` (untinted highlights, cropped the same way), optional `alert` (red frame faded in at critical health). Section grooves and shading are baked into the sprites; only dynamic effects stay procedural (leading-edge glint, ki-charge sweep, surge/form-charge strips, reserve cap line, downed-ally overlay). Icons sit inside a square `capsule` sprite that shares its outline with the bar. `XenoverseHUD`/`AlternativeHUD` are the legacy texture HUDs (`legacy 1`/`legacy 2`); they use `HudRender.blit` so bar widths are sub-pixel too.
- Animation is per rendered frame, never per tick: `HudSmoother` (wall-clock exponential smoothing, jumps after a >1 s gap), `HudBarAnimator` (front + damage/heal ghost chip), and `HudBar` (bundles both plus the counting number and `HudStatNumberAnimator` fade/pulse). `HudBar.drawValue` keys the number animator on the REAL value, not the counting text, or the colour pulse is cancelled every frame. `SurgeBarState.fraction` integrates time, so call it once per frame (only one main HUD is active).
- `HudPlayerState.of(player, data)` is the per-frame snapshot shared by the main HUDs and the party rows (works for any tracked player: `StatsSyncS2C` reaches trackers every 10 ticks).
- Shared by every style: the side meters (`HudSideMeters`; `KiReserveHUD` = Frost Demon reserve tinted with the player's ki/aura colour, max = `maxEnergy * reserveMaxRatio`; `RageMeterHUD` = Mutant rage in dark green, or the Saiyan False Super Saiyan charge in red). Also shared: `PartyHUD`.
- Party HUD data: `PartyPackets.sendHudSync` (from `TickHandler`, same 10-tick cadence as the stats sync) sends each party member every online ally (nearest first, capped at `SYNC_MAX_MEMBERS` = 16) with name/HP/Ki/distance, world position, base aura colour and a `marker` flag as `HudSyncS2C` -> `PartyHudCache` (entries go stale after 2.5 s, cleared on disconnect). `PartyHUD` only draws the first `HUD_MAX_MEMBERS` (3). When the ally entity is loaded client-side the row reads live entity health and the synced capability instead, so bars move every frame; otherwise it shows the packet values, the distance, and the skin face.
- Party markers (`client/gui/hud/PartyMarkerOverlay`, registered first so every HUD draws over it; user toggle `partyMarkers` in the config menu): a Roblox-style arrow with the name and distance over each party member's head, any distance, through walls. The server decides visibility (`marker`): same dimension, within `gameplay.partyMarkerRange` (2000, the Instant Transmission menu range at level 10), alive, not spectator, and the same filters as the Instant Transmission list (`hasAntiKiCloak`, `isInstantTransmissionBlocked` = god form without `godforms`, upgraded android) plus the ki-sense rule that a player at 0% release is hidden. The client projects the head position with `CameraProjectionCapture` (projection x view captured at `AFTER_LEVEL`, camera position); loaded allies use their interpolated entity position, far ones the packet position through three `HudSmoother`s. Hidden closer than 2.5 blocks and when the point is off screen. Sprite `HudSprites.PARTY_MARKER` (`hud_party.png` 200,0 32x32), tinted with the ally's base aura colour or red when down; size and text scale use the HUD reference unit.
- Head portraits (`client/render/HeadPortraitRenderer`): renders the third-person `DMZPlayerRenderer` directly (never through the entity dispatcher, which would pick the head-less POV renderer in first person). While `HeadPortraitRenderer.isActive()`, `DMZPlayerRenderer` skips mask capture/aura stencil/aura border/model scaling/body rotation/name tag, only runs the skin, hair and race-parts layers, and `renderRecursively` drops every bone that is not `head` or a descendant (ancestors contribute no cubes and no transform; the head's own animation is zeroed) so the portrait stays framed during any animation. Hair uses `HairRenderContext.menuPreview()` (static, never touches the world simulation state) and ignores the first-person/helmet hiding rules. The entity render writes depth: anything drawn over a portrait afterwards needs a positive Z translate.

## Client Menus

Every DMZ menu extends `client/gui/character/util/ScaledScreen` (the tabbed character menus through `BaseMenuScreen`). Menus draw in "UI coordinates" inside `beginUiScale`/`endUiScale`; mouse input is converted with `toUiX/toUiY`, scissors with `toScreenCoord` (scissors ignore the pose, so add any slide offset by hand).

- Scale is LINEAR, like the HUD: `uiScale = guiHeight / REFERENCE_HEIGHT (270) * menuScaleMultiplier`, capped so the canvas never gets smaller than `getMinGuiWidth() x getMinGuiHeight()` (320x240 by default, 420 wide for `BaseMenuScreen`, 365x293 for the NPC dialogue / technique creator) and floored at `getMinUiScale()` (0.25). The UI height is therefore constant (270 / multiplier) at any window size or GUI scale, so a menu always covers the same share of the screen; the old `sqrt(availableScale)` formula is gone. `UtilityMenuScreen` overrides `computeDynamicScale` to keep its own (already linear) formula. `ScaledScreen.adjustMenuScale(+-1)` steps the multiplier by 0.05 and refuses to grow past the fit cap. The default multiplier is `GeneralUserConfig.DEFAULT_MENU_SCALE` = 0.75 (UI height 360, the size that reads well on every screen); the 2.1.x baseline in `previousConfigs` keeps 1.0 on purpose, so the version merge moves untouched configs to 0.75 and keeps values the player changed.
- Drawing: textures go through the float vertex-buffer blit (`ScaledScreen.blit(...)` -> `HudRender.blit`, plus `HudRender.nineSlice` and `HudRender.rect`), never `GuiGraphics.blit`, so slides and zooms are sub-pixel. The DMZ widgets (`CustomTextureButton`, `TexturedTextButton`, `SwitchButton`) implement `SubpixelWidget`; move them with `ScaledScreen.slideX/slideY(widget, base, floatOffset)` (integer part goes to the hitbox, the remainder to the draw position). Entity previews still need int coordinates, so screens translate the pose by the fractional remainder around `renderEntityInInventory`.
- Animation is per rendered frame on the wall clock: `BaseMenuScreen` open/close/panel-switch progress uses `System.currentTimeMillis` only (no `partialTick` term), panel offsets are floats, `renderMenuBackground` fades the dim layer with the open/close transition, and `ScaledScreen.frameDelta()/frameEase(tau)` (sampled in `beginUiScale`) replace the old `getDeltaFrameTime()*0.4f` and per-frame `approach01` steps. Not converted on purpose: the vanilla container screens in `client/init/menu/screens` (slot hit-testing is vanilla), the minigame playfields, `TournamentBracketScreen` (own zoom/pan) and the vanilla-styled utility screens; they only got float blits.
- Config menu (`ConfigMenuScreen`): options are grouped in collapsible categories (`Interface`, `Gameplay`, `Visuals`; expanded state is remembered for the session in a static set) with a search box on top that filters by option or category name and forces matches open. Rows are drawn in immediate mode (same sprites as the old widgets) inside a nested scissor per category so the accordion and the pixel scroll are smooth; clicks are hit-tested against the same rects. Adding an option = one `toggle/number/action` line in `initializeConfigOptions`. Crowdin live translations are always on now: the `liveCrowdinTranslations` key is a null ghost field in `GeneralUserConfig` and `CrowdinManager.isLiveTranslationsEnabled` only honours the `dmz.crowdin.enabled` system property.

- Quest menu navigator (left panel of `QuestTreeScreen`): same dropdown look as the config menu. Saga rows are headers (background plate, rotating arrow sprite, bold label, `completed/total` main-quest counter, `[L]` for locked/placeholder sagas), quests with side branches get a small rotating arrow instead of the old `> `/`v ` text, and the secret-sidequest section is a sub-header. `navigatorEntries` is still the logical list (rebuilt every 10 ticks); `mergeNavigatorRows` diffs it into the persistent `navRows` display list, keeping removed rows as ghosts under their closing parent, `updateNavigatorLayout` eases one open-progress per expandable row and lays blocks out recursively (drawer slide + nested scissor per block), and `navPlacementAt` hit-tests the same placements for hover and clicks. Clicking the already-selected saga header collapses/expands it (visual only, `currentSagaCollapsed`).

## Interactive Tutorial

`client/gui/tutorial`: a non-blocking first-time guide. A screen calls `TutorialManager.request(this, id, steps)` when its content is ready (idempotent; no-op when tutorials are off or the id was already seen). Nothing else in the screen changes: the overlay is drawn from `ScreenEvent.Render.Post` and input is intercepted from the `ScreenEvent.*.Pre` events, so every screen (scaled or not) can host one. A host that implements `TutorialHost` (all `ScaledScreen`s) supplies its UI scale and canvas size; rectangles are given in the host's UI coordinates through suppliers, so they follow resizes and animations.

- `TutorialStep` (builder): text/title keys, format-arg supplier (re-evaluated every frame), highlight rect supplier(s), `when` condition (skipped when false), `onEnter/onExit` hooks, `passthrough` (clicks inside the highlight reach the screen), `centered`, `width`, `noSkip`, custom `TutorialButton`s (text or +/- icon; `STAY`/`NEXT`/`FINISH`). Without a flow button the popup shows Skip + Next/Got it. Enter/Space = next, Esc = skip (marks the tutorial as seen); every other key and click is swallowed while a tutorial runs. Closing the host aborts without marking it seen.
- `TutorialOverlay`: dim layer built as the complement of the (animated) highlight rects in one `POSITION_COLOR` batch, pulsing accent frame, popup = 9-slice of the `menusmall.png` panel + `characterbuttons.png` buttons, placed right/left/below/above the highlight union (first that fits). It clears the depth buffer and draws at z=900 because screens render entities and text at z up to 500.
- State lives in `general-user.json`: `tutorialsEnabled` and `tutorialsSeen` (list of ids). Config menu -> Interface has the toggle and "Show Tutorials Again". No configVersion bump (2.2.0 is unreleased; missing keys fall back to field defaults).
- Tutorials: `race_selection` (welcome + disable, model/arrows, racial skill), `customization_class` (requested when the Aura/Class tab opens), `hud` (`HudTutorialScreen`, a transparent screen opened by `CharacterCustomizationScreen.finish()` on character CREATION only; waits for `hasCreatedCharacter` to sync, highlights the main HUD boxes from `HudLayout`, offers the HUD editor), `stats_menu` (menu size with +/-, name, level, TPs, each stat with the statistics rows it affects, TPC, TP multiplier; forces the list view while active), `skills_general` / `skills_techniques` (one shared id for Ki/Strike/Evasion) / `skills_forms` (requested from `refreshButtons`, i.e. on tab change), `quest_difficulty` (while the difficulty modal is up) and `quest_menu` (selects the first unfinished main quest, forces the saga panel open, fakes a hover on the target preview).
- `SkillsMenuScreen` injects a client-only `SAMPLE_ENTRY` row while the general/technique tutorial runs and the player owns no real entry; it never touches `Skills`/`Techniques` (the techniques getter returns the live capability map). Button init and detail rendering guard against that id.
- `TutorialHintHUD` (registered last in `ModClientEvents`): "Press [key] to begin your adventure" in the tracked-quest HUD slot while the player has no character, no screen is open and tutorials are enabled. With `forceCharacterCreation` on, the creation screen opens by itself and the hint is rarely seen.

## Mutant Rage Meter

The `mutant` effect (lottery in `MutantManager`/`MutantEvents`) no longer grants permanent legendary-form access. It drives a rage meter: `Resources.rage` (0-100, NBT `Rage`) and `Status.rageActive` (NBT `RageActive`), both synced by the regular `StatsSyncS2C`. All logic lives in `server/events/players/RageEvents`; tuning is `general-server.json` -> `mutant.rage` (`GeneralServerConfig.RageConfig`).

- Gain: `RageEvents.onFinalDamage` is called at the very end of `CombatEvent.overrideVanillaArmorReduction` (LivingDamageEvent, LOWEST) so it sees post-mitigation damage. Damage taken counts when it is >= `significantDamageTakenRatio` of max health; damage dealt counts only against worthy targets (players, or mobs whose max health is >= `significantTargetHealthRatio` of the attacker's, and never a full-health one-shot). Gain is proportional to the health fraction removed. Hits are classified MELEE / STRIKE (`MainDamageTypes.isStrikeAttackDamage`) / KI (`isKiblastDamage`) / OTHER; changing category within `varietyWindowSeconds` raises a variety step (up to `varietyMaxSteps`, +`varietyBonusPerStep` each), repeating it lowers one. Only significant hits refresh the combat timer (in-memory, per player).
- Access: `TransformationsHelper.hasMutantLegendaryAccess` = mutant + legendary group + (rage full OR rage active) -> one fake `legendaryforms` level in `hasFormSkillAccess` (level 0 passes even without a skill entry). `isRageBorrowedForm` = the form's `unlockOnSkillLevel` is above the real skill level. These run on both sides (radial menu, `SelectFormC2S`).
- Spending: a full meter while in a legendary-group form sets `rageActive`; it drains over `activeDurationSeconds`, and gains are scaled by `activeGainMultiplier` meanwhile. Leaving the legendary group stops it. At 0 a borrowed form is reverted down the previous-form ladder (same pattern as `ExecuteActionC2S.descendForm`) until the player lands on an owned form or base; owned forms are kept. A borrowed form without an active meter (relog, command, config change) is reverted on the next tick.
- Power (`StatsData.applyMutantFormPowerModifier`, legendary group only): borrowed form = bonus x `(1 - powerBonusReductionNoSkill)` (default 0.34 -> 66%); owned form while `rageActive` = bonus x `(1 + powerBonusBoostWithSkill)`; otherwise untouched. `powerBonusReductionNoSkill` kept its key on purpose (removing it makes `JsonLoadReport` warn about an unknown field in every existing config); only its default changed from 0.67, so existing files keep 0.67 until edited or until the next config version bump three-way-merges it.
- Decay: out of combat for `fullIdleSeconds` (full) / `partialIdleSeconds` (not full) the meter drains at 100 per `idleDrainSeconds`. Death resets it.

## False Super Saiyan (Saiyan)
A hidden Saiyan-only form that cannot be bought, selected or kept: it is granted by the same rage meter the Mutant uses (`Resources.rage`) and it ends when that meter empties. Logic lives in `server/events/players/FalseSuperSaiyanEvents`, the shared predicates in `common/util/FalseSuperSaiyanHelper`; tuning is `general-server.json` -> `falseSuperSaiyan` (`GeneralServerConfig.FalseSuperSaiyanConfig`).

- Data: form group `falseform` (`formType` `falseform`, form `falsesupersaiyan`, `unlockOnSkillLevel` 99) built in `DefaultFormsFactory.createSaiyanForms`. `falseform` is not a skill name, so `Skills.isUnlockedAtLevel` can never unlock it; on top of that `TransformationsHelper.getUnlockedForms` and `getOrderedFormsForRace` skip the type outright, which hides it from the skills menu, the character preview, the radial wheel and the Ultimate base-form pick. `getNextFormCandidate` returns null while it is active and `ExecuteActionC2S` ignores descend, so the player can neither climb out of it nor drop it manually; `formStackable` false keeps Kaioken/Ultimate off it.
- Ownership of the meter: Mutant first. `RageEvents.onPlayerTick` returns early (instead of zeroing the meter) when `FalseSuperSaiyanHelper.ownsRageBar`, and every false-form path requires the player NOT to have the `mutant` effect, so exactly one system drives `rage` at a time. `RageMeterHUD` paints the bar red in false-form mode and keeps the Mutant green otherwise.
- Requirements to charge: Saiyan, created and alive, not a Mutant, `superforms` skill level 0, `minLevel` <= level < `maxLevel` (100-200), no active form or stack form, health <= `healthThreshold` (20%), and not `knockedDown`.
- Zenkai interaction: zenkai only fires on a lethal blow, so a Saiyan chipped down to 10% never triggers one — that case must be able to charge, which is why there is no zenkai requirement by default. The optional `requireZenkaiSpent` (default false) narrows charging to the `Zenkai` cooldown running OR `RacialData.zenkaiPermanentUses` having reached `saiyan.permanentMaxBuffs` (`meetsZenkaiGate`, also skipped when racial skills / zenkai are disabled). Independently of that flag, while `Status.knockedDown` is set (the zenkai knockout) the meter neither gains nor drains, so a zenkai never eats the charge.
- Gain/drain: while `canCharge` holds the meter fills on its own at `idleGainPerSecond` (10/s, so ~10 s of standing under 20% health) and never drains — meeting the requirements is enough, hits only speed it up. On top of that `FalseSuperSaiyanEvents.onFinalDamage` (right after `RageEvents.onFinalDamage` in `CombatEvent`) adds damage DEALT to worthy targets (`gainPerDealtHealthFraction`) and damage TAKEN over `significantDamageTakenRatio` of max health (`gainPerReceivedHealthFraction`, the larger of the two), both proportional to the health fraction removed, capped by `maxGainPerHit` and scaled by `activeGainMultiplier` once transformed. The health check runs on the PRE-hit health, so the blow that drops you under 20% is the one hit that does not count. Draining only happens when `canCharge` is false (healed back over the threshold) or once transformed, and then only `combatGraceSeconds` after the last hit either way, at 100 per `drainSeconds` / `activeDrainSeconds`. Set `idleGainPerSecond` to 0 to go back to a purely hit-driven meter.
- Transform/end: a full meter while `canCharge` transforms on the next tick (no ki/stamina cost, `TRANSFORMED` effect, `TRANSFORM_ON` sound). Once transformed ONLY the meter matters — the health threshold is an entry condition, checked in `canCharge`, which the active branch never calls, so healing back up does not drop the form. It ends at 0, on losing the base requirements, or on death. The form also carries zero energy/stamina/health drain so `TickHandler.handleActiveFormDrains` never reverts it, and that method's tailless-Saiyan rule (which reverts ANY active form when the SELECTED group is `oozaru`) is skipped for it — otherwise a tailless Saiyan with Oozaru selected in the wheel would lose the form on the tick it started.
- Power-up state: while the meter is charging the player reads as powering up — `Status.forcedAura` (NBT `ForcedAura`) lights the aura and `Status.forcedCharge` (NBT `ForcedCharge`) raises the hair (`HairStyleResolver` `kiCharging`) and counts as `activeCharging` in `TickHandler`, so ki refills on its own. Both keys are additive and independent of the player's own `kicontrol` aura toggle. `chargingKi` is deliberately NOT reused: the client re-sends its own key state every tick (`ClientStatsEvents`) and `MovementInputUpdateEvent` freezes movement while it is set. On transform `forcedCharge` clears and only `forcedAura` stays; `setChargeState` clears both (plus `rageActive`) for any non-Mutant Saiyan that is neither charging nor transformed, which also unsticks the flags if a form is cleared by a command or another system.

## Stat Curves (VIT health, DEF flat mitigation)

Two stats scale on a curve instead of a straight line: the per-point scaling starts at the class `*_scaling` value and grows quadratically up to `*_scaling_max` (`RaceStatsConfig.StatScaling`, defaults = 4x the minimum via `DEFAULT_VIT_SCALING_MAX_RATIO` / `DEFAULT_DEF_SCALING_MAX_RATIO` in `ConfigManager.setupScalingStats`) at the "knee", then stays at the maximum. The knee is a fraction of the highest reachable stat (`general-server.json` -> `gameplay.vitCurveKneeLevelMode/StatMode` and `defCurveKneeLevelMode/StatMode`, default 0.225 in level mode and 0.45 in stat mode; halved on 2026-09-22 so the ramp is felt early). The shared math is `StatsData.curveScalingAt` (per-point rate) and `curveValue` (its integral, so total value is continuous).

- VIT drives `getHealthBonus` (`getVitalityScalingAt/Max/CurveKnee`).
- DEF drives ONLY the flat mitigation: `getFlatDefense`/`getMaxFlatDefense` feed `rawFlatMitigation`, the adaptive mitigation ratio and the `cancelDamageMitigationThreshold` check in `calculatePostMitigationDamage`, plus `getFlatMitigation`/`getMaxFlatMitigation` for the stats screen. `getDefense`/`getMaxDefense` stay LINEAR on purpose and still feed the percentage reduction (`baseDefense / (k + baseDefense)`, capped), the block formula (`getDefenseLegacyUnits`), the ki disk check and the shadow dummy; giving the curved value to the percentage would hit `baseDamageReductionCap` at about half the resistance it does today.
- A race config without `DEF_scaling_max`/`VIT_scaling_max` (files generated before the key existed) falls back to the minimum scaling, i.e. no curve, until the file is regenerated.

## World Boss Fights (Janemba)

`server/world/worldboss`: `WorldBossManager` owns the lair, arena, spawn and the 72000-tick respawn; everything about a single FIGHT lives in `WorldBossSessions` (registry keyed by boss key, ticked from `WorldBossManager.tick` every tick of the Otherworld) and `WorldBossSession`. A session starts when the boss wakes (`WorldBossEntity.wakeUp`) or when `discoverAwakeBosses` finds an awake boss after a restart, and ends on the kill (`finishVictory`), on a leash reset (`finishDefeat`, from `returnToSleep`) or on a wipe. Tuning is `general-server.json` -> `worldBoss` (`GeneralServerConfig.WorldBossConfig`); the config is synced to clients like the rest of the file, so the HUD reads the linger time and the results screen the category weights from it.

- Participants: every player with a character that is within `contributionRange` (150) of the boss when the audience is refreshed (every `audienceRefreshSeconds`). Joining installs the hidden `worldboss_revive` technique (`ReviveTechniqueData`, `TechClassType` `REVIVE`, `TechniqueType.REVIVE`) into slot `reviveSlot` (1-based, default 4) and remembers what it displaced in `Techniques.reviveDisplacedTechnique` (NBT `ReviveDisplacedTechnique`); `uninstallRevive` puts it back when the fight ends, when the player leaves the dimension or on login without a session. `Techniques.equipTechnique/equipOrSwapTechnique/removeTechnique` refuse to touch the revive or its slot, so the menu, `/dmztech` and `DeleteTechniqueC2S` cannot move or delete it; the skills menu never lists it because its tabs filter by `instanceof Ki/Strike/EvasionAttackData`.
- Contribution (`WorldBossContribution`, one `Score` per player per boss key): damage dealt to the boss or its minions (`WorldBossCombatEvents.onDamageDealt`, split MELEE/STRIKE/KI/OTHER like `RageEvents.categorize`), damage mitigated (`DMZEvent.PlayerDamageMitigatedEvent`, posted at the end of `CombatEvent.overrideVanillaArmorReduction` with the defense/block split, plus `DMZEvent.BarrierAbsorbEvent` for ki barriers and the Android barrier, credited to the barrier's OWNER), damage received (`finalDamage` of the same mitigation event, keyed by the attacker's entity id so minions show separately) and healing (`LivingHealEvent` at LOWEST, credited to `HealContext.getAllyHealer()` when set, otherwise to the target as self-healing; skipped when `HealContext.isSystemHeal()` or `PassiveEventHandler.suppressHealingBonus`, which covers food, senzu and the revive restore; natural regen and the healing liquid never fire the event). Points = the four totals x their config weights; share = points / everyone's points.
- HUD (`client/gui/hud/WorldBossContributionHUD`, extras element `boss_contribution`, up to 8 rows, the local player replaces the last row when ranked lower): fed by `WorldBossContributionS2C` to the audience at most every 2 ticks when a score changed and at least once a second, cached in `ClientWorldBossContribution` (stale after 6 s). Rows alternate between share and compact points every 10 s; bar length is relative to the leader and tinted with the player's BASE aura colour (sent by the server, so untracked players keep their colour). The last packet on a kill carries `finished=true` and the HUD lingers `meterLingerSeconds` (15) for everyone who was in range; a wipe or reset sends `cleared=true`.
- Knockout: a lethal hit on a participant (the lethal branch of `overrideVanillaArmorReduction`, after the racial `onLethalDamage` so a Zenkai still wins, plus a `LivingDeathEvent` fallback for sources that skip the DMZ pipeline) becomes `WorldBossSession.knockOut`: `Status.knockedDown` with `KNOCKDOWN_DURATION`/`KNOCKDOWN_INVULN` = `KNOCKOUT_TICKS` (999999), forms cleared, charges cancelled, Glowing, a 5-second title/subtitle with the revives left, and `WorldBossPlayerStateS2C` so the client draws the desaturated red-bordered screen (`KnockoutScreenRenderer` + `shaders/post/knockout.json`, `loadFailed` guard, flat vignette fallback). Lives are only consumed by a successful revive; a player at 0 lives still gets knocked out instead of dying. Everyone knocked out at once = wipe: the knocked-out players are killed, the boss goes back to sleep. Any other end of the fight without a kill (`finishDefeat`: leash reset, `/dmzworldboss reset`, boss gone for 10 s, boss found asleep) RELEASES the downed players instead: they get up with the revive restore and keep their lives. While a session is active the boss counts as engaged (`WorldBossEntity.hasEngagedPlayer` -> `WorldBossSessions.isFightEngaged`) if any participant that is alive, not knocked out, not spectator/creative is within `contributionRange` of the anchor or within the 64-block leash of the boss itself; Yuse's anchor-only leash still applies on top. Without this the Super Janemba (it flies and warps) drifted past 64 blocks from the anchor and the boss reset the moment the last player near the anchor was knocked out. A session is bound to its boss UUID (`resolveBoss`; `onBossTransformed` rebinds it to the next form) so a `reset` that spawns a new boss cannot inherit the old scores. `enforceKnockouts` re-applies the state every second (login clears the flag, the async storage load can overwrite it) and re-installs the revive technique if a stats reload dropped it; relogging while down keeps you down, changing dimension leaves the fight.
- Revive: slot key -> `WorldBossReviveC2S(lockOnTargetId)` -> `WorldBossSession.tryStartRevive` (needs the technique, no `TechniqueCooldown_worldboss_revive`, target = the locked player, else the downed participant under the crosshair, else the closest one within `reviveRange`, and the target must have lives left). The cast runs `reviveCastSeconds` (15) in `tickCasts`; any `LivingHurtEvent` on the caster, moving more than a block or the target getting up cancels it, a cancel by damage/movement puts the technique on `reviveInterruptCooldownSeconds` (15). Revives stack: progress lives per TARGET (`reviveProgress`, +1 per active caster per tick), so two casters get the ally up in half the time, a helper who joins late shortens what is left, and a caster who drops out keeps the progress accumulated so far (it clears when nobody is casting). Completion restores `reviveRestoreRatio` (25%) of max health, ki and stamina (through `HealContext.asSystemHeal` so it is not counted as healing), takes a life and sets the full `reviveCooldownSeconds` (90) on every caster involved. Both sides get `WorldBossPlayerStateS2C` every tick: the caster's bar is `WorldBossReviveOverlay` (same place as the ki charge bar), the target sees the action-bar message; `ClientStatsEvents.onMovementInput` freezes the caster while `ClientWorldBossPlayerState.isCasting()`.
- Rewards (`WorldBossRewards`): `worldBoss.rewards.<bossKey>` is a list of `WorldBossRewardEntry` objects with the same fields as a quest reward (`type`, `item`/`count`, `amount`, `skill`/`level`, `command`, `formGroup`/`formName`, `code`) plus `chance`; each entry is turned into a `QuestReward` through `QuestParser.parseReward`, so quest reward types and addon-registered ones work. Contributors with `share >= minContributionShare` roll every entry: `chance >= 1` is guaranteed and its amount scales by `guaranteedRewardMinRatio + (1 - ratio) * points / bestPoints`; otherwise the chance is multiplied by `1 + rankChanceBonus[rank]` (MVP +25%, 2nd +15%, 3rd +10%). A SKILL reward that names a predefined technique also unlocks the technique. Each contributor gets the chat line with what dropped, their points and share, and a `[More info]` click that runs `/dmzworldboss results` (no permission; the other subcommands keep level 2) -> `WorldBossResultsS2C` from `WorldBossResultsCache` (30 min) -> `WorldBossResultsScreen`: rank badges, the four-colour bar (red damage, blue mitigated, orange received, green healed, hover for the breakdown), and the per-player chances/received rewards on the right; clicking a row switches the right panel to that player. The kill also shows a vanilla title to everyone in range (`announceVictory`: boss name, and for contributors their placement and share); a wipe or reset shows the defeat title (`announceDefeat`).
- Knockdown hardening that came with this: `LivingEntity.canBeSeenAsEnemy` returns false for a knocked-down player (`LivingEntityMixin`, so vanilla target goals drop them) and `DBSagasEntity.setTarget` ignores them; `StatsEvents` blocks vanilla attacks, interaction and jumping for knocked-down players; `PlayerAttackHelper.canAttack` (client swing) and `MinecraftMixin` cancel the attack; `SelectFormC2S`/`ExecuteActionC2S`/`SwitchActionC2S`/`FlyToggleC2S`/`NamekRegenC2S`/`RacialSlotActionC2S`/`RacialSecondaryActionC2S`/the Instant Transmission packets ignore stunned or downed senders; `TickHandler` cancels ki/action/technique charges while down and syncs when a knockdown expires; `WorldBossEntity.isEligible` and the party HUD "downed" overlay honour the flag.

## Config System

Runtime config root: `config/dragonminez`. Managed by `common/config/ConfigManager` (static; initialized from `DMZCommon.init()`).

Files loaded/generated:

- `general-user.json` (client-only prefs — never synced), `general-server.json`, `combat.json`, `training.json`, `skills.json`, `techniques.json`, `entities.json`.
- Per race (`DEFAULT_RACES` = human, saiyan, namekian, frostdemon, bioandroid, majin; custom race folders auto-detected): `races/<race>/character.json`, `races/<race>/stats.json`, `races/<race>/forms/*.json`.
- Stack forms: `forms/*.json`.
- (`<world>/dragonminez/wishes/*.json` is wish data owned by `WishManager`, not ConfigManager — see Wishes.)

Versioning rules:

- Config version is a **semver String** `"X.Y.Z"` (`ConfigManager.CONFIG_VERSION`, mirrored by each config class's `CURRENT_VERSION`/`configVersion`). `parseSemver` requires exactly 3 numeric components; anything else (all legacy `double`/`int` versions like `21.0`, `21.10`, `12`) is treated as outdated and forces an upgrade. Do NOT go back to numeric versions — `21.10` as a `double` equals `21.1`.
- Outdated or missing-version default config files are MOVED to `config/dragonminez/oldBackup/<same relative path>` (`backupOldConfig`) and regenerated (the three-way merge re-applies the author's still-valid edits). `oldBackup/` is excluded from config scans. The `old_` filename prefix is only a skip-filter for user-authored form files — it is NOT the backup mechanism.
- **Unparsable (malformed-JSON) files are NEVER moved or overwritten** — that would throw away the author's in-progress edits. `loadAndValidate` returns in-memory defaults for the session and leaves the file exactly as-is; the same guard covers default form files (`createOrLoadRace`/`createOrLoadStackForms` only write a default when the file is genuinely missing). Malformed race/stack/user form files, and malformed quest/saga/sidequest/wish files, are likewise skipped (not regenerated). All of these are recorded in `JsonLoadReport` so the author is told which file to fix; a syntax fix + `/dmzreload` restores their values. This is deliberate: brand-new custom quests/forms that are broken are reported, not salvaged.
- Regeneration merges **three-way** against the previous release's defaults bundled at `resources/data/dragonminez/previousConfigs/<same relative path>` (`loadBaselineObject`): if the user's value equals the old default it upgrades to the new default (propagates balance changes); if it differs it is kept (respects user edits). New default keys are added; user-added map keys are kept. With no baseline file (custom races/forms, or newly added defaults) it falls back to "preserve any value differing from the new default".
- **Per-release workflow:** before shipping, copy the previous release's generated `config/dragonminez` tree into `resources/data/dragonminez/previousConfigs/` (excluding `oldBackup`/`old_*`), then bump `CONFIG_VERSION`. Skipping this silently weakens the merge for everything without a baseline.
- The pre-`21.2` `DEFENSE_SCALING_FOLD` migration (×0.12) applies only to legacy numeric-version stats files and only folds user-modified `defenseScaling` values, avoiding double application.
- Default race/form files are regenerated only when missing or invalid/outdated. Unknown custom races and user-defined form groups are loaded and preserved (`putIfAbsent` over defaults); custom races skip default form generation entirely.

Known dead code / traps inside ConfigManager:

- The `config_defaults` template mechanism (`saveDefaultFromTemplate` reading `/assets/dragonminez/config_defaults/<name>`) points at a resource directory that does not exist; first-run generation silently falls back to no-arg constructor defaults. Do not assume templates seed files.
- The 7-arg `applySyncedServerConfig(...)` batch method is unused dead code; real sync is the per-file `applySpecificSyncedConfig` path.

Aura style (2D vs 3D) keys:

- Every aura type field is doubled: `auraType` / `extraAuraType` name a **2D** billboard sprite set (`textures/entity/races/aura/<type>_aura.png` + `_cross.png`, default `kakarot`), while `auraType3D` / `extraAuraType3D` name a **3D** shader style (default `smooth`). Present on `FormConfig.FormData` and, for the base look, `RaceCharacterConfig`. Only `smooth` and `sparking` exist in 3D; anything else falls back to `smooth` via `Aura3DRenderer.resolveType` (the single fallback point — the getters are plain Lombok and may return null/empty, which is how a blank value still means "don't override the race-level type"). The 2D names were deliberately NOT renamed to `auraType2D`, to avoid breaking configs already in the wild.
- Which of the two a viewer sees is NOT a config decision: see Player State (`Character#aura3D`) and `client/render/effects/AuraModeState`.
- The look of the 3D `smooth` aura is data: `FormConfig.Aura3DStyle`, stored as `aura3DStyle` (and `extraAura3DStyle`) on `FormData` and as `aura3DStyle` on `RaceCharacterConfig` for the base look. Keys: `size` [x,y,z], `flamePeaks`, `waveFrequency`, `waveSpeed`, `waveAmplitude`, `noiseDetail`, `upwardBias`, `coreAlpha`, `rimAlpha`, `rimPower`, `rimThreshold`, `coreColor`/`rimColor`/`noiseColor` (hex, empty = derived from the aura colour / no noise tint), `bloomIntensity`, plus four sparking-only keys: `spikeDensity` (spike columns, capped at 32 because the mesh has 128 segments and a spike needs four to resolve), `spikeBurstRate`, `spikeRarity`, `bandStart`. Every getter is null-safe, so a deleted key falls back to the base default. Tuned per-form presets live in `DefaultFormsFactory` (`aura3D()`, `kaiokenAura`, `darkAura`). Both 3D styles read the block; each ignores the keys that do not apply (sparking has no `flamePeaks`, `waveFrequency`, `upwardBias` or `noiseColor`, and reads `waveAmplitude` as spike reach and `waveSpeed` as surge speed). The alpha defaults are tuned for the hollow smooth shell: a sparking aura wants `coreAlpha` 0.18, `rimAlpha` 0.85, `rimPower` 6, `rimThreshold` 0.02, since it fills its interior.

2D aura orientation (`AuraRenderer#executeAuraShaderDraw`, `#applyAxisBillboard`). The sprite is an **axis-locked** billboard, never screen-aligned: its vertical is pinned to the aura's own axis (world up, or `flightAxis` while flying fast) and it only spins around that axis. A screen-aligned card tips with camera pitch, which both leaned the flame and swung its `AURA_2D_GROUND_OFFSET` lift along the camera's up instead of the world's, sliding the sprite off the character (up to ~105 px at 60 degrees of pitch with over-shoulder) and swinging its apparent width over a 2x range as you looked around. `applyAxisBillboard` takes the world direction the sprite's +Z should end up facing: the reverse of `Camera#getLookVector` when upright, which keeps the card parallel to the screen sideways so it never skews when the player sits off-centre; the line from the camera to the aura's centre while flying, where the axis IS the line of sight and the view direction has no usable horizontal component; and the look vector itself for the ground `_cross` disc, which reproduces the old `Ry(-yRot)` exactly. There is no over-shoulder compensation any more - the old `SHOULDER_LEAN_*` roll existed only to hide the screen-aligned tilt and now fights it.

- Upright, everything that used to read `Camera#getXRot` is measured off the line from the camera to the sprite's centre instead. `elevation` (that line against the aura axis) drives the cross-fade to the `_cross` ground sprite from `AURA_2D_CROSS_START_DEG` and the `pitchSquash` that comes with it, and decides whether the disc is flipped because the camera is genuinely underneath. Camera pitch only equals that elevation when the aura sits dead centre in the frame; over-shoulder, a wall-clamped camera, another player off to the side, or an oversized form all break the equivalence. **Flight deliberately keeps `flightAxisAlignment`** (the camera's look vector against the flight axis): there the axis is the player's own view, that reference is what the fade was tuned against, and the geometric line would collapse the cross to a foreshortened sliver whenever the camera is offset sideways.
- A wall can clamp the third-person camera inside the sprite, where it is a screen-wide wash with no silhouette left. `AURA_2D_NEAR_FADE_*` fades it out over roughly its own half width (`finalScaleX * SPAN`, bounded by `MIN`/`MAX` so a big form's aura never dims at ordinary third-person range, gone at `FLOOR` of that distance). This is the only alpha the 2D path takes from the camera.
- `KiSenseAuraRenderer` deliberately stays screen-aligned: it is a radially symmetric glow blob centred on the entity, not a flame that has to stand up.

3D aura rendering (`client/render/effects/Aura3DRenderer`, `AuraRenderer`). Both styles share one pipeline: a shell of revolution, all relief as vertex displacement, real-time motion from `AuraRenderer#advanceMotions`, and MRT bloom.

- `smooth` mesh: an egg-shaped shell (`AuraMeshFactory#getDropletMesh`, 96x96, position only). All flame tongues are vertex displacement in `aura_smooth.vsh`: `flamePeaks` vertical ridges x bands climbing at `Phase`, plus a tileable runtime noise texture (`AuraNoiseTexture`). `Peaks` is rounded to an integer and the noise repeats once per turn, so nothing seams where `atan` wraps.
- `sparking` mesh: a narrower egg (`AuraMeshFactory#sparkingProfile`, 72 rings x 128 segments, position/colour/normal; the colour is unused, there is no vanilla position+normal format). `aura_sparking.vsh` covers the shell with a grid of cells (`spikeDensity` thin columns x 18 rows, half that for the coarse ones x 12 rows); each cell fires, holds and kills its own spike on its own beat, and the grid climbs at `CLIMB_RATE` x `waveSpeed` (1.25s to cross the shell at the default, against the smooth aura's 0.8s). A spike lives about a third of a second, so it pops in and out as it rises rather than reading as a drawn-up flame. The spread of the per-cell draws is load-bearing and deliberately wide (length coefficient of variation ~0.97, beat rates 0.55x-1.55x, free per-column row offsets): raising the floors in `spikeLength` lines the shell with an even fringe, which reads as regular. The spread also drags the average length down, which is why `THIN_REACH`/`BIG_REACH` are larger than the displacement you actually see; tune those together. The needles cut into the outline band in the fragment stage climb at the same rate; the two constants have to be changed together. Spikes are suppressed to 15% away from the silhouette and rooted at the base, but deliberately kept alive over the crown: without them the round top of the egg reads as a smooth dome, which is exactly what the climbing tongues hide on the smooth aura. Shape is load-bearing: width over height is 0.66 and the widest band stays taller than it is wide (1.33:1). A wider shell, a flatter shoulder, a spike envelope that does not fade over the crown, or an outline band that is not damped on the near-horizontal caps (`vUp`) each turn the silhouette back into a rounded box.
- Motion is real-time and per aura owner (`AuraRenderer#advanceMotions`, once per frame per player), and both styles read it rather than the per-frame `alphaProgress` ramp, so ignition is frame-rate independent: `growth` ignites the shell in ~0.25s and shrinks it when the aura ends (ghost auras), each layer's shown `AuraStyle` eases towards its target (~0.5s) so transformations morph, and `phase` accumulates `waveSpeed` so speed changes never jump. Charging a form blends the style towards the next form by charge progress. Merged auras share the leader's motion state.
- `growth` drives more than size. Smooth swells the shell then bursts its tongues (`pow(Growth, 6)`); sparking swells the shell, runs a front up from the feet that lights the spike field, fires one overshoot as it passes, and on the way out pulls the spikes straight up and raises `bandStart` to 1 so the outline thins away instead of fading flat.
- Fragment output is two targets for both styles: colour (location 0) and bloom mask (location 1), so `BloomPipeline` capture records the glow without a second draw (see Bloom below). Under an Iris shader pack, or if the driver rejects the framebuffer, the shell is redrawn into the bloom mask instead. Sparking draws through `ModRenderTypes.getCustomAura`, whose stencil shard keeps it off the player's body; the capture framebuffer attaches the scene depth-stencil, so that survives capture.

Bloom, shared by every effect (2D/3D auras, lightning, flight trails, ki attacks): `client/render/shader/BloomPipeline`, fed by `EffectBloomRenderer.render` at the end of `PlayerEffectsRenderHandler#renderEffects`.

- One full-resolution mask per frame, premultiplied by coverage. Shaders with a `location = 1` output draw through `beginCapture`/`endCapture` (bound scene colour + mask + scene depth in one framebuffer). Everything else is queued with `AuraRenderer.captureBloom`/`captureAuraBloom` (ki attacks are their `KiRenderTask`s) and redrawn in its `bloomMode` through `beginRedraw`/`endRedraw` (mask + the main target's depth-stencil, so walls and the player's stencil mask still hide the glow). Under Iris only the redraw path runs.
- `resolve`: 2:1 downsample + separable blur at 1/2, 1/4, 1/8 (`bloom_down`, `bloom_blur`), then one blended composite into the main target (`bloom_composite`: bright colours glow additively with tone mapping, dark colours are laid over as a veil). The former `ki_bloom` PostChain is gone; `program/ki_blur_h.fsh`/`ki_blur_v.fsh` remain because `utility_blur` uses them.
- Under Fabulous graphics the whole effects stage draws into the main target (`BloomPipeline.bindMainIfFabulousLayer`): the weather target it would otherwise land in has cleared depth and sorts behind the terrain.
- Core shader JSON `blend` blocks must equal vanilla's (`add`, `srcalpha`, `1-srcalpha`, non-separate). Any other translucent mode latches `BlendMode.lastApplied`, after which vanilla shaders overwrite their callers' blend functions; the GUI vignette then paints the world black until an opaque post pass runs. Apply the shader first and set separate functions through `RenderSystem` afterwards (`Aura3DRenderer#drawShellMesh`, `BloomPipeline#resolve`).

Aura border (`client/render/effects/AuraBorderRenderer`, shaders `aura_border`, `aura_border_field`): a flaming outline that hugs the silhouette of any entity, independent of the 2D/3D aura. It is screen-space, not a mesh.

- Capture: an entity renderer wraps its buffer source with `AuraBorderRenderer.begin(entity, source, colorOrNull, partialTick)` and releases it with `end(...)` around `super.render`. The wrapper is a second `TransformationMaskBufferSource` (raw colour = per-frame border index in the red channel), so hair, armour and held items are in the silhouette and the skin/hair layers' capture toggles keep working (they forward to a nested outline source). Passing `null` as colour means "inactive": the border fades out over real time and the state is dropped. Captures are only accepted between `AFTER_SKY` and the effects stage, never in the Iris shadow pass, never for the first-person camera entity.
- `process` (end of `PlayerEffectsRenderHandler#renderEffects`, both the vanilla and the Iris path): flushes the mask into its own target with a copy of the main depth, then per entity (far to near) builds a blurred coverage field at 1/2, 1/4 or 1/8 resolution (picked from the on-screen thickness, scissored to the entity), draws the flames over the scene and redraws them into the bloom mask through `BloomPipeline.beginRedraw`.
- The mask flush MUST run with an identity `RenderSystem` model-view: at `AFTER_PARTICLES`/`AFTER_WEATHER` vanilla has the camera rotation pushed on the model-view stack, and the captured vertices are already in view space. Without it the mask is rotated twice and is simply empty in third person (it only "works" for geometry wrapped around the camera).
- Thickness is world-sized (`THICKNESS_PER_HEIGHT` x bounding-box height, projected), so the border keeps its proportion with distance and fades out below `FAR_FADE_PIXELS`. Noise is anchored to the entity's projected centre and scaled by the thickness, so it neither swims nor changes scale when the camera moves. Flames rise along the projected world up.
- Flames over something nearer than the entity are hidden by comparing the linearised scene depth with a per-entity depth (`DepthParams`). Verified under Fancy, Fabulous and Oculus + Complementary.
- Users: Ki Surge on players (`AuraBorderRenderer.playerColor`, active aura colour; the server no longer forces `auraActive` during a surge, see `TickHandler`), and supervillain saga NPCs (`SagaSupervillainLayer.borderColor` + a translucent skin tint).

Form lightning (`client/render/effects/LightningBoltRenderer`, shader `lightning_bolt`): the Dragon Ball style bolts around players with a lightning form or a Ki Surge (`AuraRenderer#renderSparksImpl`, third and first person) and around saga NPCs with `isLightning` (`DBSagasRenderer#executeLightningShaderDraw`). The old noise-displaced cross mesh (`lightning` shader, `AuraRenderer.getLightningMesh`) is still what `KiWaveRenderer` and `SPMajinCandyRenderer` use; leave it alone.

- A bolt is a flat ribbon rebuilt on the CPU every frame: a seeded polyline arcing around the body (uneven segment lengths, alternating kinks, pointed at both ends, up to two short forks), transformed to view space and expanded there with mitred joints so it always faces the camera. `u` runs -1..1 across the ribbon; the fragment stage turns it into a white core, a solid coloured outline and a soft halo, which is the whole look. Vertices are already in view space, so it draws with an identity model-view through its own `VertexBuffer`, never through `BufferUploader` (the model-view trap above).
- Timing is per burst, not per frame: two staggered tracks each fire a burst per period (`CHARGED_*` while the aura is active, `IDLE_*` otherwise) of one or two bolts spread over separate sectors and heights of the body, so one to four bolts from different sides are up at a time. A bolt's shape is seeded from entity id + track + cycle + index; it pops in at full strength, re-strikes once while it holds (`STRIKES_PER_LIFE`) keeping its anchor, and then always gets its own `FADE_TICKS` of thinning fade-out. `emitBurst` evaluates the previous cycle as well as the current one, because a bolt's delay + hold + fade can run past the end of its burst period; evaluating only the current cycle cut those bolts off in a single frame. Frame rate never changes the cadence.
- The stroke is deliberately thin with a strongly uneven width (swelling and pinching from joint to joint), uneven segment lengths, kinks that usually but not always alternate side, and short barbs at the joints; regular alternation reads as a sawtooth, not as drawn lightning. Charged bolts are wider only so they survive inside the aura.
- First person is its own placement (`drawFirstPerson` / `screenPath`), anchored to the CAMERA: bolts are laid out in camera space on a plane `FIRST_PERSON_DEPTH` ahead, sized from the projection matrix so they cover the same share of the screen at any FOV. Each bolt picks a spot anywhere on screen with a bias towards the edges (`FIRST_PERSON_EDGE_BIAS`, a power curve on the distance from the centre) and runs roughly along that edge, so the crosshair area stays mostly clear; it is drawn at about a quarter opacity (`AuraRenderer.LIGHTNING_FIRST_PERSON_ALPHA`). A bolt that appears in front stays where it appeared until it is gone, whatever the player does with the view: anchoring to the body made them swing with the body yaw, and anchoring to the world left them behind the player after a turn; both were rejected. Under Iris there is no depth test, as with the other effects. Bloom is a queued redraw of the same seeded geometry.

Trails. Two ribbon trails share one idea (positions sampled once per entity tick, drawn as a camera-facing ribbon in camera-relative world space with the view rotation as model-view) but not one look:

- `AuraTrailRenderer` (shader `aura_trail`) is the fast-flight aura trail of players and, through `submitEntityTrail`, the trail of both nimbus clouds (`FlyingNimbusRenderer`, `BlackNimbusRenderer`: 64 samples against the aura's 26, recorded only while the cloud moves and eaten from the tail when it stops). Entity trails are queued as `PlayerEffectQueue` entity effects so they draw in the effects stage with bloom, recover the view rotation from the entity's own render pose, are skipped in the Iris shadow pass, and are tracked in `ENTITY_TRAILS` so `forget` (which only knows about players) does not wipe them every frame. They use less white in the core and a weaker bloom (`ENTITY_CORE_WHITE`, `ENTITY_BLOOM`) or a yellow cloud's trail burns out to plain white. The nimbus entities no longer spawn their ambient and boost-trail `KINTON` particles; the boost burst is still particles.
- `KiTrailRenderer` is the comet tail of the small ki projectile (`KiProjectileRenderer`, render type 0 only). It is drawn with the ki attack shader itself so it matches the ball: `shapeMode` + `localPosMode` + `flameMode`, with the ribbon's across/along coordinates packed into the vertex colour. For that, `kiattack` now reads the vertex colour's alpha as a fade in `localPosMode` (the only other `localPosMode` mesh, `KiSpiralMesh`, writes 255). The tail is capped by length (`MAX_LENGTH` x projectile size), not by sample count, because projectile speeds differ a lot. It runs inside the projectile's `KiRenderTask`, so the bloom pass comes for free.

Aura colour balance: the 3D smooth aura tones its resolved colours down (`AuraStyle.BRIGHTNESS`, since the shell is lit by its own rim on top of the scene), and the 2D aura maps its sprite through `AuraRenderer.applyAuraColors` — one place for the four colour bands, brightened to sit at the same strength. Change both together.

Client/server config sync:

- On login (and `/dmzreload`), the server sends EVERY config file except `general-user` (`CLIENT_ONLY_CONFIG`), one gzip-compressed `SyncServerConfigS2C` per file; the first packet carries `reset=true` which begins a fresh sync batch. Payloads route by path into `SERVER_SYNCED_*` fields, and all `get*Config` getters return synced values while `serverSyncActive`. The client clears sync on disconnect (`ConfigManager.clearServerSync()` in `ForgeClientEvents`).
- `/dmzconfig` (ConfigCommand) live-edits single keys via `updateConfigValue` → `reloadSpecificConfig`, which **bypasses** version checks, oldBackup, and the three-way merge (straight deserialize + single-file sync). The in-game editor `DMZConfigEditScreen` persists via `saveRawConfig`. Only full `reload()`/`initialize()` run the validation+merge pipeline.

## Quest System

Quest data is world-save JSON, loaded by `common/quest/QuestRegistry.loadAll(MinecraftServer)` from `ForgeCommonEvents.onServerStarting` and `/dmzreload`. Runtime world structure:

```text
<world>/dragonminez/
  sagas/        # saga manifest JSON (recursive scan)
  quests/<questFolder>/   # quest files, loaded alphabetically (01_...json ordering)
  sidequests/   # side-quest JSON (recursive scan)
```

Key behaviors:

- Default generation: sagas require BOTH `storyModeEnabled` AND `createDefaultSagas`; side quests require only `createDefaultSideQuests` (independent of story mode). Runtime load gates are separate: sagas load only when `storyModeEnabled`, side quests only when `sideQuestsEnabled`.
- Default files are now **version-upgraded in place** by `QuestUpgrader` (the quest-side analogue of the `ConfigManager` three-way merge). Every generated quest/saga/side-quest is stamped with `"defaultsVersion"` (`QuestUpgrader.DEFAULTS_VERSION`, a semver string). On load, `QuestDefaults`/`SagaDefaults`/`SideQuestDefaults` route through `QuestUpgrader.upgradeOrWrite`: missing → write fresh; stamp equals current → skip (fast path); stamp missing/older → three-way merge the user file against the shipped baseline (`resources/data/dragonminez/previousQuests/<same relative path>`) and the new code default. Merge rule (matches the config merge, plus a conflict flag): user==old-default → take new default (balance fix propagates); new==old → keep user; **both changed → keep the user's value and record a conflict** (never destructive). User-added keys preserved; arrays (objectives/rewards) merge only when structurally aligned, else whole-array conflict → keep user. The pre-merge file is copied to `<world>/dragonminez/oldBackup/<relative>` only when the merge made a substantive change (a pure re-stamp does not back up).
- **Per-release baseline workflow (required, like `previousConfigs`):** before shipping a release that changes default quest values, snapshot the *previous* release's generated quest tree (`<world>/dragonminez/{sagas,quests,sidequests}`) into `resources/data/dragonminez/previousQuests/` (same relative layout), then bump `QuestUpgrader.DEFAULTS_VERSION` and apply the new values. With no baseline for a file, the merge falls back to "preserve any user value differing from the new default" (non-destructive, but that release's balance fixes won't auto-apply to edited fields).
- Upgrade results accumulate in `QuestUpdateReport` (cleared each `loadAll`): a summary is logged and written to `<world>/dragonminez/quest_update_report.txt`. The whole feature is gated by the `autoUpdateQuests` server-config flag (default true; false = legacy generate-only-if-missing). The in-chat notification is no longer quest-specific — `loadAll` pushes a one-line summary into the unified `JsonLoadReport` (see below), which surfaces it to players on login.
- **Unified JSON load report (`common/diagnostics/JsonLoadReport`):** a single in-memory collector of load-time problems across all runtime JSON — configs, quests/sagas/sidequests, and wishes. Loaders record `ERROR` entries when a file is malformed/failed (`ConfigManager.loadAndValidate` parse failures, `ConfigLoader` form-file skips, `QuestRegistry` saga/quest/sidequest parse skips, `WishManager.loadWishConfig` skips — each carrying the deepest Gson cause with its `line/column/path`) and `UPDATE` entries when defaults were auto-upgraded. Each subsystem tags its entries with a `source` (`"config"`/`"quests"`/`"wishes"`) and clears only that source at the start of its own load, so `/dmzreload config` doesn't wipe quest findings. `server/events/DataReportEvents.onPlayerLogin` shows the report to **every** player on login (not just ops), gated by the `developer.reportJsonProblemsInChat` server-config flag (default on). Purpose: let server owners/addon authors who hand-edit these files see exactly which file broke and where, instead of a silent reset-to-defaults. Console logs and `oldBackup/`/report files remain authoritative.
- Six default sagas: saiyan → frieza → android, then future and buu both branch from android, movies requires buu.
- Saga quest key is `sagaId:numericId` (the JSON `id` int, not the filename — duplicate ids in one folder silently collide). Side-quest key is the JSON string id.
- Objective types: ITEM, KILL, INTERACT, STRUCTURE, BIOME, DIMENSION, COORDS, TALK_TO, DRAGON_SUMMON, SKILL. Reward types: TPS, ITEM, ALIGNMENT, COMMAND, SKILL, TRANSFORMATION, KI_TECHNIQUE.
- **Reward difficulty (per reward, in `QuestParser.parseReward`):** each reward carries an `EnumSet<Difficulty>` (`QuestReward.difficulties`, default = all) parsed from an optional `difficulty` field (aliases `difficulties`/`difficultyType`/`minDifficulty`). The value is an **explicit allow-set**, accepted as a JSON array (`["NORMAL","HARD"]`), a comma/space string (`"NORMAL, HARD"`), or a single name (`"HARD"`); unknown tokens are dropped, absent/empty = all difficulties. `isUnlockedFor(d)` is set membership — NOT a minimum threshold, so `"NORMAL"` means Normal-only and `["EASY","HARD"]` is expressible. The old `hard:`/`normal:` **type-string prefix was removed** (a leftover `"type":"normal:ITEM"` now fails to match and the reward is dropped). `SyncQuestRegistryS2C.serializeReward` mirrors this: plain type name + a `difficulty` array (only when the set is a strict subset), re-parsed client-side via `QuestParser`. `QuestService.claimAvailableRewards` gives a reward only when `isUnlockedFor(pqd.getDifficulty())`, scaling ITEM/TPS/ALIGNMENT amounts by `Difficulty.questRewardMultiplier()`; SKILL/TRANSFORMATION/KI_TECHNIQUE/COMMAND are unlocks and don't scale. Tree + NPC panels group rewards by difficulty-set via `QuestTextFormatter.groupRewardsByDifficulty`/`describeRewardDifficulties` (header lists the set, e.g. "Only: Normal, Hard"; locked groups greyed). Defaults (`QuestDefaults`/`SideQuestDefaults`) tag rewards with the `onlyOn(reward, "NORMAL", "HARD")` helper.
- `loadAll` builds indexes (objective type, quest giver, turn-in) used by `QuestService`. `loadAll` does NOT sync to clients — `SyncQuestRegistryS2C` is sent from `StatsCapability.syncToClient()` on login and from `ReloadCommand`; reloading quests outside those paths leaves clients stale until relog.
- `SyncQuestRegistryS2C` carries two JSON strings capped at 1 MiB each; the standalone-quests blob excludes SAGA-type quests (sagas travel in the sagas blob).
- Kill objectives: contiguous KillObjectives in a sequential quest unlock and count as one block (`QuestEvents.isKillObjectiveUnlocked` walks back to the block start). Default `CountMode.QUEST_SPAWNED_ONLY` requires the killed entity to carry `dmz_quest_key` + `dmz_quest_objective_index` + `dmz_quest_owner` tags (written by `QuestService.spawnKillObjectives`, which also writes stat/AI-tier/transformation-override tags).
- Quest failure: party wipe fails only quests that have at least one KillObjective; `failQuest()` increments failureCount and resets progress.
- `PlayerQuestData` NBT: `difficulty`, `questState`, `difficultyChosen`, `partyState`, with legacy migration from `difficultyStates`/`hardModeEnabled`. Party join adopts the leader's difficulty wholesale.
- Server code uses `getQuest()/getSaga()`; client GUI uses `getClientQuest()/getClientSaga()` — cross-side calls silently return empty.

Quest update rules: preserve filename ordering conventions, translation-key titles, and user-authored addon quests when changing the parser schema.

## Wish And Dragonball Systems

Two interleaved pipelines — definitions (ball sets, radars, dragons) and wishes — with three sources: hardcoded bootstrap, external addon packs, and per-world overrides. There is **no in-jar datapack wish/definition JSON**: `DragonDefinitionReloadListener` and `DragonWishRegistry` are `SimpleJsonResourceReloadListener`s rooted at `dragonminez/dragonballs` but both IGNORE the scanned datapack JSON and call `DragonBallPackManager.loadAll()` instead. Adding standard datapack JSON under that path does nothing.

- `DragonBallDefinitions` holds bootstrap maps (hardcoded earth/namek sets, shenron/porunga, radars, recipes) plus runtime maps set on reload. `syncRegisteredBlocks()` copies Forge `RegistryObject<Block>` refs from bootstrap into same-id runtime definitions after every reload — addon packs cannot introduce new blocks at runtime; new blocks need a `Main*` deferred register.
- `DragonBallPackManager.loadAll()` scans folder and `.zip` packs under the game-dir `dragonballs` root (plus sibling candidates), routing files by suffix (`definitions/{ballset,radar,dragon,wishes}.json`, `assets/...`). It runs three times per boot/reload (bootstrap static init, definition listener, wish listener).
- `WishManager.loadWishes(server)` runs at `onServerStarting` (not on datapack reload): starts from addon-pack wishes, then merges `<world>/dragonminez/wishes/*.json` (auto-creating default `shenron.json`/`porunga.json`). World-save wish files are **plain JSON arrays**; the dragon id is the filename stem, and a file fully replaces that dragon's wish list. The `{"dragon": ..., "wishes": [...]}` object wrapper is the addon-pack format only. Note: a vanilla `/reload` re-runs the listeners but NOT `WishManager.loadWishes` — world-save overrides need `/dmzreload` or restart.
- Wish types (registered in `common/util/WishTypeAdapter`, 10 total): `item`, `command`, `tps`, `multi_wish`, `skill`, `passivereset`, `recustomize`, `relocatestats`, `changedifficulty`, `resetstory`.
- Grant flow: owner right-clicks `DragonWishEntity` → wish screen (shenron 1 wish, porunga 3) → `GrantWishC2S` with indices → server validates against `WishManager.getAllWishes()` and grants → entity despawns after 100 ticks, resets weather/time, and rescatters balls via `DragonBallsHandler.scatterDragonBalls`.
- Scattering (`server/events/DragonBallsHandler`): first spawn scatters full sets, later scatters cap to `maxSets`; positions are XZ-random around world spawn, tracked as "pending" in `DragonBallSavedData` (per-level SavedData, key `dragon_balls_data`, with legacy Earth/Namek key migration) until the chunk loads or a player comes within 128 blocks, then placed on the heightmap. Radar sync (`RadarSyncS2C`) includes pending balls and fires on scatter, place/break, login, dimension change, and a 100-tick timer.
- `DragonBallDataPackResources` is a synthetic PackResources that only injects crafting recipes for addon radar items.

## Storage

`StorageManager` (`server/storage`) selects the player-data backend from `general-server.json` (`StorageConfig`, default `NBT`):

- `NBT`: `activeStorage == null`; the whole custom layer (StorageManager/DataSyncHandler/JsonStorage/DatabaseManager) is inert and persistence is purely the vanilla capability path (`StatsProvider` INBTSerializable → player `.dat`).
- `JSON`: `<world>/dragonminez/playerdata_json/<uuid>.json` (pretty-printed via NbtOps/JsonOps).
- `DATABASE`: MariaDB via HikariCP (`jdbc:mariadb` only); gzip NBT in a `MEDIUMBLOB` keyed by uuid. Hikari `poolSize` and async `threadPoolSize` are separate config keys.

Behavior and caveats:

- Vanilla `.dat` capability persistence is ALWAYS on. JSON/DATABASE modes double-persist: the custom store async-loads on login (`DataSyncHandler` on `PlayerLoggedInEvent`) and its data overwrites vanilla-loaded values on the server thread, then a full `StatsSyncS2C` is pushed. Logout saves via `DataSyncHandler`.
- The DB "fallback" is a log message, not a code path: on connection failure `DatabaseManager` stays the active storage and silently no-ops; durability comes only from the vanilla `.dat` path. Nothing switches to JsonStorage/NBT.
- `savePlayer` serializes NBT on the server thread and submits only the IO to the executor; it skips saving when `!isDataLoaded && !hasCreatedCharacter` (blank pre-character guard).
- Auto-save is a hardcoded 5-minute `scheduleAtFixedRate` (not config-driven), JSON/DATABASE only.
- `DMZEvent.PlayerDataLoadEvent` fires before apply (tag mutable), `PlayerDataSaveEvent` after serialize / before write.
- Login load is async and racy: briefly after login the player has vanilla-loaded values until the custom apply runs; a disconnect during load skips apply.
- `/dmzreload` reload saves online players, then `shutdown()`+`init()`; note the async executor is recreated without shutting the old one down (leak on repeated reloads).
- Never block the server thread with DB/filesystem work; never log credentials; preserve `StatsData` NBT key names (cross-backend contract).

- Static resources (`src/main/resources/`): structure `.nbt`, Otherworld regions, biome modifiers, worldgen JSON, weapon attributes.

## Commands And Permissions

`DMZServer.registerCommands()` registers 22 commands from `server/commands`: Stats, RacialSkill, Bonus, Effects, Skills, Tech, Forms, Points, Debug, Mastery, Locate, Party, Story, Revive, Reload, Config, Weight, Raid, Alignment, Tail, Halo, Restore.

- Permissions: Forge PermissionAPI `PermissionNode<Boolean>`s in `DMZPermissions` (~70 nodes, self/others split), default fallback permission level 2. `hasPermission()` contains a hard-coded name-based admin bypass for `ezShokkoh`, `ImYuseix`, `MrBrunoh` — do not replicate this pattern; flag it if touching permissions. `RaidCommand` checks `hasPermission(2)` directly instead of DMZPermissions.
- `/dmzreload [all|config|story|wishes]` (default all): config scope does `ConfigManager.clearServerSync()` + `reload()`, `StorageManager.reload()`, NPC alignment + placement reload/respawn; story scope reloads `QuestRegistry`; wishes scope reloads `WishManager`; then resyncs configs (per-file `SyncServerConfigS2C`), `ProgressionSyncS2C`, `SyncQuestRegistryS2C`, `SyncWishesS2C` to online players. Requires `DMZPermissions.RELOAD`.

## Integrations

- Forge, Minecraft, GeckoLib, TerraBlender, and Curios are mandatory (`mods.toml`).
- Legendary Tooltips, Epic Fight, and Better Combat are hard-incompatible (mods.toml + startup crash in the entry class).
- JEI APIs are compile-only (`JEIDragonMineZPlugin` in `common/compat`); runtime JEI is a client-only dev mod.
- WorldGuard compatibility (`WorldGuardCompat`) is reflective and defensive — no hard dependency.
- Lombok is used at compile time (`compileOnly` + annotationProcessor).
- Crowdin uses `assets/dragonminez/lang/en_us.json` as the source locale (`crowdin.yml` maps locale filenames).

## Localization

- Source of truth: `src/main/resources/assets/dragonminez/lang/en_us.json`. Keep keys stable unless intentionally renaming; add entries for any user-visible text.
- Validate with `scripts/check_lang.sh` (jq). CI runs it in `.github/workflows/languages.yml`, which also uploads the source file to Crowdin on lang changes, on a 2-day schedule, and manually.

## Datagen

`common/datagen/DatagenManager` (mod-bus `GatherDataEvent`) registers providers: recipes (`DMZRecipeProvider`, plus `DMZKikonoRecipeProvider` and `DMZPatternRecipeProvider` used by it; the latter emits `dragonminez:pattern_crafting` 6x6 shaped recipes for the Pattern Station (per-Pattern dye pixel art of its chestplate) and fails datagen if two Patterns share a grid), loot tables, block states, item models, block/item/entity-type tags, worldgen (`DMZWorldGenProvider`) + biome tags, advancements, space pod destinations, dragon definitions, and dragon wishes.

Run `.\gradlew.bat runData` after changing providers and review the `src/generated/resources/` diff (`.cache/` is excluded from packaging).

## Beta Access Verification

Beta/alpha builds (version contains `-beta`/`-alpha`) reject non-whitelisted players in `ForgeCommonEvents.onPlayerLogin`. `BetaWhitelist` loads asynchronously from `https://raw.githubusercontent.com/DragonMineZ/.github/refs/heads/main/allowed_betatesters.txt` at server start with a small hardcoded fallback list. The disconnect is detected client-side by `DisconnectedScreenMixin`, which adds a `Verify here` button opening `BetaAccessVerificationScreen` → browser to `https://downloads.dragonminez.com/beta-access/start?username=<minecraft_username>` (override with JVM property `dragonminez.betaAccessUrl`).

The matching `dragonminez-ai` bot flow is intentionally narrow: Discord OAuth → guild member → Patreon beta roles → existing Patreon link + whitelist PR auto-approval. Keep it a small verification bridge, not a general public API.

## CI And Release Automation

Workflows in `.github/workflows/`:

- `gradle.yml` — Java CI: builds on PRs and pushes to `main` touching Java/build files; submits the Gradle dependency graph.
- `languages.yml` — Crowdin check & upload (see Localization).
- `codeql.yml` — CodeQL analysis. PMD rulesets live in `.github/workflows/pmd/`.
- `dev-jar-upload.yml` — dev distribution: runs on pushes to **`main`** (paths-filtered to Java/resources/Gradle/workflow inputs) and manual dispatch. Builds and uploads ONLY the no-classifier jar `build/libs/dragonminez-<mod_version>.jar` (never `-slim`) via SSH/SCP to the VPS with pinned host keys (vars `DMZ_VPS_HOST`/`DMZ_VPS_PORT`; secrets `DMZ_VPS_USER`/`DMZ_VPS_SSH_KEY`/`DMZ_VPS_KNOWN_HOSTS`/`DMZ_VPS_UPLOAD_DIR`). Upload is atomic (temp name → move), chmod `0644`, SHA-256 verified, then prunes old artifacts keeping the two newest `dragonminez-*__*__*.jar`. After upload it notifies the Discord bot locally on the VPS at `http://127.0.0.1:8088/dmz-dev-jar` (bypassing Cloudflare) using `DMZ_RELEASE_BOT_WEBHOOK_SECRET`.
- `release-prepare.yml` — validates stable release candidates on `main`, builds the jar, writes manifest artifacts (via `scripts/release/prepare_release.py`), and posts the candidate payload to the Discord bot at `https://release-bot.dragonminez.com/dmz-release` (secret `DMZ_RELEASE_BOT_WEBHOOK_SECRET`).
- `release-publish.yml` — triggered by Discord-bot approval through `repository_dispatch` (`dragonminez_release_approved`) or manual dispatch with the same payload fields. Verifies the approved commit is still `origin/main` HEAD, rebuilds, compares the jar SHA-256 against the approved manifest (**mismatch is a warning, not a failure** — resource optimization is not byte-reproducible), publishes to Modrinth and CurseForge, updates `update.json` (via `scripts/release/update_forge_update_json.py`), and commits it back to `main`.

Rules:

- Do not publish GitHub Release jar assets from these workflows.
- Stable `main` releases only: versions containing `alpha`/`beta` are skipped or rejected.
- The Discord bot must not hold Modrinth/CurseForge tokens; those stay in GitHub Actions secrets.
- Python release helpers live in `scripts/release/` (`prepare_release.py`, `release_common.py`, `update_forge_update_json.py`, `release_tools_test.py`).

## Update Checklist For Future Agents

Before changing behavior:

- Identify whether data is code-owned, datapack-owned, config-owned, world-save-owned, or addon-owned.
- Prefer editing canonical loaders/default factories over hand-editing generated/runtime files.
- If a JSON schema changes, update parser, defaults, config version, sync packets, and docs together. For configs, also refresh the `previousConfigs` baseline at release time.
- If adding content, register it through the appropriate `Main*` class and ensure datagen/assets/lang are complete.
- If adding packets, add the packet class and APPEND its `NetworkHandler.register()` entry (never reorder).
- If adding reloadable data, wire a reload listener and a sync path if clients need it.
- If changing server config used by clients, remember sync is generic per-file, but nested layouts need routing in `applySpecificSyncedConfig`.
- If changing player state, update ctor/save/load/copyFrom/sync/storage expectations together.
- If changing worldgen/datagen, run `runData` and inspect generated resource diffs.
- If editing language files, run `scripts/check_lang.sh` or equivalent JSON validation.
- If editing code, run at least `.\gradlew.bat build` unless blocked, and state any blockers.
